002: Агент/Инструмент

  • Зависит от: 001: Агент/Запрос
  • Дополняется: 003: Агент/Действие
Инструмент

Схема, описывающая возможность, которую может использовать агент. Она передается LLM как часть запроса и служит структурированным интерфейсом для возможного действия. LLM активирует инструмент, генерируя Вызов с определенными параметрами, который затем выполняется либо скрыто самой LLM, либо явно с помощью зарегистрированной функции кода (Действие).

Инструмент — это интерфейс на основе схемы, который описывает структурированную возможность, доступную агенту. Он служит базовым строительным блоком для всех действий агента, позволяя LLM понимать и выбирать из списка возможных вариантов поведения.

Что такое Инструменты?

Инструменты — это основа систем действий агентов. Они открывают новую возможность: выбор действия в контексте — позволяя агентам выбирать и выполнять подходящие действия в зависимости от текущей ситуации.

Инструменты обеспечивают:

  • Структурированные интерфейсы: описанные схемой возможности, которые агенты могут находить и понимать
  • Строгую типизацию: четкие контракты для входных и выходных данных
  • Компонуемость: строительные блоки, из которых складывается сложное поведение агентов
  • Интеграцию с LLM: схемы, которые языковые модели могут анализировать и выбирать

004: Агент/Вызов

Когда агент заполняет определенные параметры для Инструмента, он создает Вызов — экземпляр Инструмента со всеми заполненными обязательными параметрами, представляющий собой конкретный запрос на выполнение.

Когда использовать систему Инструментов

Используйте систему Инструментов, когда агентам нужно:

  • Динамически выбирать действия в зависимости от контекста и ситуации
  • Выбирать между несколькими возможностями для достижения цели
  • Выполнять разные реализации одной и той же возможности (например, обращаться к разным поисковым системам)
  • Совмещать логику LLM с явным кодом в процессе принятия решений

Схема как интерфейс

Система Инструментов строится на фундаментальном принципе: Инструменты — это исключительно схемы, которые определяют интерфейсы, но не требуют обязательной реализации. Такое разделение интерфейса и реализации является ключом к гибкости и компонуемости системы.

Схема Tool — это стандартный объект JSON Schema. Любое поле без префикса подчеркивания считается параметром инструмента. Система использует специальные мета-поля (с префиксом _) для определения системных свойств, которые управляют идентификацией и выполнением инструмента.

Расширения:

  • _activity: Связывает инструмент с детерминированной функцией кода для явного выполнения. См. 003: Агент/Действие
  • _delegate: Делегирует выполнение инструмента изолированному, внешнему делегату. См. 014: Агент/Делегат
  • _outputPath: Делает инструмент сохраняющим состояние, записывая его вывод в постоянный объект данных. См. 008: Агент/Вывод
  • _instance: Направляет выполнение инструмента к определенному экземпляру в многоэкземплярном запросе. См. 013: Агент/Экземплирование

Схема Инструмента полностью определяет его интерфейс:

  • title: понятное человеку имя схемы (необязательно).
  • description: объясняет, что делает инструмент.
  • properties: любые поля без подчеркивания определяют необходимые входные данные для инструмента.
  • _tool: уникальное имя для идентификации инструмента.
  • _output: структура ожидаемого результата работы инструмента.
  • _why: поле, добавляемое системой, чтобы агент мог объяснить, почему он выбрал этот инструмент.

Протоколы более высокого уровня выстраивают оркестрацию рабочих процессов, управление состоянием и политики выполнения поверх этих примитивов.

Определение Инструмента

Инструменты определяются в виде JSON-схем. В примере ниже показан Tool для анализа тональности текста. Этот Tool предназначен для скрытого исполнения, так как опирается на внутреннее понимание языка самой LLM и не требует внешней функции.

Определение Инструмента

Tool.register('sentimentAnalysis', {
  type: 'object',
  description: 'Анализирует тональность текста',
  properties: {
    _tool: { type: 'string', const: 'sentimentAnalysis' },
    text: { type: 'string', description: 'Текст для анализа' },
    _output: {
      type: 'object',
      properties: {
        sentiment: { type: 'string' },
        confidence: { type: 'number' },
      },
    },
  },
});

Пример вывода LLM

// Запрос: "Какая тональность у фразы 'Это лучшее!'"
{
  "_tool": "sentimentAnalysis",
  "text": "Это лучшее!",
  "_output": {
    "sentiment": "positive",
    "confidence": 0.99
  }
}

Переопределение Инструментов

Инструменты идентифицируются по их уникальному имени _tool. Если запрос содержит несколько определений для одного и того же инструмента (например, в истории сообщений), предпочтение отдается последнему определению.

Такое поведение «побеждает последний» открывает возможности для мощных паттернов компоновки:

  • По умолчанию и Переопределение: агенты могут быть инициализированы со стандартным набором инструментов, которые затем можно настроить под конкретные задачи, просто добавив новое определение.
  • Контекстная адаптация: описание инструмента или его параметры можно уточнять прямо в ходе разговора, чтобы они лучше подходили к меняющемуся контексту.

Когда возникает конфликт, более раннее определение игнорируется и исключается из финальной схемы, отправляемой в LLM.

Компоновка схем для LLM

Агент не просто работает с инструментами; ему часто нужно выдать окончательный структурированный результат после завершения задачи. Для этого среда выполнения агента объединяет схемы всех доступных Инструментов с пользовательской выходной схемой (output schema). Это создает единую объединенную схему, которая передается в LLM в рамках Запроса.

Такая компоновка дает LLM выбор того, как именно отвечать. В зависимости от промпта она может:

  • Сгенерировать только meta и calls: Если задача требует промежуточных шагов, LLM вызовет один или несколько инструментов, обновит версию Идеи в объекте meta и оставит поле output со значением null.
  • Сгенерировать только meta и output: Если на промпт можно ответить напрямую без использования инструментов, LLM укажет окончательный результат в поле output, обновит meta и оставит calls пустым.
  • Сгенерировать всё: В некоторых случаях LLM может выполнить действие и выдать окончательный результат за один шаг, соответствующим образом обновив meta.

Чтобы уменьшить неоднозначность и предотвратить частые галлюцинации LLM, система интеллектуально адаптирует схему инструмента на основе режима его выполнения.

  • Если Инструмент является скрытым (нет соответствующего Действия), его схема _output включается как есть, поскольку LLM сама отвечает за генерацию результата.
  • Если Инструмент является явным (опирается на Действие), его свойство _output динамически удаляется из схемы перед отправкой в LLM. Это обеспечивает четкий и однозначный контракт: единственная задача LLM — предоставить правильные входные данные для инструмента. Информация о возвращаемом значении инструмента должна быть включена в его description, чтобы помочь LLM в планировании, не давая ей поля, которое она могла бы неверно заполнить.

Этот механизм позволяет единому гибкому интерфейсу обрабатывать как простые одношаговые ответы, так и сложные задачи, использующие множество инструментов. Разработчик предоставляет схемы Инструментов и выходную схему отдельно, а система комбинирует их в структуру, которую LLM может использовать для выбора наилучшего плана действий.

Пример ниже иллюстрирует, как компонуются схема Инструмента и выходная схема.

Конфигурация Агента

Agent.Request(
  config, // Конфигурация для запроса (например, модель, температура)
  {
    // Выходная схема
    type: 'object',
    properties: {
      summary: { type: 'string' },
    },
    required: ['summary'],
  },
  [
    // Контекст
    {
      type: 'tool',
      tool: {
        greetUser: {
          type: 'object',
          properties: {
            userName: { type: 'string' },
          },
          required: ['userName'],
        },
      },
    },
    { type: 'text', text: 'какой-то ваш промпт здесь' },
  ]
);

Скомпонованная схема (для LLM)

{
  "type": "object",
  "properties": {
    "meta": {
      "type": "object",
      "description": "Метаданные об идее, включая версию и идентичность. Ожидается, что LLM обновит их, например, повысив версию.",
      "properties": {
        "path": {
          "type": "string"
        },
        "version": {
          "type": "string"
        }
      }
    },
    "output": {
      "type": ["object", "null"],
      "properties": {
        "summary": { "type": "string" }
      },
      "required": ["summary"],
      "additionalProperties": false
    },
    "calls": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "_tool": { "const": "greetUser" },
          "userName": { "type": "string" }
        },
        "required": ["_tool", "userName"]
      }
    }
  },
  "required": ["meta", "calls", "output"]
}

Расширение Инструментов с помощью Мета-свойств

Помимо определения базовых параметров инструмента, его схема может быть расширена при вызове. Это другая форма компоновки, при которой новые варианты поведения наслаиваются на один инструмент.

  • 004: Агент/Вызов

Когда агент принимает решение использовать инструмент, он создает Вызов — конкретный экземпляр этого инструмента. Вызов включает параметры для инструмента, но также может быть дополнен специальными мета-свойствами (с префиксом _), которые предоставляют дополнительные инструкции для механизма выполнения. Эти свойства управляют аспектами выполнения инструмента, которые выходят за рамки его базового определения.

Этот механизм позволяет гибко использовать простую базовую схему инструмента. Вызов становится богатой инструкцией, которая указывает, что делать (инструмент и его параметры) и как это делать (мета-свойства). Последней частью пазла является понимание различных способов, которыми на самом деле может быть выполнен Вызов.

Скрытое и Явное Исполнение

Как только Вызов сгенерирован, системе необходимо его выполнить. Схема Tool, будучи просто интерфейсом, сама по себе не содержит логики выполнения. Вместо этого ее выполнение может происходить одним из двух способов. По умолчанию используется скрытое исполнение (latent execution), при котором LLM задействует свои внутренние механизмы рассуждений для генерации результата, что идеально подходит для задач на основе языка или знаний. Для действий, требующих взаимодействия с внешним миром — например, вызова API или обращения к базе данных — Tool должен быть связан с детерминированной функцией кода. Такая явная реализация называется Действием.

  • 003: Агент/Действие.

Разделение интерфейса Инструмента и реализации Действия — это ключевой принцип проектирования. Это позволяет определять возможности агента и рассуждать о них абстрактно, в то время как базовая логика выполнения может подменяться или обновляться независимо. В 003: Агент/Действие описано, как Действия предоставляют конкретную логику для Инструментов.
