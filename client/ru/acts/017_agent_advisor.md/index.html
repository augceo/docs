Советник

Специализированное контекстное сообщение (с kind: "advisor"), которое задает персону или аналитическую модель. Оно дает агенту команду сгенерировать структурированное "мнение" или оценку уверенности до выбора Инструмента или генерации Вывода.

Протокол Советников (Advisor Protocol) обеспечивает архитектуру "сначала обдумай, потом действуй". Регистрируя Советников, агент оценивает контекст через определенные стратегические призмы — например, глазами Архитектора безопасности или Продакт-менеджера — прежде чем совершить Действие.

Ненаправленное мышление

Неструктурированные рассуждения (вроде цепочки мыслей, Chain-of-Thought) часто бывают хаотичными. Агенты блуждают без карты, смешивая сбор информации, размышления и принятие решений в единый, запутанный ответ.

Недостаток структуры раздувает контекст излишними рассуждениями. Размышления без направления заставляют агента колебаться, что приводит к смене мнений и снижению точности. Непредсказуемость этого процесса ухудшает скорость и надежность. Более того, решения, полученные из неструктурированного текста, сложно согласовать; абзац общих рассуждений не дает количественных показателей для балансировки конкурирующих приоритетов.

Протокол Советников формализует часть процесса рассуждений, чтобы решить эти проблемы. Он структурирует оценку, делая ее предсказуемой и точной. Эта структура также улучшает пользовательский опыт. Со скрытием "простыней текста" система может показывать структурированные, взвешенные выводы, которые четко выделяют расхождения во мнениях, сильные предпочтения и ясные рекомендации. Это создает лучшую среду для принятия решений и значительно улучшает отчетность.

Протокол Советников не заменяет скрытое рассуждение; он структурирует его определенную часть. Он фиксирует процесс оценки как осязаемый артефакт — взвешенное мнение, способствующее непосредственному принятию решений.

Различные перспективы и взвешивание инструментов

Регистрируя нескольких Советников, система заставляет агента оценивать ситуацию с конкурирующих точек зрения (например, "Риск" против "Возможности"). Это расхождение фиксируется через Взвешенный выбор инструментов, при котором Советники выдают явные "вызовы" (calls) или оценки уверенности для конкретных Инструментов.

Агент собирает эти взвешенные голоса от своего совета. Он не просто "выбирает" инструмент; он согласовывает вектор расходящихся мнений для достижения консенсуса. Активация инструмента становится взвешенным решением на основе конкурирующих советов.

Сообщение Советника

Сообщение Советника определяет фокус, через который агент рассматривает проблему.

  • id: Уникальный идентификатор советника (например, "securityArchitect").
  • persona: Для чего нужен этот советник — его область знаний и точка зрения, которую он отстаивает. Поле названо в честь того, что оно содержит, — именно persona, а не role, потому что role уже является полем конверта сообщения. Советник, созданный как обычный контент и содержащий role, был бы неотличим от конверта, а примитив, который их различает, не должен ничего знать о Советниках.
  • answer: JSON-схема, определяющая структуру совета. Она позволяет получать конкретные количественные выводы (например, оценки рисков, сметы) или структурные значения, выходящие за рамки стандартного голосования за инструменты. Поле названо в честь того, что оно содержит — форму ответа этого советника, ведь в библиотеке, где каждое поле представляет собой схему, слово "schema" ничего не значит.
  • on: Определяет стратегию участия.
  • scopes: Массив ключей контекста (например, ["input", "state"]), задающих фокус для анализа советником.
  • isInstanced: Логический флаг (по умолчанию false). Если true, то определение советника включает свойство _instance, что гарантирует индивидуальную консультацию для каждого экземпляра в пакете.

Оба поля: persona и answer — не обязательны, а объявленное поле answer доходит до типа ответа: поле, заявленное как перечисление (enum) из двух элементов, приходит именно как этот enum, а не как тип any.

Один Советник, множество сообщений

Советник — это не одно сообщение; это все сообщения с общим id. Более позднее сообщение обновляет текущее определение поле за полем, поэтому запрос может уточнить Советника, которого окружающая система уже зарегистрировала:

{
  "type": "advisor",
  "id": "riskAnalyst",
  "answer": {
    "type": "object",
    "properties": { "score": { "type": "number" } }
  }
}

Это сообщение не задает persona и в этом нет необходимости. В любых полях приоритет имеет последнее объявленное значение. А если кто-то использует ранее не заявленный id, то просто создается новый Советник — объявление накладывается на пустующее место. Стоит честно сказать о цене этого правила: ошибка в id незаметно создадет нового Советника без описания персоны вместо того, чтобы уточнить нужного.

Исключением является поле on. Оно устанавливается один раз. Оно определяет, через какой механизм предоставляется Советник — в виде свойства в ответе или через инструмент ConsultAdvisor. Так что изменение этого значения между шагами переместило бы Советника через границы кэша, заставив тип ответа зависеть от хода. Если позднее сообщение указывает на иной тип участия — это ошибка. А сообщение вообще без этого поля наследует текущее, что и позволяет впоследствии сделать 'спящего' (silent) Советника активным.

Стратегии выполнения

Свойство on управляет типом участия:

  • start (На старте): Высказывает мнение только в начале разговора, чтобы задать направление. Разговор считается начатым, когда модель сделает свой собственный ход. До этого момента Советник типа start является обязательным, а после предлагается аналогично останавливающему (stopping). Это единственный тип участия, обязанность которого зависит от истории, а не от объявления.
  • finish (Остановка): С ним советуются при принятии решения о том, нужно ли остановить цикл.
  • request (Непрерывно): Высказывает свое мнение в начале, в конце и на каждой итерации. Идеален для мониторинга безопасности или для главных стратегических советников.
  • null / undefined (По запросу): Бездействует, пока к нему явно не обратятся. Система предоставляет мета-инструмент, ConsultAdvisor, позволяющий LLM вызывать этих советников в неоднозначных ситуациях по мере необходимости.

Очередность консультирования

Если Советники активны, LLM в первую очередь генерирует их структурированный вывод в пределах того же окна генерации. Она применяет персоны советников для анализа состояния или голосования за действия. Затем Агент немедленно использует этот вывод для принятия окончательного решения, какой Инструмент следует вызвать.

Количественные данные, такие как "вызовы" (calls), кодируются как Встроенный JSON (Inline JSON) внутри строкового поля. Это делается для предотвращения раздувания схемы с сохранением строгости формата.

Регистрация Советников

[
  {
    "type": "advisor",
    "id": "riskAnalyst",
    "on": "request",
    "scopes": ["†state.deploymentHistory"],
    "persona": "Анализирует риски и голосует за действия по развертыванию.",
    "answer": {
      "type": "object",
      "properties": {
        "thought": { "type": "string", "description": "Оценка рисков развертывания." }
      },
      "required": ["thought"]
    }
  }
]

Ответ LLM

{
  "advisors": [
    {
      "id": "riskAnalyst",
      "thought": "Новая функция прошла модульные тесты, но не имеет интеграционных тестов. Высокий риск регрессии.",
      "calls": "{\"deploy\": 10, \"rollback\": 5, \"delay\": 95}"
    }
  ],
  "calls": [
    {
      "_tool": "delay",
      "_why": "RiskAnalyst настойчиво рекомендует отложить релиз из-за недостаточного тестирования."
    }
  ]
}

Взаимодействие с другими системами

    • 002: Агент/Инструмент

    Инструмент: Советники не выполняют действий; они голосуют за них. То, что могут Советники, в выходной схеме структурно похоже на вызов инструмента. Тем не менее это мета-действие — "процесс обдумывания", который строго предшествует выполнению любого реального Инструмента. Такое разделение гарантирует, что мнения собираются еще до того, как решение принято окончательно.

    • 010: Агент/Цикл

    Цикл: Свойство on интегрирует советников в жизненный цикл агента. Советники со значением on: request работают как непрерывные наблюдатели, запускаясь на каждом шаге цикла. А советники, у которых on: null (по запросу), действуют как предохранительные клапаны — они доступны для обращения, когда агент сталкивается с двусмысленностью или принимает сложные решения во время исполнения.

    • 012: Агент/План

    План: Слово советника имеет решающее значение на этапе планирования. Консультируясь с советниками, имеющими значение on: start или on: request, агент может согласовывать свою начальную стратегию и последующие шаги с мнением специализированных персон, тем самым гарантируя, что План будет надежным и обоснованным с самого начала.

    • 013: Агент/Экземплирование

    Экземплирование: Советники поддерживают пакетное выполнение. При установке isInstanced: true советник начинает распознавать используемые экземпляры. Для каждого контекста (идентифицируемого по _instance) система будет генерировать отдельный совет, гарантируя, что советник будет оценивать каждый элемент в пакете индивидуально.

    • 015: Агент/Области видимости

    Области видимости: Свойство scopes в сообщении Советника предлагает способ для его фокусировки. В отличие от строгой изоляции данных в Делегатах, области видимости (scopes) работают как мягкие направляющие (soft guidance). Они указывают конкретной персоне советника на приоритетный анализ перечисленных ключей контекста (например, ["†state.deploymentHistory"]), обеспечивая "разделение обязанностей" на этапе советов и без блокировки доступа к более широкому контексту.
