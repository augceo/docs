003: Агент/Действие

  • Требуется: 002: Агент/Инструмент
Действие

Явная асинхронная функция, реализующая логику Инструмента. Это механизм для выполнения действий, требующих вызовов внешних API, операций с базами данных или любых задач, которые не могут быть обработаны в скрытом пространстве (latent space) LLM.

Протокол Действий (Activity Protocol) определяет, как Инструменты подкрепляются конкретным, исполняемым кодом. Если Инструмент задаёт интерфейс возможности, то Действие предоставляет её реализацию.

Архитектура двойного реестра

Система агента использует два дополняющих друг друга реестра, чтобы отделить интерфейс возможности от её реализации:

  • Реестр Инструментов: Хранит определения схем для Инструментов.
  • Реестр Действий: Хранит явные асинхронные (async) функции кода (Действия), которые реализуют Инструменты.

Такое разделение — ключ к гибкости системы. Оно позволяет определять и использовать Инструменты исключительно в скрытом режиме (когда LLM напрямую генерирует вывод), а также подменять различные реализации Действия без изменения интерфейса Инструмента (например, для разных сред: разработки и продакшена).

Регистрация Действия

Действие регистрируется под уникальным именем, которое используется для привязки к Инструменту. Обработчик представляет собой функцию async, принимающую три аргумента:

  • call: Конкретный объект Вызова. Он содержит все параметры инструмента, включая любые мета-свойства (с префиксом _), управляющие его выполнением.
  • tool: Определение схемы выполняемого Инструмента. Это позволяет действию изучать свой собственный интерфейс, например, ожидаемую схему _output.
  • context: Массив сообщений, выборочно импортированных из родительской среды. Это не полный контекст родителя, а ограниченный обзор, управляемый протоколом Областей видимости, что делает контекстную информацию явной и требующей согласия на получение.

Возвращаемое значение Activity гибко. Если функция возвращает объект Message (например, Data Message), Цикл Исполнения добавит его напрямую в контекст. Это дает Activity полный контроль над выводом, позволяя создавать именно то сообщение, которое нужно для рабочего процесса. Если возвращается любое другое значение (например, обычный объект или строка), цикл автоматически обернет его в Data Message, используя значение _outputPath из оригинального вызова, чтобы определить, куда записать результат.

Реализация Действия

// Регистрируем реализацию Действия.
// По соглашению, Действие может быть привязано к Инструменту с тем же именем.
// Типы автоматически выводятся из Инструмента.
Activity.register('weatherCheck', async (call, tool, context) => {
  const data = await weatherAPI.get(call.location);
  return { temperature: data.temp, conditions: data.desc };
});

Соответствующая схема Инструмента

Tool.register('weatherCheck', {
  type: 'object',
  description: 'Gets the current weather for a location.',
  properties: {
    _tool: { type: 'string', const: 'weatherCheck' },
    location: { type: 'string' },
    _output: {
      type: 'object',
      properties: {
        temperature: { type: 'number' },
        conditions: { type: 'string' },
      },
      required: ['temperature', 'conditions'],
    },
  },
  required: ['location'],
});

Режимы выполнения: Скрытое против Явного

Система поддерживает два принципиально разных режима выполнения для Вызова Инструмента:

    • 104: Концепция/Скрытое
    Скрытое выполнение (Latent Execution): Используется способность LLM к рассуждению. Агент «обдумывает» проблему и генерирует вывод напрямую в том же самом вызове. Это режим по умолчанию, когда для Инструмента не найдено Действие.
  • Явное выполнение (Explicit Execution): Передает Вызов детерминированному коду. Для вычисления результата вызывается функция Действия. Это необходимо для взаимодействия с внешним миром (например, API, базами данных) или для задач, требующих точной, повторяемой логики.

Скрытый шаг завершается на том же ходу, который его создал

Фраза «в том же самом вызове» значит больше, чем кажется, и именно она делает скрытый (latent) шаг полезным даже после завершения этапа прототипирования.

Вызов, у которого поле _activity пустое, содержит _output, которое модель заполняет в том же ответе, в котором и создает этот вызов. Ничего не отправляется вовне, ничего не ожидается — ответ приходит вместе с запросом. Цикл записывает этот вывод по Пути к Выводу в пределах того же источника (drain), а источник и так уже занимается повторным сканированием. Поэтому соседний вызов, читающий этот путь, становится готовым на том же ходу.

  • 011: Агент/Выражения — вычисляемый параметр чаще всего выступает потребителем скрытого вывода (latent output) на том же ходу.

Скрытый Вызов без _output не может быть исполнен на текущем ходу: рабочий цикл не передаст его на выполнение, и этот вызов отправится в План следующего хода, чтобы модель ответила позже. Это «межпоходовая» форма, которая расходует ход, — поэтому заполняйте поле _output на том же ходу, когда выписываете запрос, если у вас уже имеются нужные данные. Оставляйте поле незаполненным, только если входящие для него данные (input) еще не получены.

Таким образом, суждение без написанного для него кода — какой из отрывков читается в позитивном ключе, какой из документов содержит подтверждение — и всё, что вычисляется на основе этого суждения, может быть решено за один запрос вместо трёх. Скрытый шаг работает не просто как заглушка для еще ненаписанного Действия. Это возможность получить результат, который система не смогла бы вычислить алгоритмически, причем представленный как значение. Этим значением другие шаги могут воспользоваться сразу, избавляя вас от необходимости интерпретировать обычный текст на следующем ходу.

Стратегия разрешения Действия

Система использует стратегию «без настройки конфигурации» (zero-configuration), чтобы определить, какой режим выполнения запустить при вызове Инструмента. Поле _activity в схеме Инструмента сигнализирует о намерении использовать явную реализацию. Данное поле автоматически разрешается во время сборки схемы на основе следующих правил:

  1. Явное поле _activity: Если само определение Инструмента включает непустую строку _activity, то это значение используется для поиска Действия в реестре.
  2. Совпадение имён (Рекомендуется): Если поле _activity в Инструменте отсутствует, система проверяет, зарегистрировано ли Действие с тем же именем, что и Инструмент. Если найдено, поле _activity автоматически устанавливается как имя Инструмента.
  3. Переход к скрытому исполнению: Если подходящего Действия по указанным выше правилам не найдено, поле _activity остается пустой строкой, сигнализируя, что Вызов должен быть выполнен в скрытом режиме.

Такой подход, основанный на соглашениях, упрощает разработку:

  • Для работы без конфигурации достаточно регистрировать своё Действие под тем же именем, что и ваш Инструмент.
  • Инструменты без соответствующего Действия автоматически и безопасно перейдут к скрытому выполнению по умолчанию.
  • Явное поле _activity в схеме Инструмента всегда имеет высший приоритет, что позволяет одному Действию реализовывать интерфейсы сразу нескольких Инструментов.

Взаимодействие с другими системами

Действие не выполняется в изоляции. Для структурированного и безопасного получения параметров и контекста оно полагается на другие протоколы.

    • 004: Агент/Вызов
    • 008: Агент/Вывод
    • 013: Агент/Экземплирование

    Вызов: Аргумент call предоставляет Действию полноценный объект вызова. Это больше, чем просто словарь параметров; это богатая структура, способная включать мета-свойства, такие как _outputPath, указывающее путь сохранения результата, или _instance для нацеливания на конкретный элемент в пакетной обработке. Это позволяет Действию участвовать в сложных рабочих процессах, управляющих состояниями.

    • 015: Агент/Области видимости

    Области видимости: Аргумент context наполняется через протокол Областей видимости. Свойство _scopes в Вызове действует как белый список, указывая, какие именно сообщения из родительской среды (например, Состояние или Ввод) следует передать в Действие. Это дает Действию контролируемый, понятный механизм доступа к нужной информации без погружения во всё множество, порой избыточное, родительского контекста.

  • Возможности управления ветвлением (Branching Paths): Способность Activity возвращать полноценное Message является ключевой для проактивной обработки ошибок и другой сложной логики ветвления. Теперь поле _outputPath вызова call работает как контракт или ориентир. Когда Activity принимает вызов с ветвящимся выражением вроде _outputPath: '†state.success <|> †state.error', внутренняя логика действия может определить исход операции, а затем собрать и вернуть корректное Data Message для записи результата в нужный путь (например, сообщение, содержащее { data: { success: { ... } } }). Это предоставляет детерминированному коду полный контроль над управлением потоком плана.

Почему важно разделение Действий

Без отделения схем Инструментов от реализаций Действий, определение возможности агента было бы намертво привязано к логике её выполнения. Чтобы переключиться от реализации на базе LLM к использованию внешнего API, вам пришлось бы находить и изменять каждого агента, использующего эту Инструмент.

Архитектура двойного реестра решает эту проблему. Она сохраняет интерфейсы Инструментов стабильными, позволяя при этом их реализациям свободно развиваться. Агенты взаимодействуют с единообразной схемой Инструмента, вне зависимости от того, выполняется ли он в скрытом режиме с помощью LLM или явно с использованием Действия. Это значит:

  • Изменения в реализации не ломают работу агентов: Можно перейти со скрытого к явному режиму, даже не трогая код агентов.
  • A/B-тестирование стратегий: Вы можете сравнивать эффективность логических выводов LLM и работу внешнего API для одних и тех же задач.
  • Постепенное развёртывание: Доступно внедрение новых реализаций Действий для определенной группы выделенных агентов, в то время как остальные будут использовать старую версию или резервный скрытый вариант выполнения.

От Определения к Действию

Отделяя то, «что нужно делать» (Инструмент), от того, «как это делать» (Действие), система приобретает высокую степень гибкости. Но всё это — лишь одна часть истории. Когда интерфейсы и их реализации заданы, последним элементов становится оркестровка: то, как организуются, запускаются и упорядочиваются Вызовы.
