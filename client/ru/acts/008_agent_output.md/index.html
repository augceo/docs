008: Агент/Вывод

  • Требуется:
    • 004: Агент/Вызов
    • 007: Агент/Переменные

Путь вывода

Мета-свойство _outputPath у Вызова, которое указывает, где нужно сохранить результат работы инструмента. Это строка, которая сообщает движку исполнения (execution engine), куда поместить результат, делая его доступным для последующих шагов.

В системе агентов есть две формы вывода: промежуточные результаты Вызовов инструментов, записываемые в контекст, и Финальный вывод всего повторяющегося (итеративного) процесса.

Запись в контекст с помощью Пути вывода

Хотя целью может быть любое Сообщение с данными, чаще всего производится запись в Сообщение состояния, чтобы сохранить информацию на протяжении множества шагов процесса.

Хотя любое Сообщение с данными может служить черновиком для рабочего процесса, Путь вывода в мета-свойствах Вызова является основным механизмом записи в него. Когда Вызов инструмента с этим свойством выполняется, система добавляет его результат в конец контекста как новое сообщение.

Это новое сообщение является стандартным Сообщением с данными, но оно включает несколько дополнительных элементов метаданных, скрытых от LLM:

  • _call: Исходный Вызов инструмента, который сгенерировал этот вывод.
  • _date: Временная метка ISO, указывающая, когда был записан вывод.
  • _outputMethod: Метод, указанный в исходном вызове, который определяет, как эти данные должны объединяться с другими данными.

Это обеспечивает полный, проверяемый след того, как изменялся контекст, что бесценно для отладки и отслеживания логики рассуждений агента.

Определение Пути вывода

Путь вывода можно задать двумя способами, что дает разный уровень контроля над поведением инструмента.

Динамический путь (Решает LLM)

В этом режиме у LLM есть свобода решать во время работы, где сохранить результат, что делает инструмент очень гибким.

// Схема инструмента позволяет использовать любую строку для _outputPath
{
  "_outputPath": {
    "type": "string",
    "description": "Путь для сохранения сводки по пользователю.",
    "pattern": "^†"
  }
}

Заранее заданный путь (Жестко закодирован)

Этот подход задает строгое предсказуемое поведение: инструмент всегда будет записывать свой вывод в конкретное, жестко прописанное место.

// Схема инструмента жестко привязывает _outputPath к конкретному значению
{
  "_outputPath": {
    "type": "string",
    "const": "†data.user.summary"
  }
}

Динамическое разрешение переменных

Важно отметить, что эти сообщения вывода добавляются, а не объединяются в момент записи. Такой подход позволяет динамически собирать конечное состояние любой переменной в момент чтения на основе _outputMethod, сохраненного в каждом сообщении.

Когда нужно определить значение Ссылки на переменную, например †data.user.name, движок ищет сообщения контекста в обратном хронологическом порядке (от новых к старым).

  • Если алгоритм находит сообщение для искомого пути с _outputMethod, равным set (или без метода, так как set используется по умолчанию), он сразу останавливается. Значение этого сообщения становится итоговым, а все более старые сообщения по этому пути игнорируются. Это поведение называется "побеждает последняя запись" (last-write-wins).
  • Если алгоритм находит сообщения с методами merge (глубокое объединение), assign (поверхностное объединение), push или concat, он продолжает поиск назад, собирая все такие сообщения, пока не наткнется на сообщение с методом set или на начало контекста. Затем он восстанавливает окончательное значение, применяя собранные операции в хронологическом порядке (от старых к новым).
  • Если алгоритм находит сообщение с _outputMethod, равным erase, он останавливается так же, как и при set, за исключением того, что он не возвращает никаких данных. Путь читается так, будто в него ничего никогда не записывали, и любые новые данные после стирания начинают накапливаться с чистого листа.

Такое динамическое разрешение переменных гарантирует, что состояние всегда остается согласованным и точно отражает историю операций, позволяя совершать сложные и надежные манипуляции с состоянием.

Стирание пути, и почему это единственная отмена (Undo)

Вызов инструмента считается завершенным, когда его Путь вывода содержит значение. Больше ничто не фиксирует, что вызов сработал — нет никакого журнала выполнений, и ни один вызов не имеет отметки о том, что он уже произошел. Состояние — это и есть запись. Шаг находится в ожидании, потому что читаемый им путь пуст, и он перестает ждать, когда что-то заполнит этот путь.

Поэтому запустить шаг повторно означает отнять его результат: сотрите путь (командой erase), и вызов потребуется снова. Именно для этого нужен erase, и именно поэтому повторный запуск выражается в виде записи, а не команды циклу исполнения.

Цена за это озвучена прямо: вызов, который ничего не записывает, не сохраняет состояние (stateless). Вызов без _outputPath — это подход "выстрелил и забыл", описанный ниже. Он не оставляет следа о своем выполнении, поэтому нет разницы между запуском один раз или дважды. В этом и заключается суть термина "без сохранения состояния", и это является правильным поведением, а не недочетом. Побочный эффект, который должен сработать ровно один раз, записывает об этом в состояние, и с этого момента он подчиняется тому же механизму, что и любой другой шаг.

Пример: Добавление и Разрешение переменных

1. Начальное состояние

Контекст начинается с начального сообщения с данными.

[
  {
    "type": "data",
    "data": { "user": { "name": "Alex", "status": "active" } }
  }
]

2. Исполнение Вызова инструмента

Инструмент вызывается для обновления статуса пользователя.

// Выполняется вызов
{
  "_tool": "updateUserStatus",
  "newStatus": "inactive",
  "_outputPath": "†data.user.status"
}

3. Контекст после Выполнения

Движок добавляет новое сообщение с выводом, куда включены метаданные о вызове, создавшем этот вывод.

[
  // Исходное сообщение с данными
  {
    "type": "data",
    "data": { "user": { "name": "Alex", "status": "active" } }
  },
  // Добавленное сообщение вывода от вызова
  {
    "type": "data",
    "data": { "user": { "status": "inactive" } },
    "_call": {
      "_tool": "updateUserStatus",
      "newStatus": "inactive",
      "_outputPath": "†data.user.status"
    },
    "_date": "2025-10-26T12:00:00Z"
  }
]

4. Разрешение переменных

  • Чтобы найти †data.user.status, движок প্রথমে проверяет последнее сообщение. Он находит user.status и возвращает "inactive".
  • Чтобы найти †data.user.name, движок проверяет последнее сообщение, не находит user.name, затем проверяет предыдущее сообщение. Он находит значение там и возвращает "Alex"

Мощь сочетания Ссылок на переменные с Путями вывода кроется в их способности задавать операции с данными, которые еще недоступны. Например, Вызов инструмента можно настроить для работы со значением из сообщения Входа, даже если этот конкретный ввод еще не предоставлен. Это позволяет создавать переиспользуемые, параметризованные рабочие процессы.

Эта концепция также распространяется на объединение Вызовов инструментов в цепочки. Можно создать Вызов инструмента со Ссылкой на переменную, указывающей на Путь вывода предыдущего вызова в той же последовательности. Это формирует многоэтапный поток данных, в котором вывод одного инструмента становится вводом для следующего.

Вызовы без Пути вывода

Не каждому Вызову инструмента необходимо сохранять свой результат. Отказ от свойства _outputPath — осознанный выбор, сигнализирующий о различном поведении для скрытых (latent) и явных вызовов.

Временные рассуждения для скрытых вызовов

Для скрытого вызова пропуск _outputPath позволяет ему работать как временный шаг для рассуждения — "мысль", которая направляет последующие действия в рамках того же такта (turn), но не записывается в постоянное Состояние. Это специальная методика структурирования процесса рассуждения LLM.

Например, агента можно спроектировать так, чтобы он сначала использовал скрытый инструмент think для анализа проблемы и планирования стратегии. Эта "мысль" не сохраняется, но её генерация моментально обогащает внутренний контекст самой LLM. На следующем же этапе внутри того же solution, LLM уже может генерировать конкретные, явные Вызовы инструментов, которые окажутся более эффективными и точными благодаря предшествующему, несохраненному этапу рассуждений.

"Выстрелил и забыл" для явных вызовов

Для явного вызова Активности отсутствие _outputPath означает операцию по принципу "выстрелил и забыл". Цикл исполнения запустит Активность, но не будет дожидаться результата или сохранять его в контексте.

Это полезно для побочных эффектов, когда возвращаемое значение не требуется для продолжения текущего рабочего процесса. Вот частые примеры:

  • Запись события во внешний сервис аналитики.
  • Отправка уведомления пользователю или другой системе.
  • Запуск длительного фонового процесса без необходимости блокировать текущий план.

Его цена уже названа выше: вызов, который ничего не записывает, не сохраняет состояние, поэтому в контексте не остается следов того, был ли он запущен, или нет. Выбирайте подход "выстрелил и забыл", если повторение операции безвредно. Но если это не так, дайте вызову _outputPath — тогда факт его запуска станет обычным значением, и erase послужит инструментом для его намеренной отмены.

Взаимодействие с другими системами

    • 005: Агент/Данные

    Сообщение с данными: _outputPath — это основной механизм для создания и обновления Сообщений с данными внутри рабочих процессов. Он превращает Вызов инструмента без сохранения состояния в операцию с сохранением состояния, записывая результат в контекст и делая его доступным для последующих шагов.

    • 009: Агент/Состояние

    Сообщение состояния: Хотя целью может быть любое Сообщение с данными, в большинстве случаев идет запись в Сообщение состояния. Это делает объект Состояния главным "черновиком" рабочего процесса, позволяя разным инструментам обмениваться информацией и использовать результаты друг друга на протяжении множества тактов Цикла исполнения.

    • 007: Агент/Переменные

    Ссылка на переменную: Путь вывода напрямую связан со Ссылкой на переменную. Путь вывода записывает данные в контекст, а Ссылка на переменную их читает. Вместе они формируют законченную, декларативную схему передачи данных, связывая вывод одного инструмента со вводом другого.

    • 011: Агент/Выражения

    Выражения: Выражения внедряют логику непосредственно в контуры передачи данных. Используя <|> и *> в Пути вывода, Вызов инструмента можно настроить на обработку условных исходов или распределение результатов по нескольким адресатам. Это переводит систему от жестких, запрограммированных потоков к гибкой структуре, которая адаптируется под условия во время ее исполнения.

    • 012: Агент/План

    План: В контексте Плана, Пути вывода выполняют роль "проводов", которые соединяют разные Вызовы инструментов ("узелки") в полноценный граф передачи данных. Это позволяет агенту настраивать и выполнять целую многоэтапную стратегию в виде единого декларативного объекта.

    • 013: Агент/Экземплирование

    Экземплирование: Если Вызов инструмента включает свойство _instance, любой указанный в нем _outputPath автоматически ограничивается контекстом данных этого конкретного экземпляра. Это гарантирует изоляцию данных при параллельной обработке, так что вывод инструмента, работающего с одним экземпляром, не затронет состояние другого.

От Временных результатов к Постоянному состоянию

Механизм Пути вывода предоставляет способ управления потоком данных между отдельными Вызовами инструментов, и его целью может быть любое Сообщение с данными. Тем не менее, для создания сложных, многоэтапных агентов, способных рассуждать и адаптироваться с течением времени, требуется особая память — тип сообщения, специально разработанный для сохранения информации между множеством независимых запросов.
