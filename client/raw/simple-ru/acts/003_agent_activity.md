# 003: Агент/Действие

> [!DEFINITION] [Действие](./000_glossary.md)
> Чёткая функция, которая выполняет реальную работу для :term[Инструмента]{canonical="Tool"}. Это способ делать то, с чем ИИ не справится сам в своей «голове» (например: сделать запрос куда-то в интернет, сохранить данные в базу или запустить настоящую программу).

> Sidenote:
> - Требуется: :term[002: Агент/Инструмент]{href="./002_agent_tool.md"}

**Протокол Действий (Activity)** описывает, как :term[Инструменты]{canonical="Tool"} работают на самом деле с помощью настоящего кода. Если :term[Инструмент]{canonical="Tool"} — это как пункт в меню, который описывает блюдо, то :term[Действие]{canonical="Activity"} — это сам процесс готовки на кухне, то есть его реализация.

## Два списка: Меню и Рецепты

Наша система использует две отдельные коллекции (списка), чтобы отделить то, что мы просим сделать, от того, как именно это выполняется:

- **:term[Список Инструментов]{canonical="Tool"}**: Хранит описания и схемы всех :term[Инструментов]{canonical="Tool"} (наше меню).
- **:term[Список Действий]{canonical="Activity"}**: Хранит конкретный исполняемый код — асинхронные функции (:term[Действия]{canonical="Activity"}), которые делают всю реальную работу (наша книга рецептов).

Такое разделение делает систему невероятно гибкой. Оно позволяет ИИ иногда самому придумывать ответы («в уме»), а иногда — использовать реальный код. При этом, код можно легко менять и тестировать в разных условиях, не меняя само описание :term[Инструмента]{canonical="Tool"}.

## Как зарегистрировать Действие

Мы регистрируем :term[Действие]{canonical="Activity"} под уникальным именем, которое потом связывает его с нужным :term[Инструментом]{canonical="Tool"}. Код (функция) при этом получает три важные вещи для работы:

- **`call` (вызов)**: Конкретный :term[Запрос]{canonical="Call"}. В нём лежат все параметры задачи, а также служебные настройки (имена которых начинаются с `_`), которые направляют процесс.
- **`tool` (инструмент)**: Схема самого :term[Инструмента]{canonical="Tool"}. Это помогает коду понять, чего вообще от него ждут (например, в каком формате нужно вернуть результат `_output`).
- **`context` (окружение)**: Небольшой набор прошлых сообщений. Это не вся история переписки, а только то, что нужно прямо сейчас. Этим управляет протокол :term[Областей видимости]{canonical="Scope"}, так что мы передаем только ту информацию, которая действительно нужна.

Если :term[Действие]{canonical="Activity"} возвращает готовое сообщение (Data Message), система просто добавит его в ход работы как есть. Если функция возвращает просто текст или числа, система сама красиво упакует это в правильное сообщение и направит по пути сохранения (`_outputPath`), который был указан в запросе.

::::columns
:::column{title="Реализация Действия"}

```typescript
// Регистрируем функцию ДЕЙСТВИЯ.
// Обычно мы даем Действию то же имя, что и Инструменту.
// Типы автоматически подхватываются от Инструмента.
Activity.register('weatherCheck', async (call, tool, context) => {
  const data = await weatherAPI.get(call.location);
  return { temperature: data.temp, conditions: data.desc };
});
```

:::
:::column{title="Соответствующая схема Инструмента"}

```typescript
Tool.register('weatherCheck', {
  type: 'object',
  description: 'Получает текущую погоду для выбранной локации.',
  properties: {
    _tool: { type: 'string', const: 'weatherCheck' },
    location: { type: 'string' },
    _output: {
      type: 'object',
      properties: {
        temperature: { type: 'number' },
        conditions: { type: 'string' },
      },
      required: ['temperature', 'conditions'],
    },
  },
  required: ['location'],
});
```

## Два режима работы: В уме (Скрытое) и Наяву (Явное)

Система умеет выполнять вызов :term[Запроса]{canonical="Call"} двумя совершенно разными способами:

- **Скрытое исполнение (В уме)**: Использует силу нейросети. Агент сам «обдумывает» задачу и выдаёт результат сразу же. Это режим по умолчанию, когда для задачи не написано специального реального кода.
  > Sidenote:
  > - :term[104: Концепция / Скрытое]{href="./104_concept_latent.md"}
- **Явное исполнение (Наяву)**: :term[Запрос]{canonical="Call"} передаётся настоящей функции с кодом, которая и выполняет работу. Это нужно для взаимодействия с внешним миром (скачать файл, сделать запрос на сайт) или там, где нужна 100% точность вычислений.

### Скрытые шаги решаются мгновенно

Фраза «сразу же» значит больше, чем кажется. Именно поэтому скрытые шаги так полезны, даже не только на этапе прототипирования проекта.

Если у :term[Запроса]{canonical="Call"} нет привязанного кода (в поле `_activity` пусто), то **система вписывает ответ в тот же самый ход, когда агент вообще об этом попросил**. Не нужно ничего ждать. Ответ сразу кладётся по нужному пути (:term[Путь к результату]{canonical="Output Path"}), и **другие задачи могут прочитать этот ответ прямо на том же ходу**.

Поэтому, если агенту нужно принять какое-то решение — например, «какие из этих текстов позитивные?» — ему не нужен код. Он делает вывод в уме, и этот вывод сразу превращается в значение, с которым могут работать другие инструменты. Это не просто «мысли вслух», которые кто-то должен прочитать; это быстрый и четкий ответ, полученный за один шаг, а не за три.

> Sidenote:
> - :term[011: Агент/Выражения]{href="./011_agent_expressions.md"} — вычисляемый параметр обычно сразу же подхватывает результат скрытого выполнения прямо на том же ходу.
>
> Скрытый :term[Запрос]{canonical="Call"} без указанного результата (`_output`) не выполняется сразу: он просто «уезжает» в :term[План]{canonical="Plan"} на следующий ход. Это тратит целое действие зря. Поэтому всегда заполняйте `_output` прямо в момент создания запроса (когда данные у вас уже есть) и оставляйте его пустым, только если результатов ещё физически не существует.

## Как система понимает, что нужно делать (Стратегия разрешения)

Вам почти ничего не нужно настраивать. Система автоматически понимает, какой режим включить (в уме или наяву). Главную роль тут играет поле `_activity` в схеме :term[Инструмента]{canonical="Tool"}:

1.  **Явное поле `_activity`**: Если в описании :term[Инструмента]{canonical="Tool"} указано имя нужного :term[Действия]{canonical="Activity"}, система найдет эту функцию в реестре и запустит её.
2.  **Одинаковые имена (Рекомендуется)**: Если поля `_activity` нет, система попытается найти код (:term[Действие]{canonical="Activity"}), который назван **точно так же**, как и :term[Инструмент]{canonical="Tool"}. Если находит — автоматически его использует.
3.  **Переход в режим «в уме»**: Если код не найден, поле `_activity` остается пустым, и это сигнал, что задачу придется решать скрыто, силами нейросети.

Благодаря этому разработка идет очень быстро:

- **Просто называйте код так же, как инструмент — и всё заработает само.**
- Если вы пока не написали код, инструменты будут безопасно работать в режиме «в уме».
- Если вам нужно, чтобы разный код выполнял одно и то же действие, вы просто указываете его имя напрямую через поле `_activity`.

## Связь с другими частями системы

:term[Действие]{canonical="Activity"} не работает в вакууме. Оно общается с другими правилами, чтобы получать данные и контекст безопасно:

- **:term[Запрос]{canonical="Call"}:** Параметр `call` дает коду всю нужную информацию о задаче. Там есть не только сами данные, но и мета-свойства, например, `_outputPath` (куда положить результат) или `_instance` (ссылка на конкретный элемент при массовой обработке). Это позволяет коду участвовать в сложных цепочках.

  > Sidenote:
  > - :term[004: Агент/Запрос]{href="./004_agent_call.md"}
  > - :term[008: Агент/Вывод]{href="./008_agent_output.md"}
  > - :term[013: Агент/Экземплирование]{href="./013_agent_instancing.md"}

- **:term[Области видимости]{canonical="Scope"}:** Параметр `context` настраивается через протокол :term[Областей видимости]{canonical="Scope"}. Свойство `_scopes` работает как фильтр — оно решает, какие из сообщений среды (например :term[Состояние]{canonical="State"} или :term[Ввод]{canonical="Input"}) можно показать внутри :term[Действия]{canonical="Activity"}. Благодаря этому код не отвлекается на лишний информационный шум из общей среды агента.

  > Sidenote:
  > - :term[015: Агент/Области видимости]{href="./015_agent_scopes.md"}

- **Развилки на пути:** Код может возвращать не только простое число или строку, но и готовое сообщение. И это важно для обработки ошибок. Когда код видит, что результат нужно записать с условием успеха или провала (например, `_outputPath: '†state.success <|> †state.error'`), он сам понимает, удалась ли операция, и затем создает сообщение так, чтобы сразу отправить данные в нужную (успешную или ошибочную) ветку плана. Это дает коду полный контроль над маршрутом агента.

## Почему важно разделять Меню и Рецепты

Если бы мы навсегда склеили описание того, что ИИ *может* делать (:term[Инструмент]{canonical="Tool"}), с тем, *как* он это делает (:term[Действие]{canonical="Activity"}), это превратило бы систему в хаос. Чтобы поменять логику ИИ на внешний API, пришлось бы переписывать код внутри всех агентов, которые знали этот навык.

Архитектура двух списков решает эту проблему заранее. Для агента «меню» навыков всегда выглядит одинаково, неважно, как оно реализовано на «кухне». Это даёт огромные плюсы:

- **Смена логики ничего не ломает агентам**: Вы можете переключаться со скрытого мышления на реальный внешний API (и обратно) — сам агент этого даже не заметит, переделывать его не придется.
- **Тестирование (А/Б тесты)**: Вы можете легко проверять, чья логика лучше справится с задачей: рассуждения нейросети или профессиональная внешняя программа.
- **Постепенные запуски**: Можно давать обновленный код только части агентов, оставляя других работать на старой версии или в скрытом режиме.

## От замысла к реальным шагам

Разделив то, «что нужно» (:term[Инструмент]{canonical="Tool"}), и то, «как это сделать» (:term[Действие]{canonical="Activity"}), мы сделали систему невероятно гибкой. Но это лишь часть картины. Когда у нас есть интерфейс и реализация, их нужно правильно запускать, контролировать последовательность и управлять потоком запросов.

:term[004: Агент/Запрос]{href="./004_agent_call.md"} расскажет о протоколе выполнения — о том, как всем этим дирижировать, превращая сухие правила в осознанные действия, шаг за шагом.
