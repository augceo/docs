# 002: Агент/Инструмент

> [!DEFINITION] [Инструмент](./000_glossary.md)
> Это описание того, что умеет делать агент. Оно работает как меню доступных действий, которое передается языковой модели (LLM). Нейросеть выбирает нужный инструмент и создает :term[Вызов]{canonical="Call"} со своими параметрами. После этого действие выполняется — либо мысленно, внутри самой модели (скрыто), либо с помощью реального программного кода — :term[Действия]{canonical="Activity"}.

> Sidenote:
> - Базируется на: :term[001: Агент/Запрос]{href="./001_agent_request.md"}
> - Дополняется через: :term[003: Агент/Действие]{href="./003_agent_activity.md"}

:term[Инструмент]{canonical="Tool"} — это как строчка в меню, которая четко описывает, что именно может сделать агент. Это главный кирпичик для любых его действий. Благодаря ему нейросеть понимает, какие варианты поведения ей доступны, и может выбрать самый подходящий.

## Что такое Инструменты?

**Инструменты — это основа** того, как агенты взаимодействуют с миром. Они дают агенту новую суперспособность: **выбирать действия по ситуации**. Агент может оценить обстановку и сам решить, как правильно отреагировать.

Что дают инструменты:

- **Понятные описания**: Агенты видят четкие инструкции о том, какие способности им доступны.
- **Точные данные**: Понятно, что именно нужно положить в инструмент, чтобы он заработал, и в каком виде он вернет результат.
- **Собираемость**: Их можно комбинировать друг с другом, как шестеренки в механизме, создавая сложное поведение агента.
- **Понятность для нейросетей**: Модели легко читают эти схемы и могут осознанно выбирать нужный вариант.

Когда агент выбирает инструмент и заполняет его параметры, он создает :term[Вызов]{canonical="Call"}. По сути, это конкретная просьба выполнить работу с заданными условиями.

> :term[004: Агент/Вызов]{href="./004_agent_call.md"}
>

## Когда использовать систему инструментов

Вам нужны инструменты, если агенты должны:

- **Выбирать действия на лету**, отталкиваясь от текущей задачи.
- **Выбирать между разными возможностями**, чтобы добраться до цели.
- **Использовать разные варианты одной и той же функции** (например, искать через разные поисковики).
- **Совмещать размышления нейросети с жесткими правилами** из обычных программ при принятии решений.

## Схема как интерфейс

Система построена на очень важном принципе: **Инструменты — это только описания**. Они описывают, *как* пользоваться функцией, но не говорят, *как именно* она работает внутри. Такое разделение — секрет гибкости всей системы.

Схема инструмента — это обычный объект JSON. Любое поле, имя которого не начинается с нижнего подчеркивания, считается параметром для работы. Если поле начинается с подчеркивания (например, `_`), система воспринимает его как мета-инструкцию, чтобы понимать, как этот инструмент должен запускаться.

Описание инструмента включает в себя:

> Sidenote:
> Расширения:
>
> - **`_activity`**: Связывает инструмент со строгим кодом для явного командного исполнения. Смотрите :term[003: Агент/Действие]{href="./003_agent_activity.md"}
> - **`_delegate`**: Передает работу инструмента другому независимому исполнителю (:term[Делегату]{canonical="Delegate"}). Смотрите :term[014: Агент/Делегат]{href="./014_agent_delegate.md"}
> - **`_outputPath`**: Сохраняет результат работы в память постоянного хранилища. Смотрите :term[008: Агент/Вывод]{href="./008_agent_output.md"}
> - **`_instance`**: Делает так, чтобы инструмент сработал для конкретного экземпляра при потоке данных. Смотрите :term[013: Агент/Экземплирование]{href="./013_agent_instancing.md"}

- **`title`**: Понятное человеку название (по желанию).
- **`description`**: Объясняет нейросети, что именно делает этот инструмент.
- **`properties`**: Обычные поля (без подчеркивания) говорят, какие данные нужно передать инструменту на вход.
- **`_tool`**: Уникальное имя, чтобы инструмент не перепутался с другими.
- **`_output`**: Описывает, в каком виде инструмент вернет ответ.
- **`_why`**: Поле, которое запрашивает система, чтобы агент мог объяснить причину своего выбора.

Более крупные механизмы используют эти схемы, чтобы управлять процессами, сохранять память и диктовать правила выполнения.

## Задание инструмента

Инструменты прописываются как JSON-схемы. Пример ниже показывает :term[Инструмент]{canonical="Tool"} для анализа настроения текста. Этот конкретный инструмент рассчитан на *скрытое* выполнение — нейросеть будет опираться на свое собственное понимание текста, без вызова дополнительного кода.

::::columns
:::column{title="Задание инструмента"}

```typescript
Tool.register('sentimentAnalysis', {
  type: 'object',
  description: 'Анализирует настроение текста',
  properties: {
    _tool: { type: 'string', const: 'sentimentAnalysis' },
    text: { type: 'string', description: 'Текст для анализа' },
    _output: {
      type: 'object',
      properties: {
        sentiment: { type: 'string' },
        confidence: { type: 'number' },
      },
    },
  },
});
```

:::
:::column{title="Пример ответа от нейросети"}

```json
// Запрос: "Какое настроение у текста 'Это просто лучший!'"
{
  "_tool": "sentimentAnalysis",
  "text": "Это просто лучший!",
  "_output": {
    "sentiment": "positive",
    "confidence": 0.99
  }
}
```

:::
::::

## Переопределение инструментов

Система различает инструменты по их имени `_tool`. Если вдруг в одном запросе (например, в долгой переписке) попалось сразу несколько описаний одного и того же инструмента, **выигрывает самое новое**.

Такой подход "побеждает последний" открывает интересные трюки:

- **База и замена**: Агентам можно прикрепить стандартный набор инструментов, а потом легко менять их под конкретную задачу, просто отправляя новую версию инструкции следом.
- **Адаптация на лету**: Описание инструмента можно сделать точнее прямо во время разговора, если ситуация поменялась.

Если старая и новая версия отличаются, старая просто игнорируется и прячется от нейросети.

## Сборка описаний для нейросети

Агент не просто бесконечно дергает разные ручки; обычно ему нужно выдать финальный, готовый ответ. Чтобы помочь ему, система собирает вместе схемы всех доступных :term[Инструментов]{canonical="Tool"} и схему *финального ответа*. Получается единый чертеж, который отправляется модели в :term[Запросе]{canonical="Request"}.

Такая сборка дает нейросети право выбора. Опираясь на задачу, она может:

- **Сгенерировать только `meta` и `calls` (вызовы):** Если нужны промежуточные шаги, нейросеть вызовет инструменты, обновит номер версии :term[Идеи]{canonical="Idea"} в блоке `meta`, а поле ответа `output` оставит пустым (`null`).
- **Сгенерировать только `meta` и `output`:** Если ответ можно дать сразу без дополнительных действий, нейросеть выдаст его в `output`, обновит `meta` и ничего не станет вызывать.
- **Сгенерировать всё и сразу:** В редких случаях модель может за один шаг и совершить действие, и выдать готовый ответ.

Чтобы нейросеть не путалась и не придумывала лишнего, система умным образом меняет схему инструмента перед его отправкой.

- Если :term[Инструмент]{canonical="Tool"} **скрытый** (у него нет реального кода :term[Действия]{canonical="Activity"}), его схема `_output` отправляется как есть. Ведь нейросеть сама должна генерировать ответ.
- Если :term[Инструмент]{canonical="Tool"} **явный** (привязан к жесткому коду :term[Действия]{canonical="Activity"}), его поле `_output` **удаляется из схемы** перед отправкой. Это строгое правило: нейросеть должна только передать правильные входные данные программисту в код. То, что код вернет, написано в описании (`description`), чтобы модель просто учла это в планах, не пытаясь заполнить это поле сама.

Благодаря этому можно использовать один удобный подход и для быстрых ответов, и для сложных многоуровневых операций. Разработчик просто дает структуры :term[Инструментов]{canonical="Tool"} и финального результата, а система склеивает их в вариант, который понятен нейросети.

Пример ниже показывает, как собирается чертеж из :term[Инструмента]{canonical="Tool"} и финального ответа.

::::columns
:::column{title="Настройка агента"}

```typescript
Agent.Request(
  config, // Настройки для запроса (например, модель сети, температура)
  {
    // Схема для финального ответа
    type: 'object',
    properties: {
      summary: { type: 'string' },
    },
    required: ['summary'],
  },
  [
    // Контекст
    {
      type: 'tool',
      tool: {
        greetUser: {
          type: 'object',
          properties: {
            userName: { type: 'string' },
          },
          required: ['userName'],
        },
      },
    },
    { type: 'text', text: 'какой-то текст тут' },
  ]
);
```

:::
:::column{title="Собранная схема (для нейросети)"}

```json
{
  "type": "object",
  "properties": {
    "meta": {
      "type": "object",
      "description": "Метаданные об идее, включая версию. Нейросеть должна обновить это поле, например, повысив версию.",
      "properties": {
        "path": {
          "type": "string"
        },
        "version": {
          "type": "string"
        }
      }
    },
    "output": {
      "type": ["object", "null"],
      "properties": {
        "summary": { "type": "string" }
      },
      "required": ["summary"],
      "additionalProperties": false
    },
    "calls": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "_tool": { "const": "greetUser" },
          "userName": { "type": "string" }
        },
        "required": ["_tool", "userName"]
      }
    }
  },
  "required": ["meta", "calls", "output"]
}
```

:::
::::

## Расширение инструментов с помощью мета-свойств

Помимо обычных параметров, инструмент можно усилить в момент его запуска. Это позволяет добавлять новые привычки к одному и тому же набору действий.

Когда агент все же решает использовать инструмент, он генерирует :term[Вызов]{canonical="Call"} — конкретный запрос на работу. В этот :term[Вызов]{canonical="Call"} входят не только параметры из меню, но и особые мета-свойства (с нижним подчеркиванием). Эти свойства дают движку дополнительные указания, которые выходят за рамки обычной работы инструмента.

> Sidenote:
> - :term[004: Агент/Вызов]{href="./004_agent_call.md"}

Благодаря этому один простой инструмент можно настраивать очень гибко. :term[Вызов]{canonical="Call"} становится богатой инструкцией, которая отвечает не только на вопрос *что* сделать, но и *как* именно. Последний шаг — понять, как этот :term[Вызов]{canonical="Call"} на самом деле выполняется.

## Скрытое и явное исполнение

Как только :term[Вызов]{canonical="Call"} собран, системе нужно воплотить его в жизнь. Сам по себе :term[Инструмент]{canonical="Tool"} — лишь описание, в нем нет механики. Работа протекает одним из двух вариантов. По умолчанию это **скрытое исполнение**: нейросеть использует собственные связи и знания, чтобы выдать результат. Это работает для задач с текстом или ответами на вопросы. Но если нужно повлиять на внешний мир (например, скачать файл, сохранить базу данных), :term[Инструмент]{canonical="Tool"} придется привязать к конкретному коду, который четко сработает. Выполнение реального кода называется **:term[Действием]{canonical="Activity"}**.

Разделение между интерфейсом :term[Инструмента]{canonical="Tool"} и кодом :term[Действия]{canonical="Activity"} — это главная идея архитектуры. Оно позволяет агенту думать о своих возможностях абстрактно, в то время как код под капотом можно менять в любой момент. В документе :term[003: Агент/Действие]{href="./003_agent_activity.md"} рассказывается, как :term[Действия]{canonical="Activity"} добавляют реальную работу к :term[Инструментам]{canonical="Tool"}.
