# 012: Агент/План

> [!DEFINITION] [План](./000_glossary.md)
> Это словно карта действий агента, которая представляет собой граф :term[Вызовов Инструментов]{canonical="Tool Call"}. Эта карта передается от шага к шагу, чтобы система не забывала, что она делает, и умела менять тактику на ходу.

> Sidenote:
> - Требует изучения:
>   - :term[004: Агент/Вызов]{href="./004_agent_call.md"}
>   - :term[010: Агент/Цикл]{href="./010_agent_loop.md"}
>   - :term[007: Агент/Переменные]{href="./007_agent_variables.md"}
>   - :term[009: Агент/Состояние]{href="./009_agent_state.md"}
>   - :term[013: Агент/Экземплирование]{href="./013_agent_instancing.md"}

Сообщение :term[План]{canonical="Plan"} — это главный способ заставить агента помнить всё задуманное. Агент умеет выполнять простые разовые просьбы, как торговый автомат. Но когда появляется `План`, это сигнал: мы начинаем долгий проект. Это заставляет :term[Цикл Выполнения]{canonical="Execution Loop"} бережно хранить составленный план и результаты (то есть :term[Состояние]{canonical="State"}) от одного шага к другому, будто вкладывать закладку в книгу.

Эта память — фундамент для создания умных агентов. Когда мозг системы получает свой :term[План]{canonical="Plan"} вместе со свежим :term[Состоянием]{canonical="State"}, он мгновенно понимает, где находится, как турист с картой. Он может идти прямо по маршруту, добавлять туда новые :term[Вызовы Инструментов]{canonical="Tool Call"} или вообще порвать карту и придумать новую, если столкнется с закрытой дорогой. Без `Плана` каждый запрос — это чистый лист, и агент ничего не вспомнит о прошлых решениях.

## Как строится План

Связи между этапами не прописываются жесткими линиями. Они похожи на передачу эстафетной палочки — информация течет от шага к шагу через :term[Состояние]{canonical="State"}.

- **Узлы (:term[Вызовы Инструментов]{canonical="Tool Call"}):** Каждый шаг — это конкретное действие, которое нужно сделать.
- **Связи (через :term[Состояние]{canonical="State"}):** Шаги связываются друг с другом, записывая и считывая данные из :term[Состояния]{canonical="State"}. Один :term[Инструмент]{canonical="Tool"} записывает свой ответ в определенное место, используя свойство :term[Путь Вывода]{canonical="Output Path"}. А следующий :term[Инструмент]{canonical="Tool"} может забрать этот ответ в качестве входных данных, используя **:term[Ссылку на Переменную]{canonical="Variable Reference"}** на то же самое место.

  > Sidenote:
  > - [008: Агент/Вывод](./008_agent_output.md)

Так появляется строгая очередь: второй :term[Вызов Инструмента]{canonical="Tool Call"} не сможет ожить, пока первый не сделает работу и не положит информацию в :term[Состояние]{canonical="State"}.

Например, :term[План]{canonical="Plan"} проверить профиль пользователя, а затем сделать по нему краткую выжимку, будет состоять из двух :term[Вызовов Инструментов]{canonical="Tool Call"}:

:::div{.limited-width}

```json
[
  {
    "_tool": "fetchUserProfile",
    "userName": "Alice",
    "_outputPath": "†state.userProfileData"
  },
  {
    "_tool": "summarizeProfile",
    "profile": "†state.userProfileData",
    "_outputPath": "†state.profileSummary"
  }
]
```

> Sidenote:
> ```mermaid
> graph TD
>     state_var{{"state.user.profile"}}
>
>     Call1["fetchUserProfile"]
>     Call2["summarizeProfile"]
>
>     Call1 -- записывает в --> state_var
>     state_var -- читается --> Call2
> ```

:::

Здесь шаг `summarizeProfile` должен дождаться, пока `fetchUserProfile` принесет ответ, образуя двухшаговый маршрут. Это легко представить в виде простой схемы.

## Содержимое Плана: Граф Потока Данных

То, что лежит внутри сообщения :term[План]{canonical="Plan"}, называется графом потока данных. Это схема, которая строит стратегию агента как цепочку взаимосвязанных :term[Вызовов Инструментов]{canonical="Tool Call"}. Представляя работу в виде такой схемы, система может четко понимать, что за чем должно идти, где результат одной функции дает старт другой. Это удобный технический формат, который :term[Цикл Выполнения]{canonical="Execution Loop"} легко считывает и запускает в работу.

> Sidenote:
> :term[План]{canonical="Plan"} не обязан состоять только из прямой, как стрела, последовательности. В нем могут быть узлы с условиями: когда дорога разветвляется в зависимости от того, как прошел другой шаг:
>
> ```mermaid
> graph TD
>     A[Запросить погоду] --> B{На улице солнечно?};
>     B -- state.sunny --> C[Идти в парк];
>     B -- state.notSunny --> D[Посмотреть кино];
>     C -- state.suggestion --> E[Выдать предложение];
>     D -- state.suggestion --> E[Выдать предложение];
> ```

Кстати, такую структуру графа можно использовать не только для запуска рабочих процессов. Вы можете попросить агента набросать граф :term[Вызовов Инструментов]{canonical="Tool Call"} для чего-то совершенно иного — нарисовать карту социальных связей, показать структуру базы данных или визуализировать проект.

Важно отличать такие рисунки от реального :term[Плана]{canonical="Plan"}. Да, внутри всё устроено похоже, но настоящим путеводителем они становятся только тогда, когда мы отправляем их в :term[Запрос]{canonical="Request"} как специальное сообщение `Plan`, подразумевая, что мы хотим, чтобы агент пошел работать. Это защищает систему от путаницы, где мы просто визуализируем идеи, а где раздаем приказы.

Хотя :term[План]{canonical="Plan"} отлично помогает накидывать идеи или "думать вслух", здесь он в первую очередь нужен для старта реальной работы. Поэтому мы используем формат **Ориентированного ациклического графа (DAG)**, где каждая точка — это :term[Вызов Инструмента]{canonical="Tool Call"}.

У этого DAG есть несколько строгих правил, которые делают его идеальным для дела:

- **Граф (Схема):** Это весь набор вашего сообщения :term[План]{canonical="Plan"}: сами :term[Вызовы Инструментов]{canonical="Tool Call"} (узлы) и потоки данных, которые их соединяют (ребра).
- **Ориентированный:** Связи идут только в одну сторону, как вода по течению реки. Шаг, который создает данные, всегда стоит _перед_ шагом, который их пьёт.
- **Ациклический (Работа без зацикливаний):** В маршруте нет круговых ловушек, благодаря чему у него есть ясное начало и логичный конец. Это важнейшая функция безопасности — она не дает LLM построить бесконечную карусель. Перед тем как начать, система проверяет, всё ли в порядке и нет ли циклов.

**Любой шаг запускается в ту секунду, когда по его :term[Пути Вывода]{canonical="Output Path"} появляется значение, и ни секундой раньше.** Шагу не нужны метки "готово" или "подожди-ка" — он просто смотрит, появились ли нужные данные в Состоянии. Именно из этого правила вытекает вся магия системы — ветвления маршрута, ожидание еще не родившихся результатов и разница между ними.

> Sidenote:
> Чтобы заставить план бегать по кругу (как цикл `for`), мы используем прием делегирования и вложенности. Главный, "верхний" :term[План]{canonical="Plan"} занимается подсчетом (например, отмеряет шаги-итерации), а для каждого нового оборота привлекает :term[Делегата]{canonical="Delegate"}, вызывая его как отдельный запрос. Внутри этого под-запроса существует свой маленький, отдельный :term[План]{canonical="Plan"}, и он занимается логикой одной конкретной итерации. Именно так мы безопасно строим кольцевые циклы и никогда не запутываемся.

## Планирование и Выполнение — это одно и то же действие

**Планировать — значит уже действовать.** У агента нет никакого ползунка переключения режима. Когда LLM выдает своё `solution` (решение), она одновременно и размышляет над проблемами, и сразу закрывает все шаги, которые может закрыть сейчас.

- Скрытый инструмент (например, нарезающий текст на абзацы) в одной мысли получает и свой приказ (`call`), и выплёвывает готовый результат (`_output`).
- Явная :term[Активность]{canonical="Activity"} отправляется в путь с помощью :term[Цикла Выполнения]{canonical="Execution Loop"} ровно в тот момент, когда для нее найдены значения по её **:term[Ссылкам на Переменные]{canonical="Variable Reference" href="./007_agent_variables.md"}**.

Второе условие — это и есть всё правило планирования. **Инструмент запускается ровно тогда, когда у него есть на руках всё, что он запрашивал.** Шаг, который еще не готов бежать, — это просто шаг, которому не хватает информации.

Таким образом, агенту вообще не обязательно заканчивать весь план за один заход. Он рисует всю схему разом и выполняет те кусочки, которые может. Если для скрытого шага еще нет входных данных (они просто не подъехали), он оставляет ячейку `_output` пустой, а не фантазирует результаты из воздуха. Это не считается ошибкой — он просто не запускается. Шаг покорно лежит в плане, а на следующем ходу, когда долгожданная информация появляется, агент быстро его доделывает.

Развилка путей (вида `†state.sunny <|> †state.rainy`) работает точно так же и переживет текущий ход. Когда ход проектируется, никаких данных для явного вызова еще в природе нет, так что выбирать не из чего. :term[Активность]{canonical="Activity"} сделает свой ход во время работы. А вот **скрытый** вызов всегда работает наоборот: его `_output` (исход) — это собственные размышления модели, поэтому, придумывая план, она уже делает этот выбор. Альтернативы, которые модель решила не брать, просто считываются со состояния чуть позже. Те ветки, где значений так и не появилось — это просто те रास्ते, по которым мы никогда не пойдем. Инструменты, которые на них стояли, просто отпадают, а не отмечаются как провалы.

### Предлагать, а не Выполнять

Осознанный подход к работе — сначала строим план, затем ждем проверки человеком — тоже не требует никаких "особых кнопок". Это всё то же правило расписания, только использованное хитро: **черновик (предложение плана) — это просто инструмент, который ждет данных оттуда, куда их еще никто не написал.**

Что это за пути? Вы решаете сами на уровне договоренности. **Любая запись в области `†state.approvals` (согласования) — это барьер-блокпост**, и нет других способов его возвести: никаких галочек напротив задач, никаких тайных каналов. Если барьер нужно где-то регистрировать галочкой, кто-то обязательно об этом забудет. Вы не можете "забыть" сам путь к данным.

Дайте каждому запасному плану свой личный барьер и пускай каждый его первый шаг читает именно его. План А будет ждать переменную `†state.approvals.planA`, а План B будет ждать `†state.approvals.planB`. Пока данных нет ни там, ни там, оба плана спят, и сидят в :term[Плане]{canonical="Plan"} просто как предложения командиру — как чистая схема ваших возможных тактик. И это ровно то, чего требует осознанная работа. Черновик маршрута можно:

- **Проверить:** посмотреть, нет ли на маршруте глупых зацикливаний или других оплошностей.
- **Отрепетировать:** прогнать вхолостую и сымитировать действия.
- **Представить на одобрение:** показать живому человеку, чтобы он подправил, поменял или дал этому зеленый свет (:term[HITL]{canonical="HITL (Human-in-the-Loop)"}).

Дать зеленый свет означает просто записать значение в этот блокпост. И всё, никаких секретных механизмов больше нет — шаги выбранного плана немедленно просыпаются (ведь теперь им есть что читать!), а шаги выброшенной в мусорку альтернативы остаются стоять столбом и тихо отпадают со следующего хода. Какому варианту какой шаг принадлежит — определяется исключительно путем к барьеру. Нет никакого специального ярлычка "ожидает ревью" и никакой параллельной системы.

На деле только ПЕРВЫЙ шаг ветки спрашивает барьер; остальные шаги читают то, что напишет он. Вся эта куча следующих за ним шагов висит на блокпосте, и ждет по той же самой причине, хотя барьер упомянут только на самом верху.

**Одобрение — это процесс, происходящий МЕЖДУ заходами, а никогда не внутри одного захода.** Ничто внешнее не может влезть и поменять :term[Состояние]{canonical="State"}, пока цикл вертится. Поэтому предложение никогда в жизни не будет выполнено ровно на том же шагу, который его породил. Модель делает предложение, цикл тормозит. Человек (или другой управляющий) смотрит, решает, записывает одобрение в блокпост, и вот уже следующий цикл начинается с этого значения, которое лежит в :term[Состоянии]{canonical="State"} готовеньким. Ничего не надо ставить на паузу, ничего не надо замораживать в криокамере. От :term[Цикла Выполнения]{canonical="Execution Loop"} не требуется никакой сложной памяти. Красота и дешевизна механизма кроется как раз в том, что все решается просто именем переменной.

**Ждущее предложение — это не поломка, и как ошибка оно не светится.** Запрос ждёт. А вот запрос, стоящий на пути, куда уже никто никогда ничего не напишет — он уже сломан. И тот, и другой всего-навсего столкнулись с тем, что их :term[Ссылки на Переменные]{canonical="Variable Reference"} не материализовались. Система аккуратно выводит ожидание один раз в конце цикла: "Мы ждем у блокпоста". Она не пишет это каждый ход красными буквами, иначе контекст лопнет от спама, а модель испугается и решит, что использовать контрольные барьеры — это преступление.

**Одобрение для отдельных задачек-экземпляров не усложняет систему.** Барьер — это просто обычный путь в :term[Состоянии]{canonical="State"}, он работает так же, как остальные: если повесить добро глобально, он разбудит потоки у всех экземпляров сразу; если записать добро на один конкретный экземпляр, разбудится только он один, а остальные продолжат дремать на блокпосте. Никакого особого синтаксиса не требуется, потому что строгие правила из :term[013: Агент/Экземплирование]{href="./013_agent_instancing.md"} и без этого все прекрасно рулят.

Учитывайте единственную важную вещь: **план-предложение с инструментами, у которых уже есть всё для старта, сорвется с цепи моментально.** Инструмент, который читает переменные, уже лежащие сейчас в :term[Состоянии]{canonical="State"} — это не предложение, это прямой приказ. Поэтому барьер должен быть :term[Ссылкой на Переменную]{canonical="Variable Reference"}. `†state.approvals.planA` — будет ждать. А слово `"approved"`, гордо написанное прямо в значение, ждать никого не собирается. Если хотите, чтобы план предлагался — заставьте его ждать несуществующих данных.

## План как Живая Стратегия

:term[План]{canonical="Plan"} не высечен в камне; это живая стратегия. Его можно менять и перемалывать на каждом кругу вашей работы. Но помните, что `План` — это не любая строчка, прилетевшая от нейросети (LLM). Когда модель в первый раз высыпает стопку :term[Вызовов Инструментов]{canonical="Tool Call"} — она лишь предлагает сценарий действий. Настоящим :term[Планом]{canonical="Plan"} он становится только когда мы пришиваем его как сообщение контекста к _следующему_ запросу в цикле.

Это колесо трансформирует одноразовый позыв в бесконечный, гибкий подход:

- **:term[контекст]{canonical="context"}** нового запроса держит в кармане :term[Состояние]{canonical="State"} и сообщение с :term[Планом]{canonical="Plan"} с нашего прошлого круга.
- Новое **:term[решение]{canonical="Solution"}**, которое рожает LLM, хранит новую комбинацию :term[Вызовов Инструментов]{canonical="Tool Call"}, и вот уже эта комбинация станет **нашим новеньким :term[Планом]{canonical="Plan"}** для следующего шага.

Такой круговорот помогает агентам быть и целеустремленными, и гибкими. Он может спокойно двигаться по изначальному :term[Плану]{canonical="Plan"}, но если что-то свернуло не туда (например, :term[Вызов Инструмента]{canonical="Tool Call"} выдал ошибку), он может на лету нарисовать себе свежий :term[План]{canonical="Plan"}, обходящий проблему. Система становится упругой, как мячик, и выкручивается из любых ситуаций.

Этот пример показывает, как `План` работает словно колея, направляя агента и не давая ему свернуть со стандартного пути, даже когда вокруг много других привлекательных вариантов.

**Сценарий:** Агенту службы поддержки нужно сделать возврат средств. Обычное дело — сначала проверить историю платежей клиента (понять всю картину), а затем вернуть деньги.

**1. Начальный Запрос**

В самом начале поступает просьба клиента. Опираясь на этот `input`, языковая модель пишет себе стандартный `План` в два шага. Это идеальный маршрут, когда всё идет хорошо.

```json
// Agent.Request(config, schema, context)
{
  "schema": {
    "type": "object",
    "properties": {
      "calls": { "type": "array" },
      "output": {
        "type": "object",
        "nullable": true,
        "properties": {
          "confirmationId": { "type": "string" },
          "message": { "type": "string" }
        }
      }
    }
  },
  "context": [
    {
      "type": "input",

      "customerId": "cust_123",
      "amount": 50.0
    }
  ]
}
```

**2. Следующий Запрос в Цикле**

:term[Цикл Выполнения]{canonical="Execution Loop"} запускает команду `checkBillingHistory` и загружает результаты в :term[Состояние]{canonical="State"}. История полна сюрпризов (например, клиент уже делал отмену платежа). Агент без четкого руководства, скорее всего, испугался бы и передал это дело начальнику (вызвал бы инструмент `escalateToSupervisor`).

Но у нас под рукой `План`. Скрестив то, что агент _знает_ (сложное `Состояние`) с тем, что он _должен делать_ (`План`), мозг агента точно понимает, где находится, и продолжает уверенно идти по колее "идеального пути".

::::columns
:::column{title="Контекст"}

```json
[
  {
    "type": "state",
    "billingHistory": {
      "orders": 5,
      "lastChargeback": "2025-09-10"
    }
  },
  {
    "type": "plan",
    "plan": [
      {
        "_tool": "checkBillingHistory",
        "customerId": "†input.customerId"
      },
      {
        "_tool": "issueRefund",
        "customerId": "†input.customerId",
        "amount": "†input.amount"
      }
    ]
  }
]
```

:::
:::column{title="Новое Решение от LLM"}

```json
{
  "calls": [
    {
      "_tool": "issueRefund",
      "customerId": "†input.customerId",
      "amount": "†input.amount"
    }
  ],
  "output": {
    "confirmationId": "refund_xyz789",
    "message": "The refund has been processed successfully."
  }
}
```

:::
::::

`План` следит за порядком, останавливая случайную панику и удерживая действия в задуманном русле.

:::::

:::::details{title="Пример: Корректировка Плана"}

Этот пример демонстрирует, как агент может подкорректировать свой текущий :term[План]{canonical="Plan"} на ходу, если поступят новые обстоятельства, просто выбрав другой инструмент.

::::columns
:::column{title="Контекст"}

Агенту дается изначально правильный `План`, но приходит новый `Input` (Ввод) от пользователя с другим важным ограничением.

```ts
[
  { type: 'tool', tool: Tool.bookFlight },
  { type: 'tool', tool: Tool.bookHotel },
  { type: 'tool', tool: Tool.findPetFriendlyHotel },
  {
    type: 'plan',
    plan: [
      {
        _tool: 'bookFlight',
        destination: '†input.destination',
      },
      {
        _tool: 'bookHotel',
        destination: '†input.destination',
      },
    ],
  },
  {
    type: 'input',
    destination: 'Berlin',
    instruction: "Actually, I'll be traveling with my dog.",
  },
];
```

:::
:::column{title="Решение от LLM (`solution`)"}

LLM видит, что старый план никуда не годится. Модель берет старый план, выбрасывает его и пишет себе новый, заменяя обычный выбор отеля на более подходящий инструмент.

```json
{
  "calls": [
    {
      "_tool": "bookFlight",
      "destination": "†input.destination"
    },
    {
      "_tool": "findPetFriendlyHotel",
      "destination": "†input.destination"
    }
  ],
  "output": null
}
```

:::
::::

Модель не просто меняет настройку или пару цифр; она в корне меняет подходы, подбирая другой :term[Инструмент]{canonical="Tool"} (`findPetFriendlyHotel`), потому что условия игры изменились. Эти новые инструменты — новый `План` агента для следующего шага в :term[Цикле Выполнения]{canonical="Execution Loop"}.

:::::

:::::details{title="Пример: Работа с Ограничениями и Ошибками"}

Этот пример показывает, как агент реагирует, если идеальный сценарий :term[Плана]{canonical="Plan"} терпит крах. Вы увидите два этапа: изначальный радужный план и срочный "пересмотр", который происходит, если ломается инструмент.

**1. Изначальный План**

Агенту дают в руки инструменты и сумму задачи. Он рисует красивый двухэтапный :term[План]{canonical="Plan"}, который даже не предполагает, что что-то может сломаться.

::::columns
:::column{title="Первоначальный Контекст"}

```ts
Agent.Request(config, {
  schema: {
    type: 'object',
    properties: {
      calls: { type: 'array' },
      output: {
        type: 'object',
        nullable: true,
        properties: {
          status: {
            type: 'string',
            enum: ['Success', 'Failed'],
          },
        },
      },
    },
  },
  context: [
    { type: 'tool', tool: 'Tool.processPayment' },
    { type: 'tool', tool: 'Tool.confirmOrder' },
    { type: 'tool', tool: 'Tool.reportFailure' },
    { type: 'input', amount: 50.0 },
  ],
});
```

:::
:::column{title="Первоначальное Решение"}

```json
{
  "calls": [
    {
      "_tool": "processPayment",
      "amount": "†input.amount",
      "_outputPath": "†state.receipt <|> †state.error"
    },
    {
      "_tool": "confirmOrder",
      "receipt": "†state.receipt"
    }
  ],
  "output": null
}
```

:::
::::

**2. Ошибка и Перестроение Плана**

:term[Цикл Выполнения]{canonical="Execution Loop"} пытается провести оплату `processPayment`, но банк дает отказ. Движок записывает значение в переменную `†state.error`. При новом заходе модель видит ошибку в контексте, смотрит на уже неактуальный красивый план, и собирает спасательную стратегию.

::::columns
:::column{title="Контекст для Следующего Запроса"}

```json
[
  {
    "type": "state",
    "error": { "code": "card_declined", "message": "Your card was declined." }
  },
  // Старый и уже неактуальный план всё еще находится в контексте
  {
    "type": "plan",
    "plan": [
      { "_tool": "processPayment", "_outputPath": "†state.receipt <|> †state.error" },
      { "_tool": "confirmOrder", "receipt": "†state.receipt" }
    ]
  }
]
```

:::
:::column{title="Новое Решение (Обновленный План)"}

```json
{
  "calls": [
    {
      "_tool": "reportFailure",
      "error": "†state.error"
    }
  ],
  "output": { "status": "Failed" }
}
```

:::
::::

Агент заметил, что в :term[Состоянии]{canonical="State"} теперь лежит `error` (ошибка). Он забросил старый "идеальный" :term[План]{canonical="Plan"} и состряпал себе новый, состоящий всего из одного шага `reportFailure` (Сообщить о провале). Так система реактивно маневрирует при внезапных неудачах.

:::::

:::::details{title="Пример: Планирование по Схеме"}

Этот пример показывает, как передача жесткой `schema` (схемы) для :term[Состояния]{canonical="State"} работает как трафарет, позволяющий модели (LLM) построить идеально правильный, крепкий :term[План]{canonical="Plan"}.

::::columns
:::column{title="Контекст со Схемой Состояния"}

Мы даем входные данные `Input` и кидаем сообщение `State`, в котором есть лишь пустышка — `schema` (схема). Она и диктует логику того, как переменные в плане будут перетекать друг в друга.

```json
[
  { "type": "tool", "tool": "Tool.detectLanguage" },
  { "type": "tool", "tool": "Tool.isEnglish" },
  { "type": "tool", "tool": "Tool.translateText" },
  {
    "type": "input",
    "text": "Bonjour le monde"
  },
  {
    "type": "state",
    "schema": {
      "type": "object",
      "properties": {
        "language": { "type": "string" },
        "isEnglish": { "type": "boolean" },
        "translatedText": { "type": "string" }
      }
    }
  }
]
```

:::
:::column{title="Решение от LLM (`solution`)"}

Модель использует эту схему Состояния как готовый чертеж. Ей не нужно ничего изобретать, она просто бережливо скрепляет :term[Путь Вывода]{canonical="Output Path"} одной команды с проводами входа другой.

```json
{
  "calls": [
    {
      "_tool": "detectLanguage",
      "text": "†input.text",
      // LLM в курсе, что путь можно подглядеть из схемы
      "_outputPath": "†state.language"
    },
    {
      "_tool": "isEnglish",
      // Модель корректно перенаправляет результаты прошлого шага.
      "language": "†state.language",
      "_outputPath": "†state.isEnglish"
    },
    {
      "_tool": "translateText",
      "text": "†input.text",
      "isEnglish": "†state.isEnglish",
      "_outputPath": "†state.translatedText"
    }
  ],
  "output": null
}
```

:::
::::

Давая `schema` (схему), мы предоставляем агенту четкий чертеж. Модели не нужно ломать голову над именами переменных или их порядком в танце; она просто расставляет детали по готовым окошкам. Результат — надежный, железобетонный `План`.

:::::

Эта повторяющаяся карусель из планов и их выполнения — бьющееся сердце любого :term[Процесса]{href="./203_idea_process.md"}. Окружение как бы делает моментальный снимок происходящего: набор открытых :term[Инструментов]{canonical="Tool"}, живое и дышащее :term[Состояние]{canonical="State"} с данными, плюс сам :term[План]{canonical="Plan"}.

## От Единого Плана к Повторным Рабочим Процессам

Сам по себе :term[План]{canonical="Plan"} просто обозначает цепочку действий для одной-единственной задачи. Но если мы хотим превратить это в настоящие многоразовые механизмы, которые можно "вызывать на помощь" из других :term[Планов]{canonical="Plan"}, нам нужно красиво упаковать их в компоненты.

В документе :term[013: Агент/Экземплирование]{href="./013_agent_instancing.md"} подробно описываются правила такой параллельной сложной работы.
