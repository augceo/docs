# 003: Агент/Действие

> [!DEFINITION] [Действие](./000_glossary.md)
> Явная асинхронная функция, реализующая логику :term[Инструмента]{canonical="Tool"}. Это механизм для выполнения действий, требующих вызовов внешних API, операций с базами данных или любых задач, которые не могут быть обработаны в скрытом пространстве (latent space) LLM.

> Sidenote:
> - Требуется: :term[002: Агент/Инструмент]{href="./002_agent_tool.md"}

**Протокол Действий (Activity Protocol)** определяет, как :term[Инструменты]{canonical="Tool"} подкрепляются конкретным, исполняемым кодом. Если :term[Инструмент]{canonical="Tool"} задаёт интерфейс возможности, то :term[Действие]{canonical="Activity"} предоставляет её реализацию.

## Архитектура двойного реестра

Система агента использует два дополняющих друг друга реестра, чтобы отделить интерфейс возможности от её реализации:

- **:term[Реестр Инструментов]{canonical="Tool"}**: Хранит определения схем для :term[Инструментов]{canonical="Tool"}.
- **:term[Реестр Действий]{canonical="Activity"}**: Хранит явные асинхронные (`async`) функции кода (:term[Действия]{canonical="Activity"}), которые реализуют :term[Инструменты]{canonical="Tool"}.

Такое разделение — ключ к гибкости системы. Оно позволяет определять и использовать :term[Инструменты]{canonical="Tool"} исключительно в скрытом режиме (когда LLM напрямую генерирует вывод), а также подменять различные реализации :term[Действия]{canonical="Activity"} без изменения интерфейса :term[Инструмента]{canonical="Tool"} (например, для разных сред: разработки и продакшена).

## Регистрация Действия

:term[Действие]{canonical="Activity"} регистрируется под уникальным именем, которое используется для привязки к :term[Инструменту]{canonical="Tool"}. Обработчик представляет собой функцию `async`, принимающую три аргумента:

- **`call`**: Конкретный объект :term[Вызова]{canonical="Call"}. Он содержит все параметры инструмента, включая любые мета-свойства (с префиксом `_`), управляющие его выполнением.
- **`tool`**: Определение схемы выполняемого :term[Инструмента]{canonical="Tool"}. Это позволяет действию изучать свой собственный интерфейс, например, ожидаемую схему `_output`.
- **`context`**: Массив сообщений, выборочно импортированных из родительской среды. Это не полный контекст родителя, а ограниченный обзор, управляемый протоколом :term[Областей видимости]{canonical="Scope"}, что делает контекстную информацию явной и требующей согласия на получение.

Возвращаемое значение `Activity` гибко. Если функция возвращает объект `Message` (например, `Data Message`), :term[Цикл Исполнения]{canonical="Execution Loop"} добавит его напрямую в контекст. Это дает `Activity` полный контроль над выводом, позволяя создавать именно то сообщение, которое нужно для рабочего процесса. Если возвращается любое другое значение (например, обычный объект или строка), цикл автоматически обернет его в `Data Message`, используя значение `_outputPath` из оригинального вызова, чтобы определить, куда записать результат.

::::columns
:::column{title="Реализация Действия"}

```typescript
// Регистрируем реализацию Действия.
// По соглашению, Действие может быть привязано к Инструменту с тем же именем.
// Типы автоматически выводятся из Инструмента.
Activity.register('weatherCheck', async (call, tool, context) => {
  const data = await weatherAPI.get(call.location);
  return { temperature: data.temp, conditions: data.desc };
});
```

:::
:::column{title="Соответствующая схема Инструмента"}

```typescript
Tool.register('weatherCheck', {
  type: 'object',
  description: 'Gets the current weather for a location.',
  properties: {
    _tool: { type: 'string', const: 'weatherCheck' },
    location: { type: 'string' },
    _output: {
      type: 'object',
      properties: {
        temperature: { type: 'number' },
        conditions: { type: 'string' },
      },
      required: ['temperature', 'conditions'],
    },
  },
  required: ['location'],
});
```

## Режимы выполнения: Скрытое против Явного

Система поддерживает два принципиально разных режима выполнения для :term[Вызова]{canonical="Call"} :term[Инструмента]{canonical="Tool"}:

- **Скрытое выполнение (Latent Execution)**: Используется способность LLM к рассуждению. Агент «обдумывает» проблему и генерирует вывод напрямую в том же самом вызове. Это режим по умолчанию, когда для :term[Инструмента]{canonical="Tool"} не найдено :term[Действие]{canonical="Activity"}.
  > Sidenote:
  > - :term[104: Концепция/Скрытое]{href="./104_concept_latent.md"}
- **Явное выполнение (Explicit Execution)**: Передает :term[Вызов]{canonical="Call"} детерминированному коду. Для вычисления результата вызывается функция :term[Действия]{canonical="Activity"}. Это необходимо для взаимодействия с внешним миром (например, API, базами данных) или для задач, требующих точной, повторяемой логики.

### Скрытый шаг завершается на том же ходу, который его создал

Фраза «в том же самом вызове» значит больше, чем кажется, и именно она делает скрытый (latent) шаг полезным даже после завершения этапа прототипирования.

:term[Вызов]{canonical="Call"}, у которого поле `_activity` пустое, содержит `_output`, **которое модель заполняет в том же ответе, в котором и создает этот вызов**. Ничего не отправляется вовне, ничего не ожидается — ответ приходит вместе с запросом. Цикл записывает этот вывод по :term[Пути к Выводу]{canonical="Output Path"} в пределах того же источника (drain), а источник и так уже занимается повторным сканированием. Поэтому **соседний вызов, читающий этот путь, становится готовым на том же ходу**.

Таким образом, суждение без написанного для него кода — какой из отрывков читается в позитивном ключе, какой из документов содержит подтверждение — и всё, что вычисляется на основе этого суждения, может быть решено за один запрос вместо трёх. Скрытый шаг работает не просто как заглушка для еще ненаписанного :term[Действия]{canonical="Activity"}. Это возможность получить результат, который система не смогла бы вычислить алгоритмически, причем представленный как **значение**. Этим значением другие шаги могут воспользоваться сразу, избавляя вас от необходимости интерпретировать обычный текст на следующем ходу.

> Sidenote:
> - :term[011: Агент/Выражения]{href="./011_agent_expressions.md"} — вычисляемый параметр чаще всего выступает потребителем скрытого вывода (latent output) на том же ходу.
>
> Скрытый :term[Вызов]{canonical="Call"} без `_output` не может быть исполнен на текущем ходу: рабочий цикл не передаст его на выполнение, и этот вызов отправится в :term[План]{canonical="Plan"} следующего хода, чтобы модель ответила позже. Это «межпоходовая» форма, которая расходует ход, — поэтому заполняйте поле `_output` на том же ходу, когда выписываете запрос, если у вас уже имеются нужные данные. Оставляйте поле незаполненным, только если входящие для него данные (input) еще не получены.

## Стратегия разрешения Действия

Система использует стратегию «без настройки конфигурации» (zero-configuration), чтобы определить, какой режим выполнения запустить при вызове :term[Инструмента]{canonical="Tool"}. Поле `_activity` в схеме :term[Инструмента]{canonical="Tool"} сигнализирует о намерении использовать явную реализацию. Данное поле автоматически разрешается во время сборки схемы на основе следующих правил:

1.  **Явное поле `_activity`**: Если само определение :term[Инструмента]{canonical="Tool"} включает непустую строку `_activity`, то это значение используется для поиска :term[Действия]{canonical="Activity"} в реестре.
2.  **Совпадение имён (Рекомендуется)**: Если поле `_activity` в :term[Инструменте]{canonical="Tool"} отсутствует, система проверяет, зарегистрировано ли :term[Действие]{canonical="Activity"} с **тем же именем**, что и :term[Инструмент]{canonical="Tool"}. Если найдено, поле `_activity` автоматически устанавливается как имя :term[Инструмента]{canonical="Tool"}.
3.  **Переход к скрытому исполнению**: Если подходящего :term[Действия]{canonical="Activity"} по указанным выше правилам не найдено, поле `_activity` остается пустой строкой, сигнализируя, что :term[Вызов]{canonical="Call"} должен быть выполнен в скрытом режиме.

Такой подход, основанный на соглашениях, упрощает разработку:

- **Для работы без конфигурации достаточно регистрировать своё :term[Действие]{canonical="Activity"} под тем же именем, что и ваш :term[Инструмент]{canonical="Tool"}.**
- :term[Инструменты]{canonical="Tool"} без соответствующего :term[Действия]{canonical="Activity"} автоматически и безопасно перейдут к скрытому выполнению по умолчанию.
- Явное поле `_activity` в схеме :term[Инструмента]{canonical="Tool"} всегда имеет высший приоритет, что позволяет одному :term[Действию]{canonical="Activity"} реализовывать интерфейсы сразу нескольких :term[Инструментов]{canonical="Tool"}.

## Взаимодействие с другими системами

:term[Действие]{canonical="Activity"} не выполняется в изоляции. Для структурированного и безопасного получения параметров и контекста оно полагается на другие протоколы.

- **:term[Вызов]{canonical="Call"}:** Аргумент `call` предоставляет :term[Действию]{canonical="Activity"} полноценный объект вызова. Это больше, чем просто словарь параметров; это богатая структура, способная включать мета-свойства, такие как `_outputPath`, указывающее путь сохранения результата, или `_instance` для нацеливания на конкретный элемент в пакетной обработке. Это позволяет :term[Действию]{canonical="Activity"} участвовать в сложных рабочих процессах, управляющих состояниями.

  > Sidenote:
  > - :term[004: Агент/Вызов]{href="./004_agent_call.md"}
  > - :term[008: Агент/Вывод]{href="./008_agent_output.md"}
  > - :term[013: Агент/Экземплирование]{href="./013_agent_instancing.md"}

- **:term[Области видимости]{canonical="Scope"}:** Аргумент `context` наполняется через протокол :term[Областей видимости]{canonical="Scope"}. Свойство `_scopes` в :term[Вызове]{canonical="Call"} действует как белый список, указывая, какие именно сообщения из родительской среды (например, :term[Состояние]{canonical="State"} или :term[Ввод]{canonical="Input"}) следует передать в :term[Действие]{canonical="Activity"}. Это дает :term[Действию]{canonical="Activity"} контролируемый, понятный механизм доступа к нужной информации без погружения во всё множество, порой избыточное, родительского контекста.

  > Sidenote:
  > - :term[015: Агент/Области видимости]{href="./015_agent_scopes.md"}

- **Возможности управления ветвлением (Branching Paths):** Способность `Activity` возвращать полноценное `Message` является ключевой для проактивной обработки ошибок и другой сложной логики ветвления. Теперь поле `_outputPath` вызова `call` работает как контракт или ориентир. Когда `Activity` принимает вызов с ветвящимся выражением вроде `_outputPath: '†state.success <|> †state.error'`, внутренняя логика действия может определить исход операции, а затем собрать и вернуть корректное `Data Message` для записи результата в нужный путь (например, сообщение, содержащее `{ data: { success: { ... } } }`). Это предоставляет детерминированному коду полный контроль над управлением потоком плана.

## Почему важно разделение Действий

Без отделения схем :term[Инструментов]{canonical="Tool"} от реализаций :term[Действий]{canonical="Activity"}, определение возможности агента было бы намертво привязано к логике её выполнения. Чтобы переключиться от реализации на базе LLM к использованию внешнего API, вам пришлось бы находить и изменять каждого агента, использующего эту :term[Инструмент]{canonical="Tool"}.

Архитектура двойного реестра решает эту проблему. Она сохраняет интерфейсы :term[Инструментов]{canonical="Tool"} стабильными, позволяя при этом их реализациям свободно развиваться. Агенты взаимодействуют с единообразной схемой :term[Инструмента]{canonical="Tool"}, вне зависимости от того, выполняется ли он в скрытом режиме с помощью LLM или явно с использованием :term[Действия]{canonical="Activity"}. Это значит:

- **Изменения в реализации не ломают работу агентов**: Можно перейти со скрытого к явному режиму, даже не трогая код агентов.
- **A/B-тестирование стратегий**: Вы можете сравнивать эффективность логических выводов LLM и работу внешнего API для одних и тех же задач.
- **Постепенное развёртывание**: Доступно внедрение новых реализаций :term[Действий]{canonical="Activity"} для определенной группы выделенных агентов, в то время как остальные будут использовать старую версию или резервный скрытый вариант выполнения.

## От Определения к Действию

Отделяя то, «что нужно делать» (:term[Инструмент]{canonical="Tool"}), от того, «как это делать» (:term[Действие]{canonical="Activity"}), система приобретает высокую степень гибкости. Но всё это — лишь одна часть истории. Когда интерфейсы и их реализации заданы, последним элементов становится оркестровка: то, как организуются, запускаются и упорядочиваются :term[Вызовы]{canonical="Call"}.

Документ :term[004: Агент/Вызов]{href="./004_agent_call.md"} изучает протокол, который управляет этим выполнением, превращая абстрактные определения в конкретные действия, учитывающие состояния.
