# 012: Агент/План

> [!DEFINITION] [План](./000_glossary.md)
> Контекстное сообщение, содержащее граф потока данных :term[Вызовов Инструментов]{canonical="Tool Call"}, который представляет собой стратегию агента. Оно передается между шагами для обеспечения итеративного выполнения и адаптации.

> Sidenote:
> - Требования:
>   - :term[004: Агент/Вызов]{href="./004_agent_call.md"}
>   - :term[010: Агент/Цикл]{href="./010_agent_loop.md"}
>   - :term[007: Агент/Переменные]{href="./007_agent_variables.md"}
>   - :term[009: Агент/Состояние]{href="./009_agent_state.md"}
>   - :term[013: Агент/Экземплирование]{href="./013_agent_instancing.md"}

Сообщение :term[План]{canonical="Plan"} — это основной механизм для реализации итеративного выполнения с сохранением состояния. Хотя система агентов может обрабатывать простые, одноразовые запросы, добавление сообщения `Plan` в контекст сигнализирует о переходе к постоянному рабочему процессу. Его наличие указывает :term[Циклу Выполнения]{canonical="Execution Loop"} на необходимость сохранять сгенерированный план и полученное :term[Состояние]{canonical="State"} в течение нескольких ходов.

Такое сохранение — основа создания адаптивных агентов. Когда LLM получает текущий :term[План]{canonical="Plan"} вместе с актуальным объектом :term[Состояния]{canonical="State"}, она обретает полное понимание ситуации, в которой находится в рамках рабочего процесса. Это позволяет ей разумно следовать существующему плану, генерировать новые :term[Вызовы Инструментов]{canonical="Tool Call"} для его расширения или вообще отбросить его и составить новый план в ответ на непредвиденные результаты. Без сообщения `Plan` запрос рассматривается как операция без сохранения состояния, и никакие стратегии или состояния не переносятся на следующие шаги.

## Как формируется План

Связи в графе создаются не с помощью явных указателей, а через соглашение о потоке данных с использованием объекта :term[Состояния]{canonical="State"}.

- **Узлы (:term[Вызовы Инструментов]{canonical="Tool Call"}):** Каждый шаг рабочего процесса — это :term[Вызов Инструмента]{canonical="Tool Call"}, представляющий действие, которое нужно выполнить.
- **Ребра (Объект :term[Состояния]{canonical="State"}):** Связи между шагами создаются путем записи и чтения из объекта :term[Состояния]{canonical="State"}. Один :term[Инструмент]{canonical="Tool"} записывает свой результат по определенному пути в :term[Состоянии]{canonical="State"} с помощью метасвойства :term[Путь Вывода]{canonical="Output Path"}. Следующий :term[Инструмент]{canonical="Tool"} может использовать этот результат в качестве входных данных, ссылаясь на этот же путь через **:term[Ссылку на Переменную]{canonical="Variable Reference"}**.

  > Sidenote:
  > - [008: Агент/Вывод](./008_agent_output.md)

Это устанавливает четкую зависимость: второй :term[Вызов Инструмента]{canonical="Tool Call"} не может выполниться, пока первый не завершится и не заполнит :term[Состояние]{canonical="State"}.

Например, :term[План]{canonical="Plan"} по получению профиля пользователя и последующему созданию его резюме состоял бы из двух :term[Вызовов Инструментов]{canonical="Tool Call"}:

:::div{.limited-width}

```json
[
  {
    "_tool": "fetchUserProfile",
    "userName": "Alice",
    "_outputPath": "†state.userProfileData"
  },
  {
    "_tool": "summarizeProfile",
    "profile": "†state.userProfileData",
    "_outputPath": "†state.profileSummary"
  }
]
```

> Sidenote:
> ```mermaid
> graph TD
>     state_var{{"state.user.profile"}}
>
>     Call1["fetchUserProfile"]
>     Call2["summarizeProfile"]
>
>     Call1 -- записывает в --> state_var
>     state_var -- считывается --> Call2
> ```

:::

Здесь вызов `summarizeProfile` зависит от результата `fetchUserProfile`, создавая план из двух шагов. Эту взаимосвязь можно представить себе как простой граф.

## Содержимое Плана: Граф потока данных

Содержимое сообщения :term[План]{canonical="Plan"} — это граф потока данных. Эта структура используется для представления стратегии агента как последовательности связанных :term[Вызовов Инструментов]{canonical="Tool Call"}. Представляя рабочий процесс как граф, система может четко определять зависимости между шагами, где результат одного :term[Вызова Инструмента]{canonical="Tool Call"} становится входным параметром для другого. Такой формат предоставляет четкую, машиночитаемую структуру, которую :term[Цикл Выполнения]{canonical="Execution Loop"} агента может интерпретировать и исполнять.

> Sidenote:
> :term[План]{canonical="Plan"} не ограничивается линейными последовательностями. Он может представлять сложные рабочие процессы с условной логикой, где путь выполнения зависит от результата предыдущего шага:
>
> ```mermaid
> graph TD
>     A[Узнать Погоду] --> B{Солнечно?};
>     B -- state.sunny --> C[Найти Парк];
>     B -- state.notSunny --> D[Найти Фильм];
>     C -- state.suggestion --> E[Предложить Вариант];
>     D -- state.suggestion --> E[Предложить Вариант];
> ```

Сама структура графа не ограничивается определением только исполняемых рабочих процессов. Агента можно попросить сгенерировать граф :term[Вызовов Инструментов]{canonical="Tool Call"}, который представляет собой совершенно иное — визуализацию социальной сети, пайплайн GitHub Actions или схему базы данных.

Крайне важно отличать такие результаты от :term[Плана]{canonical="Plan"}. Хотя в них используется та же структура графа, архитектурно они не являются «планами», если только они не передаются в последующий :term[Запрос]{canonical="Request"} как контекстное сообщение :term[План]{canonical="Plan"} с намерением их выполнить. Такое различие позволяет избежать путаницы между генерацией описания (схемы) существующей системы и созданием исполняемой стратегии.

Несмотря на то, что содержимое :term[Плана]{canonical="Plan"} может быть отличным способом для мозгового штурма, дискуссий и «мыслей вслух», в нашей системе его основное применение — определение исполняемых рабочих процессов. Для этого мы применяем особый тип графа под названием **Направленный ациклический граф (DAG)**, где каждым узлом является :term[Вызов Инструмента]{canonical="Tool Call"}.

У DAG есть несколько ключевых свойств, которые делают его идеальным для выполнения:

- **Граф:** «Граф» представляет собой всё содержимое сообщения :term[Плана]{canonical="Plan"} — набор всех :term[Вызовов Инструментов]{canonical="Tool Call"} (узлов) и связывающих их зависимостей по данным (ребер).
- **Направленный:** Связи являются однонаправленными и определяются потоком данных. Шаг, создающий данные, должен идти _перед_ шагом, который их использует.
- **Ациклический:** У рабочего процесса не может быть круговых зависимостей, что гарантирует точное начало и конец. Это важнейшая функция безопасности, которая не дает LLM создавать бесконечный цикл. Система проверяет, является ли :term[План]{canonical="Plan"} ациклическим, перед его выполнением.

**Шаг вычисляется тогда, когда его :term[Путь Вывода]{canonical="Output Path"} имеет значение, и никак не раньше.** Ничто искусственно не помечает шаг как выполненный или отложенный; состояние читается на основе того, что в нем уже записано. Это единственное правило, из которого вытекают остальные принципы поведения, описанные в этой главе — ветвление плана, ожидание шагом еще не существующего результата и разница между ними.

> Sidenote:
> Для реализации итеративной логики (например, цикла "for"), используется шаблон вложенного, делегированного выполнения. Внешний :term[План]{canonical="Plan"} управляет состоянием цикла (например, счетчиком итераций), и для каждой итерации он вызывает подзапрос через :term[Делегата]{canonical="Delegate"}. Этот подзапрос содержит собственный независимый ациклический :term[План]{canonical="Plan"}, который выполняет логику для отдельной итерации. Это гарантирует, что циклы создаются явно и безопасно.

## Планирование и Выполнение — это один Акт

**Планирование — это выполнение.** Здесь нет режимов, флагов или отдельной стратегии оценки. Когда LLM генерирует `solution` (решение), она выполняет единый, непрерывный акт рассуждения и выполнения для каждого шага, который может разрешить.

- Скрытый инструмент (например, создание summary текста) получает свой `call` (вызов) и свой `_output` в одной и той же мысли.
- Явное :term[Действие]{canonical="Activity"} получает свой `call`, отправленный :term[Циклом Выполнения]{canonical="Execution Loop"} в тот момент, когда разрешаются :term[Ссылки на Переменные]{canonical="Variable Reference" href="./007_agent_variables.md"} этого вызова.

Этот второй пункт и является сутью правила планирования, поэтому никаких дополнительных режимов не требуется. **Вызов запускается ровно тогда, когда данные для чтения существуют.** Шаг, который еще не должен запускаться — это шаг, читающий то, чего еще нет.

По этой причине ход (итерация) не обязан завершать план за одну мысль. Модель пишет весь граф сразу и вычисляет доступные ей шаги: скрытый шаг, для которого еще нет входных данных, не может ничего высчитать, поэтому он оставляет `_output` пустым, а не выдумывает его. Этот шаг не является ошибкой и не отправляется на выполнение — отсутствие значения по его Пути Вывода (Output Path) значит лишь то, что он еще не вычислен. Он остается в плане, и на следующем ходу, когда появится значение, которого он ждет, он будет вычислен тогда.

Ветвящийся `_outputPath` (`†state.sunny <|> †state.rainy`) по той же причине сохраняется при переходе хода. Результат явного вызова еще не существует в момент записи хода, поэтому ничто не принуждает выбирать какой-то один вариант; :term[Действие]{canonical="Activity"} принимает решение во время выполнения. **Скрытый (latent)** вызов — это противоположный и всегда таким бывший случай: его `_output` — это собственные рассуждения модели, поэтому само по себе вычисление путей *уже* есть выбор, и `<|>` в Пути Вывода скрытого вызова определяется еще до отправки хода. Те альтернативы, которые он не выбрал, затем считываются из состояния — как только Выражение (Expression) разрешается, каждая пустая ветка (без значения) означает, что во время этого выполнения она уже не появится, а вызовы, ожидающие в этих ветках, просто переносятся, а не отмечаются как ошибочные.

### Предложение вместо Выполнения

Продуманный рабочий процесс (сначала план, а затем действие после проверки) не требует отдельного режима планирования. Это намеренное использование правила планировщика: **предложение — это вызов, приостановленный на пути, в который еще никто ничего не записал (шлюзе).**

О том, какие это пути, договариваются неявно (по соглашению), а не декларируют. **Любой путь в `†state.approvals` — это шлюз одобрения (approval gate)**, и нет другого способа определить его: ни флага на вызове, ни второго канала связи, ни списка, который нужно синхронизировать с планом со стороны хоста. Шлюз, который где-то нужно прописывать, можно забыть прописать; а пространство имен (namespace) забыть невозможно, поскольку это и есть сам путь.

Дайте каждой альтернативе собственный шлюз и позвольте каждому шагу из этой альтернативы читать его. План А с шагами, читающими `†state.approvals.planA`, план Б с шагами, читающими `†state.approvals.planB`. Ни в одном пути пока нет значения, поэтому ни один план не запускается, и оба находятся в :term[Плане]{canonical="Plan"} как предложения — чистая структура данных, представляющая всю стратегию, что является именно тем чекпойнтом, который требуется обдуманному рабочему процессу. Его можно:

- **Проверить на валидность:** граф можно проверить на наличие круговых зависимостей или других структурных ошибок.
- **Провести симуляцию:** холостой прогон может помочь предсказать поведение рабочего процесса.
- **Показать для одобрения:** предоставить человеку для проверки, внесения правок или одобрения перед выполнением (:term[HITL]{canonical="HITL (Human-in-the-Loop)"}).

Одобрение в таком случае является обычной записью в выбранный шлюз. Ничего нового при этом не выбирается; шаги этого плана становятся готовы к выполнению, так как теперь появилось то, что они должны прочесть, а шаги плана, который никто не выбрал, продолжают ждать и отбрасываются на более позднем ходу. То, к какой альтернативе относится шаг, зависит от пути, к которому он привязан — здесь нет никаких меток «предложение» или второго канала связи.

На практике только ПЕРВЫЙ шаг в цепи альтернативы ссылается на этот шлюз; остальные шаги читают то, что написал бы этот первый шаг. Весь подграф, зависящий от узла шлюза, приостанавливается и тоже ждет разрешения по той же причине, даже если в нем есть только один вызов, упоминающий путь одобрения.

**Одобрение происходит между запусками (runs), а не во время одного.** Ничто извне цикла не может выполнять запись в :term[Состояние]{canonical="State"} в момент, когда цикл запущен, поэтому предложение никогда не отправляется на исполнение во время того же запуска, когда было написано. Модель предлагает, запуск заканчивается, затем тот, кто принимает решение, пишет в шлюз, а следующий запуск начинается с того, что готовое значение уже лежит в :term[Состоянии]{canonical="State"} — так ожидающие шаги просто разрешаются. Не бывает никаких пауз или блокировок, и :term[Цикл Выполнения]{canonical="Execution Loop"} не получает никаких новых состояний. Именно поэтому весь механизм обходится только наличием пространства имен и не требует отдельной машинерии.

**Предложение за шлюзом ожидания не является сбоем и не сообщает об ошибке.** Вызов, ждущий открытия шлюза, просто ждет; вызов, ждущий по пути, в который уже никто никогда ничего не напишет, является сломанным. И те, и другие — это вызовы, чьи :term[Ссылки на Переменные]{canonical="Variable Reference"} не разрешились, поэтому только пространство имен и отличает их друг от друга. Об их ожидании сообщается один раз, в самом конце запуска (run), когда перечисляется каждый шлюз и то, что он удерживает — и больше ни разу во время хода. Иначе контекст был бы наполнен лишними уведомлениями, а модель усвоила бы, что ожидание через шлюз — это то, за что её наказывают.

**Одобрение каждого экземпляра (instance) не требует никаких дополнительных настроек.** Шлюз — это обычный путь :term[Состояния]{canonical="State"}, поэтому работает он так же: записанный глобально, он будет доступен для каждого экземпляра и все они продолжат выполнение; записанный внутри одного экземпляра, он разрешится только там, а во всех остальных экземплярах это же предложение останется в ожидании. Для одобрений нет никакого специального синтаксиса, связанного с адресацией экземпляров, поскольку это уже решено через правило специфичности в :term[013: Агент/Экземплирование]{href="./013_agent_instancing.md"}.

Цена отсутствия отдельного режима легко объясняется тем, что для этого нет никаких структурных ограничений: **предложение, чьи вызовы не имеют невыполненных зависимостей, отправляется в работу немедленно.** Вызов, который читает лишь уже имеющиеся в :term[Состоянии]{canonical="State"} значения, — это не предложение, а действие. И шлюз должен быть :term[Ссылкой на Переменную]{canonical="Variable Reference"}: `†state.approvals.planA` будет ждать, но если в этом же параметре лежит просто слово `"approved"`, он ничего не будет ждать. Если что-то задумывается как предложение, оно должно стоять за шлюзом ожидания.

## План как Эволюционирующая Стратегия

:term[План]{canonical="Plan"} не статичен; это живая стратегия, которая может адаптироваться на каждом шаге цикла выполнения. Ключевое отличие заключается в том, что `Plan` — это не просто какой-то вывод от LLM. Когда агент впервые генерирует набор :term[Вызовов Инструментов]{canonical="Tool Call"}, это всего лишь предполагаемая последовательность действий. Истинным :term[Планом]{canonical="Plan"} она становится только в случае, если передается в качестве контекстного сообщения в _следующий_ запрос в цикле.

Этот цикл превращает разовый вывод в продолжительную стратегию:

- **:term[Контекст]{canonical="context"}** запроса содержит объект :term[Состояния]{canonical="State"} и сообщение :term[План]{canonical="Plan"} с предыдущего шага.
- **:term[Решение]{canonical="Solution"}**, сгенерированное LLM, содержит новый набор :term[Вызовов Инструментов]{canonical="Tool Call"}, которые становятся **новым :term[Планом]{canonical="Plan"}** для следующего шага.

Такой итеративный процесс позволяет агенту быть одновременно проактивным и реактивным. Он может следовать уже существующему :term[Плану]{canonical="Plan"}, но при этом изменять его в зависимости от результатов предыдущего шага. К примеру, если :term[Вызов Инструмента]{canonical="Tool Call"} падает с ошибкой, агент может сгенерировать новый :term[План]{canonical="Plan"}, включающий шаги по устранению этой ошибки. Это делает систему отказоустойчивой и легко адаптируемой.

**Сценарий:** Агенту службы автоматической поддержки клиентов необходимо обработать возврат средств. Стандартная процедура, инициированная запросом пользователя, заключается в том, чтобы сначала проверить историю платежей для контекста, а затем оформить возврат средств.

**1. Изначальный Запрос**

Цикл начинается с запроса от клиента. На основе этого значения `input` LLM формирует стандартный двухшаговый `Plan` по возврату средств. Это будет идеальным, наиболее часто встречающимся рабочим процессом.

::::columns
:::column{title="Контекст и Схема для Запроса"}

```json
// Agent.Request(config, schema, context)
{
  "schema": {
    "type": "object",
    "properties": {
      "calls": { "type": "array" },
      "output": {
        "type": "object",
        "nullable": true,
        "properties": {
          "confirmationId": { "type": "string" },
          "message": { "type": "string" }
        }
      }
    }
  },
  "context": [
    {
      "type": "input",
      "request": "I'd like a refund for my last order.",
      "customerId": "cust_123",
      "amount": 50.0
    }
  ]
}
```

:::
:::column{title="`solution` от LLM"}

```json
{
  "calls": [
    {
      "_tool": "checkBillingHistory",
      "customerId": "†input.customerId"
    },
    {
      "_tool": "issueRefund",
      "customerId": "†input.customerId",
      "amount": "†input.amount"
    }
  ],
  "output": null
}
```

:::
::::

**2. Следующий Запрос в Цикле**

:term[Цикл Выполнения]{canonical="Execution Loop"} запускает вызов `checkBillingHistory` и заполняет :term[Состояние]{canonical="State"}. История подсвечивает некую сложность (например, предыдущий возврат платежа). На этом этапе агент, предоставленный самому себе, вполне мог бы решить воспользоваться другим доступным инструментом, `escalateToSupervisor`.

Однако сообщение `Plan` в контексте обеспечивает необходимую структуру. Объединяя то, что она _знает_ (текущее, сложное `State`) с тем, что _должна сделать_ (`Plan`), LLM точно понимает свою позицию в рабочем процессе и придерживается прописанного «счастливого пути».

::::columns
:::column{title="Контекст"}

```json
[
  {
    "type": "state",
    "billingHistory": {
      "orders": 5,
      "lastChargeback": "2025-09-10"
    }
  },
  {
    "type": "plan",
    "plan": [
      {
        "_tool": "checkBillingHistory",
        "customerId": "†input.customerId"
      },
      {
        "_tool": "issueRefund",
        "customerId": "†input.customerId",
        "amount": "†input.amount"
      }
    ]
  }
]
```

:::
:::column{title="`solution` от LLM"}

```json
{
  "calls": [
    {
      "_tool": "issueRefund",
      "customerId": "†input.customerId",
      "amount": "†input.amount"
    }
  ],
  "output": {
    "confirmationId": "refund_xyz789",
    "message": "The refund has been processed successfully."
  }
}
```

:::
::::

Такой `Plan` обеспечивает процедурную согласованность, предотвращая преждевременную эскалацию и удерживая агента на выбранном маршруте.

:::::

:::::details{title="Пример: Внесение Изменений в План"}

Этот пример демонстрирует, как агент может изменить существующий :term[План]{canonical="Plan"} в ответ на появление новой информации, выбрав другой инструмент.

::::columns
:::column{title="Контекст"}

Агенту выдают существующий «счастливый путь» `Plan` и новый `Input` от пользователя, в котором появляется дополнительное ограничение.

```ts
[
  { type: 'tool', tool: Tool.bookFlight },
  { type: 'tool', tool: Tool.bookHotel },
  { type: 'tool', tool: Tool.findPetFriendlyHotel },
  {
    type: 'plan',
    plan: [
      {
        _tool: 'bookFlight',
        destination: '†input.destination',
      },
      {
        _tool: 'bookHotel',
        destination: '†input.destination',
      },
    ],
  },
  {
    type: 'input',
    destination: 'Berlin',
    instruction: "Actually, I'll be traveling with my dog.",
  },
];
```

:::
:::column{title="`solution` от LLM"}

LLM понимает, что исходный план больше не актуален. Она отбрасывает старый план и генерирует новый, меняя `bookHotel` на более специализированный инструмент.

```json
{
  "calls": [
    {
      "_tool": "bookFlight",
      "destination": "†input.destination"
    },
    {
      "_tool": "findPetFriendlyHotel",
      "destination": "†input.destination"
    }
  ],
  "output": null
}
```

:::
::::

Агент не ограничивается одним лишь параметром; он фундаментально меняет свою стратегию, выбирая более подходящий инструмент (`findPetFriendlyHotel`), исходя из новых требований. Этот новый набор :term[Вызовов Инструментов]{canonical="Tool Call"} становится :term[Планом]{canonical="Plan"} для следующего шага в :term[Цикле Выполнения]{canonical="Execution Loop"}.

:::::

:::::details{title="Пример: Обработка Ошибок"}

Этот пример демонстрирует, как агент может отклониться от «счастливого пути» своего :term[Плана]{canonical="Plan"} при столкновении с непредвиденной ошибкой. Процесс показан в двух этапах: исходный «счастливый путь» и перепланирование, которое происходит при падении инструмента.

**1. Исходный План**

Агенту выдается набор инструментов и ввод от пользователя. Он генерирует оптимистичный «счастливый путь» из двух шагов, который не включает в себя возможные падения и сбои.

::::columns
:::column{title="Исходный Контекст"}

```ts
Agent.Request(config, {
  schema: {
    type: 'object',
    properties: {
      calls: { type: 'array' },
      output: {
        type: 'object',
        nullable: true,
        properties: {
          status: {
            type: 'string',
            enum: ['Success', 'Failed'],
          },
        },
      },
    },
  },
  context: [
    { type: 'tool', tool: 'Tool.processPayment' },
    { type: 'tool', tool: 'Tool.confirmOrder' },
    { type: 'tool', tool: 'Tool.reportFailure' },
    { type: 'input', amount: 50.0 },
  ],
});
```

:::
:::column{title="Исходное Решение"}

```json
{
  "calls": [
    {
      "_tool": "processPayment",
      "amount": "†input.amount",
      "_outputPath": "†state.receipt <|> †state.error"
    },
    {
      "_tool": "confirmOrder",
      "receipt": "†state.receipt"
    }
  ],
  "output": null
}
```

:::
::::

**2. Ошибка и Перепланирование**

:term[Цикл Выполнения]{canonical="Execution Loop"} пытается запустить `processPayment`, но происходит ошибка инструмента. Движок заполняет `†state.error`. На следующей итерации LLM видит это новое состояние с ошибкой вместе с исходным (теперь уже устаревшим) планом и генерирует новое решение для устранения ошибки.

::::columns
:::column{title="Контекст для Следующего Запроса"}

```json
[
  {
    "type": "state",
    "error": { "code": "card_declined", "message": "Your card was declined." }
  },
  // Исходный, теперь уже устаревший план, все еще находится в контексте
  {
    "type": "plan",
    "plan": [
      { "_tool": "processPayment", "_outputPath": "†state.receipt <|> †state.error" },
      { "_tool": "confirmOrder", "receipt": "†state.receipt" }
    ]
  }
]
```

:::
:::column{title="Новое Решение (Перепланированное)"}

```json
{
  "calls": [
    {
      "_tool": "reportFailure",
      "error": "†state.error"
    }
  ],
  "output": { "status": "Failed" }
}
```

:::
::::

Агент распознал наличие `error` в :term[Состоянии]{canonical="State"}, проигнорировал устаревший «счастливый путь» в :term[Плане]{canonical="Plan"} и сгенерировал новый, состоящий из одного шага план для `reportFailure`. Это демонстрирует способность агента быстро реагировать на непредвиденные результаты.

:::::

:::::details{title="Пример: Планирование на основе Схемы"}

Этот пример демонстрирует, как предоставление параметра `schema` для объекта :term[Состояния]{canonical="State"} работает в качестве :term[черновика]{canonical="Blueprint"}, направляя LLM при создании структурно правильного :term[Плана]{canonical="Plan"}.

::::columns
:::column{title="Контекст со Схемой Состояния"}

Вызывающий предоставляет `Input` и сообщение `State`, которое содержит только `schema`. Эта схема определяет намереваемый поток данных, задавая "переменные", которые этот план должен использовать.

```json
[
  { "type": "tool", "tool": "Tool.detectLanguage" },
  { "type": "tool", "tool": "Tool.isEnglish" },
  { "type": "tool", "tool": "Tool.translateText" },
  {
    "type": "input",
    "text": "Bonjour le monde"
  },
  {
    "type": "state",
    "schema": {
      "type": "object",
      "properties": {
        "language": { "type": "string" },
        "isEnglish": { "type": "boolean" },
        "translatedText": { "type": "string" }
      }
    }
  }
]
```

:::
:::column{title="`solution` от LLM"}

LLM использует схему `State` как руководство для построения подходящего плана, правильно связывая :term[Путь Вывода]{canonical="Output Path"} одного инструмента с входом следующего.

```json
{
  "calls": [
    {
      "_tool": "detectLanguage",
      "text": "†input.text",
      // LLM знает, что нужно использовать этот путь из схемы.
      "_outputPath": "†state.language"
    },
    {
      "_tool": "isEnglish",
      // Правильно ссылается на результат предыдущего шага.
      "language": "†state.language",
      "_outputPath": "†state.isEnglish"
    },
    {
      "_tool": "translateText",
      "text": "†input.text",
      "isEnglish": "†state.isEnglish",
      "_outputPath": "†state.translatedText"
    }
  ],
  "output": null
}
```

:::
::::

Предоставляя `schema`, вызывающий дает LLM четкий :term[черновик]{canonical="Blueprint"} (схему) потока данных. LLM не нужно гадать над именами переменных или последовательностями; она просто заполняет готовые слоты, возвращая более надежный и предсказуемый `Plan`.

:::::

Этот итеративный цикл планирования и выполнения является основой :term[Процесса]{canonical="Process" href="./203_idea_process.md"}. Он представляет собой автономный снимок рабочего процесса, регистрирующий доступные :term[Инструменты]{canonical="Tool"}, текущее :term[Состояние]{canonical="State"} и сам :term[План]{canonical="Plan"}.

## От Единичного Плана к Переиспользуемым Рабочим Процессам

Сообщение :term[План]{canonical="Plan"} определяет последовательность действий для конкретной задачи. Чтобы сделать такие рабочие процессы переиспользуемыми, нам нужен способ инкапсулировать их в компоненты, которые можно вызывать из других :term[Планов]{canonical="Plan"}.

:term[013: Агент/Экземплирование]{href="./013_agent_instancing.md"} описывает протокол для этого параллельного выполнения.
