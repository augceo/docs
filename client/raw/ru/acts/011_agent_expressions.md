# 011: Агент/Выражения

> [!DEFINITION] [Выражение](./000_glossary.md)
> Синтаксис для объединения нескольких путей в :term[Ссылке на переменную]{canonical="Variable Reference"} или :term[Пути вывода]{canonical="Output Path"} для создания условных или параллельных потоков данных.

> Sidenote:
> - Требует:
>   - :term[007: Агент/Переменные]{href="./007_agent_variables.md"}
>   - :term[008: Агент/Вывод]{href="./008_agent_output.md"}
> - Открывает:
>   - :term[012: Агент/План]{href="./012_agent_plan.md"}

В то время как :term[Ссылки на переменные]{canonical="Variable Reference"} и :term[Пути вывода]{canonical="Output Path"} обеспечивают базовую маршрутизацию потока данных, **Выражения (Expressions)** добавляют в нее логику. Они представляют собой синтаксис для создания условных ветвлений и параллельных потоков данных, позволяя агенту декларативно задавать более сложное и адаптивное поведение.

В выражениях используется `<|>` (ИЛИ) для условной логики и `*>` (И) для параллельных операций. Их можно применять двумя основными способами: для сбора входных данных для инструмента и для распределения выходных данных от инструмента.

## Входные выражения (Многие к одному)

При использовании во входных параметрах :term[Вызова инструмента]{canonical="Tool Call"}, выражения позволяют одному параметру получать данные из различных источников. Это создает поток данных **многие-к-одному (`M:1`)**, обеспечивая гибкие шаблоны сбора данных, такие как резервные варианты (fallbacks) и слияния.

> Sidenote:
> ```mermaid
> graph TD
>     SourceA["†state.userInput"] --> ToolInput["processData(data)"]
>     SourceB["†state.default"] --> ToolInput
> ```

Эта возможность является ключом к созданию надежных и переиспользуемых инструментов. Вместо жестко заданной структуры входных данных, инструмент может гибко подстраиваться под доступный контекст, запрашивая данные из разных мест в зависимости от того, что доступно во время выполнения.

::::columns
:::column{title="Резервная логика с <|>"}

При использовании в :term[Ссылке на переменную]{canonical="Variable Reference"}, оператор `<|>` работает как резервный вариант. Выражение `†state.userInput <|>
 †state.default` дает движку команду сначала искать значение в `state.userInput`. Если оно не найдено, будет использовано значение из `state.default`. Это удобно для задания значений по умолчанию или элегантной обработки необязательных входных данных.

```json
{
  "_tool": "processData",
  "data": "†input.optionalData <|> †state.defaultData"
}
```

:::
:::column{title="Параллельные зависимости с *>"}

При использовании в :term[Ссылке на переменную]{canonical="Variable Reference"}, оператор `*>` служит шлюзом, гарантирующим, что все указанные пути к данным существуют в контексте перед тем, как продолжить. Если все пути присутствуют, выражение принимает значение _последнего_ пути в цепочке. Это дает возможность задавать зависимости, гарантируя, что инструмент запустится только после того, как будут доступны все необходимые для него данные.

```json
// Этот инструмент запустится только если загружены и профиль пользователя, и его разрешения.
// Параметр `permissions` получит значение переменной `†state.permissions`.
{
  "_tool": "renderDashboard",
  "permissions": "†state.userProfile *> †state.permissions"
}
```

:::
::::

## Выходные выражения (Один ко многим)

При применении в :term[Пути вывода]{canonical="Output Path"}, выражения позволяют записывать результат работы одного инструмента сразу в несколько мест. Это создает поток данных **один ко многим (`1:M`)**, что делает возможными такие паттерны, как условное ветвление и разветвление (fan-out).

> Sidenote:
> ```mermaid
> graph TD
>     ToolOutput["verifyUser()"] --> DestA["†data.user.verified"]
>     ToolOutput --> DestB["†data.user.failed"]
> ```

Этот механизм дает возможность одному инструменту иметь несколько результатов, зависящих от контекста. Это основа для создания динамичных агентов, которые могут разумно реагировать на ситуации, выбирая подходящий путь выполнения на основе результатов своих действий.

::::columns
:::column{title="Альтернативные пути (Ветвление) с <|>"}
Использование `<|>` в :term[Пути вывода]{canonical="Output Path"} позволяет инструменту объявить свои возможные исходы; из них будет записан ровно один. По умолчанию путь записывает **первую** альтернативу, которая является обычным результатом работы инструмента. Чтобы записать любую другую альтернативу, :term[Действие]{canonical="Activity"} возвращает готовое сообщение `Data Message` с указанием нужного пути вместо простого значения — сообщение, которое не управляется общим Путём вывода. На этом всё "внутренняя логика инструмента сама решает": нет никакого отдельного протокола, и нигде не фиксируется, какая именно альтернатива имелась в виду.

Оператор состоит из трёх символов без пробелов между ними: знак меньше, вертикальная черта, знак больше. Символы `|` и `||` — это ошибки, а не операторы: первый считывается как часть пути, поэтому запись попадет туда, где ее никто не прочтет, и все вызовы, ожидающие любой из результатов, зависнут. Символ `|>` — это вообще другой оператор: он передает значение в функцию (pipe) и используется только параметрах; если его поместить в Путь вывода, он будет отклонён, а не записан, и это единственная ошибка здесь, о которой система сообщит прямо.

```json
// Если `verifyUser` выполняется успешно, результат записывается в `data.user.verified`;
// иначе — в `data.user.failed`
{
  "_tool": "verifyUser",
  "userId": "perfect-stranger",
  "_outputPath": "†data.user.verified <|> †data.user.failed"
}
```

:::
:::column{title="Параллельные пути (Разветвление) с *>"}
Использование `*>` в :term[Пути вывода]{canonical="Output Path"} дает движку команду выполнить разветвление, записав один и тот же результат сразу в несколько путей. Это полезно для трансляции результата в несколько частей состояния или для целей аудита.

```json
// Одновременная запись в объекты `user` и `audit` в состоянии.
{
  "_tool": "generateSummary",
  "text": "Long body of text here...",
  "_outputPath": "†data.user.summary *> †data.audit.summary"
}
```

:::
::::

## Входное выражение — это любое вычисление, а не только выбор

Приведенная выше входная сторона объединяет несколько путей в одно значение, используя для этого ровно один комбинатор. Это самый примитивный вариант "многие к одному". **Основная форма — это выражение на языке, который читатель уже знает**, поэтому `†state.a <|> †state.b` и `†state.items.filter(i => i.paid).length` — это одно и то же, просто одно из них выбирает, а другое вычисляет.

Это применяется сразу в трёх местах, и ни одно из них не является новым механизмом:

- **Параметр** хранит вычисленное значение, а не просто найденное. Инструмент, которому нужно количество, получает количество, а не массив и инструкцию (что с ним делать).
- **Условие** придерживает вызов до тех пор, пока не поступит то, с чем стоит работать. Ветвление на основе *значения*, а не просто на основе наличия значения, становится тем, что цикл может обработать самостоятельно.
- **Именованное выражение** вычисляется единожды и используется повсеместно: его результат сохраняется в `†expr.<name>`, поэтому ссылка на него является обычной :term[Ссылкой на переменную]{canonical="Variable Reference"} и не требует повторного вычисления.

**То, на основе чего производятся вычисления, не обязательно должно быть вычислено заранее чем-то еще.** :term[Вызов]{canonical="Call"}, за которым не стоит :term[Действие]{canonical="Activity"}, получает ответ от модели в том же самом запросе, который его и создал, и эта запись направляется в тот же сток — поэтому выражение, считывающее его :term[Путь вывода]{canonical="Output Path"}, становится готовым на этом же шаге, а не на следующем. Решение, для которого никто не писал код, и арифметика над ним — выполняются за один запрос. Данным механизмом управляет :term[003: Агент/Действие]{href="./003_agent_activity.md"}; здесь же важно то, что вычисляемый параметр может такой ответ считывать.

**На стороне вывода это не работает.** :term[Путь вывода]{canonical="Output Path"} должен оставаться путём: "один ко многим" остается тем, чем является, а выражения допускаются только во входных позициях. Если размыть эти границы, вычисленная строка может быть истолкована как запись по множеству назначений — а это скрытый и дорогостоящий способ совершить ошибку.

## Почему операторы отличаются от языковых

Возникает соблазн оставить `||` и `&&`, поскольку основной формат теперь базируется на JavaScript, а в JavaScript есть и то, и другое. **Но здесь они означают совсем иное, и разница может быть незаметна.**

Эти операторы проверяют **существование**: путь либо разрешён (найден), либо нет. JavaScript проверяет на **истинность** (truthiness). Таким образом, `†state.count || 5` выдаст само число в одном случае и `5` в другом всякий раз, когда счётчик равен нулю — одни и те же символы, другой результат, и вы этого даже не заметите.

Более глубокая причина заключается в том, что :term[Ссылка на переменную]{canonical="Variable Reference"} — это **значение в будущем (future)**. Она называет значение, которое будет существовать, ссылаясь на него до его появления — на этом строится всё понятие готовности цикла. А **операторы JavaScript работают с готовыми значениями.** Неразрешённая ссылка не является ни `null`, ни `undefined`; это объект, который всё еще находится в ожидании, поэтому оператор `??` тут не поможет и каждый раз будет тихо выбирать левую сторону.

Поэтому эти два оператора позаимствованы из традиции, которая серьезнее всего подошла к работе со значениями, которых может и не быть:

- **`<|>`** — ` Alternative ` (Альтернатива). *Первая альтернатива, у которой есть значение.* В случае с будущими значениями (futures) приоритет отдается левой стороне: считывается значение слева, если оно есть, а в правую сторону мы переходим только в том случае, если левого значения нет.
- **`*>`** — ` sequence-right ` (правая последовательность). *Дождаться левого, отбросить его, взять правое.* Шлюз — он работает в точности так, как и ожидается.

**`<|>` отвечает на два разных вопроса, и их стоит разделять.** Вопрос *«Какое значение?»* решается предпочтением левой стороны, описанным выше. Вопрос *«Когда может пройти вызов?»* — это уже спекулятивная часть: условие готовности удовлетворяется, как только **любая** из сторон получила значение, поэтому вызов, медленная ветка которого всё еще задерживается, переходит на быструю. Ни на один из вопросов нет ответа «какое придет первым» — ничто не фиксирует порядок поступления данных, и даже если бы фиксировало, оператор бы его не считывал.

К ним присоединяется третий оператор, когда выражение может содержать конвейер (pipeline), а не одиночный термин:

- **`|>`** — ` flow ` (поток). `x |> f` означает `f(x)`, поэтому цепочка читается в порядке выполнения, а не задом наперед. Это конвейерная передача (pipe) из F#, OCaml, Elixir и Julia, и к ней же стремится предложение по внедрению конвейеров в самом JavaScript.

```
†state.items |> map(enrich, 4) |> filter(i => i.valid) |> reduce(sum, 0)
```

Ни один из трех операторов нельзя написать в JavaScript — все они вызовут синтаксическую ошибку, поэтому их невозможно по ошибке принять за встроенные в язык. Синтаксис здесь разделяется по объекту взаимодействия, а не по договоренности: **`||` и `??` — для готовых значений, `<|>` `*>` `|>` — для будущих значений (futures).**

**Приоритет операторов от самого строгого к самому свободному: `<|>`, затем `|>`, затем `*>`.** Источник выбирается до его передачи по конвейеру, а шлюз управляет всем, что идет после него, поэтому `†a <|> †b |> f` берет источник, который дал ответ, и передает его дальше, в то время как `†gate *> †docs |> f` удерживает весь конвейер, пока шлюз не разрешится. **Используйте скобки всякий раз, когда эти три оператора смешиваются.** Внимательный читатель может прочесть средний случай двояко, а модели, которой пришлось объяснять, что одиночная `|` не является оператором, такие вещи доверять точно нельзя.

### Конвейер занимает весь параметр или не является конвейером вовсе

**Эти три оператора считываются только на верхнем уровне выражения**, а если оператор встроен в более крупное выражение, он просто игнорируется без всяких предупреждений. В выражении `'total: ' + (†state.x |> f)` оператор `|>` находится на глубине вложенности один, где его ничто не разделяет — так что строка не скомпилируется как выражение, а воспримется как обычный литерал на последнем этапе парсинга, и **:term[Действию]{canonical="Activity"} будет передан сам текст с символом креста.** Ни на одном из уровней не возникнет ошибки, а полученное неправильное значение будет выглядеть вполне правдоподобно.

Способ обойти эту ситуацию кроется не в экранировании, а в расположении. **Сделайте конвейер всем параметром, а изменяющуюся часть поместите внутрь функции обратного вызова (callback)**, где использование :term[Ссылок на переменную]{canonical="Variable Reference"} вполне законно:

```
†state.passages |> filter(p => †state.chosen.includes(p.id)) |> map(p => p.words, 4)
```

То же самое правило работает и в обратную сторону для автора, стремящегося к параллелизму: символ-указатель внутри списка аргументов — `take(†a <|> †b)` — тоже никогда не переписывается. Альтернативе место в самом начале конвейера — именно там она наглядно показывает, что имел в виду автор.

> Sidenote:
> `|>` несет в себе один риск, которого нет у двух других операторов, и о нем стоит упомянуть не из-за вероятности сбоя, а из-за того, как именно он произойдет. Предложение о конвейере в JavaScript зависло между двумя вариантами написания, и если язык однажды внедрит другой вариант, `|>` перестанет вызывать синтаксическую ошибку. Такой сбой будет **громким** — токенизатор столкнётся с валидным JavaScript там, где он ожидал увидеть свой собственный оператор — а именно из-за «громких» ошибок нам и пришлось отказаться от `||`. Направление передачи данных в обоих вариантах совпадает; отличается только сам символ-заполнитель.

## Откуда берутся стадии

Функции `map`, `filter` и `reduce` в этой цепочке — это не методы массива. Это `@idealic/iterators`, и выражение получает их уже привязанными — именно это позволяет цепочке читаться так, как она написана, поскольку у каждого из этих операторов есть каррированная форма, а каррированный оператор **является** той функцией `вход → выход`, которой и должна быть стадия.

Из этого следуют три вещи, которые не может сделать цепочка `Array.prototype`, и именно они оправдывают существование этого конвейера вообще:

- **Параллелизм — это аргумент.** `map(enrich, 4)` обогащает (enrich) сразу по четыре за раз. Цепочка массива обрабатывает элементы по одному, и нет способа указать иное.
- **Конвейер является ленивым, поэтому `take` останавливает работу, а не просто отбрасывает результаты.** `|> map(expensive) |> take(2)` запустит ресурсоемкую функцию `expensive` дважды. Если выполнить то же самое через цепочку массива, она запустится для всего, а затем большая часть результатов будет просто выброшена.
- **Запуск можно отменить.** Каждый оператор несет собственный сигнал прерывания вычислений, поэтому, если затраты на выражение превышают лимит, работе дается команда остановиться, а не продолжать выполняться в фоновом режиме. У `Promise.race` намеренно нет способа передать такую команду, поэтому в гонке параллельная ветка продолжает работать, а в данном конвейере — нет.

Конвейер, заканчивающийся потоковым оператором, возвращает собранные элементы: `†state.items |> map(enrich, 4)` поступает в параметр в виде массива. Конвейер, заканчивающийся на `reduce`, `find` или `every`, возвращает само итоговое значение напрямую.

> Sidenote:
> Значение в будущем (future), которое может участвовать в гонке, — это значение, над которым можно спекулировать (выполнять спекулятивно), — но **гонка двух ссылок происходит не так.** Выражение дожидается каждой прочитанной ссылки перед выполнением своего тела, поэтому к моменту старта оба значения уже получены, и `Promise.race` между ними просто разрешается по очереди в списке. Спекуляция кроется в `<|>`, который запускает вызов, как только любая из сторон получает значение. Для настоящей гонки нужны две вещи, которые разрешаются в разное время, и выражение должно само их предоставить.
>
> Где бы она ни происходила, это даёт одно преимущество — не требуется дополнительных механизмов: **одно выражение, одно значение, одна запись**, поэтому тут нечего отменять и нет возможности стереть записанную ветку проигравшего. Проигравший не отменяется (сохраняя смысл «гонки», как и везде); просто его значение перестает передаваться дальше. Если ветка достигла инструмента, она его достигла.

## От выражений к стратегиям

Выражения служат логическим «клеем» для связи отдельных :term[Вызовов инструментов]{canonical="Tool Call"}. Обладая этой возможностью, агент может выйти за рамки простых линейных последовательностей действий и начать конструировать сложные, разветвлённые рабочие процессы.

:term[012: Агент/План]{href="./012_agent_plan.md"} описывает, как эти выразительные связи используются для построения целостного стратегического :term[Плана]{canonical="Plan"}.
