# 008: Агент/Вывод

> [!DEFINITION] [Путь вывода](./000_glossary.md)
> Мета-свойство `_outputPath` у :term[Вызова]{canonical="Call"}, которое указывает, где нужно сохранить результат работы инструмента. Это строка, которая сообщает движку исполнения (execution engine), куда поместить результат, делая его доступным для последующих шагов.

> Sidenote:
> - Требуется:
>   - :term[004: Агент/Вызов]{href="./004_agent_call.md"}
>   - :term[007: Агент/Переменные]{href="./007_agent_variables.md"}
> - Позволяет:
>   - :term[010: Агент/Цикл]{href="./010_agent_loop.md"}

В системе агентов есть две формы вывода: промежуточные результаты :term[Вызовов инструментов]{canonical="Tool Call"}, записываемые в контекст, и :term[Финальный вывод]{canonical="Final Output"} всего повторяющегося (итеративного) процесса.

## Запись в контекст с помощью :term[Пути вывода]{canonical="Output Path"}

Хотя любое :term[Сообщение с данными]{canonical="Data Message" href="./005_agent_data.md"} может служить черновиком для рабочего процесса, :term[Путь вывода]{canonical="Output Path"} в мета-свойствах :term[Вызова]{canonical="Call"} является основным механизмом записи в него. Когда :term[Вызов инструмента]{canonical="Tool Call"} с этим свойством выполняется, система добавляет его результат в конец контекста как новое сообщение.

> Sidenote:
> Хотя целью может быть любое :term[Сообщение с данными]{canonical="Data Message"}, чаще всего производится запись в :term[Сообщение состояния]{canonical="State Message" href="./009_agent_state.md"}, чтобы сохранить информацию на протяжении множества шагов процесса.

Это новое сообщение является стандартным :term[Сообщением с данными]{canonical="Data Message"}, но оно включает несколько дополнительных элементов метаданных, скрытых от LLM:

- **`_call`**: Исходный :term[Вызов инструмента]{canonical="Tool Call"}, который сгенерировал этот вывод.
- **`_date`**: Временная метка ISO, указывающая, когда был записан вывод.
- **`_outputMethod`**: Метод, указанный в исходном вызове, который определяет, как эти данные должны объединяться с другими данными.

Это обеспечивает полный, проверяемый след того, как изменялся контекст, что бесценно для отладки и отслеживания логики рассуждений агента.

### Определение Пути вывода

:term[Путь вывода]{canonical="Output Path"} можно задать двумя способами, что дает разный уровень контроля над поведением инструмента.

::::columns{.examples}
:::column{title="Динамический путь (Решает LLM)"}

В этом режиме у LLM есть свобода решать во время работы, где сохранить результат, что делает инструмент очень гибким.

```json
// Схема инструмента позволяет использовать любую строку для _outputPath
{
  "_outputPath": {
    "type": "string",
    "description": "Путь для сохранения сводки по пользователю.",
    "pattern": "^†"
  }
}
```

:::
:::column{title="Заранее заданный путь (Жестко закодирован)"}

Этот подход задает строгое предсказуемое поведение: инструмент всегда будет записывать свой вывод в конкретное, жестко прописанное место.

```json
// Схема инструмента жестко привязывает _outputPath к конкретному значению
{
  "_outputPath": {
    "type": "string",
    "const": "†data.user.summary"
  }
}
```

:::

### Динамическое разрешение переменных

Важно отметить, что эти сообщения вывода **добавляются**, а не объединяются в момент записи. Такой подход позволяет динамически собирать конечное состояние любой переменной в момент чтения на основе `_outputMethod`, сохраненного в каждом сообщении.

Когда нужно определить значение :term[Ссылки на переменную]{canonical="Variable Reference" href="./007_agent_variables.md"}, например `†data.user.name`, движок ищет сообщения контекста в **обратном хронологическом порядке** (от новых к старым).

- Если алгоритм находит сообщение для искомого пути с `_outputMethod`, равным **`set`** (или без метода, так как `set` используется по умолчанию), он сразу останавливается. Значение этого сообщения становится итоговым, а все более старые сообщения по этому пути игнорируются. Это поведение называется "побеждает последняя запись" (last-write-wins).
- Если алгоритм находит сообщения с методами **`merge`** (глубокое объединение), **`assign`** (поверхностное объединение), **`push`** или **`concat`**, он продолжает поиск назад, собирая все такие сообщения, пока не наткнется на сообщение с методом `set` или на начало контекста. Затем он восстанавливает окончательное значение, применяя собранные операции в хронологическом порядке (от старых к новым).
- Если алгоритм находит сообщение с `_outputMethod`, равным **`erase`**, он останавливается так же, как и при `set`, за исключением того, что он не возвращает никаких данных. Путь читается так, будто в него ничего никогда не записывали, и любые новые данные после стирания начинают накапливаться с чистого листа.

Такое динамическое разрешение переменных гарантирует, что состояние всегда остается согласованным и точно отражает историю операций, позволяя совершать сложные и надежные манипуляции с состоянием.

### Стирание пути, и почему это единственная отмена (Undo)

:term[Вызов инструмента]{canonical="Call"} считается завершенным, когда его :term[Путь вывода]{canonical="Output Path"} содержит значение. Больше ничто не фиксирует, что вызов сработал — нет никакого журнала выполнений, и ни один вызов не имеет отметки о том, что он уже произошел. **Состояние — это и есть запись.** Шаг находится в ожидании, потому что читаемый им путь пуст, и он перестает ждать, когда что-то заполнит этот путь.

Поэтому запустить шаг повторно означает отнять его результат: сотрите путь (командой `erase`), и вызов потребуется снова. Именно для этого нужен `erase`, и именно поэтому повторный запуск выражается в виде записи, а не команды циклу исполнения.

Цена за это озвучена прямо: **вызов, который ничего не записывает, не сохраняет состояние (stateless).** :term[Вызов]{canonical="Call"} без `_outputPath` — это подход "выстрелил и забыл", описанный ниже. Он не оставляет следа о своем выполнении, поэтому нет разницы между запуском один раз или дважды. В этом и заключается суть термина "без сохранения состояния", и это является правильным поведением, а не недочетом. Побочный эффект, который должен сработать ровно один раз, записывает об этом в состояние, и с этого момента он подчиняется тому же механизму, что и любой другой шаг.

:::::details{title="Пример: Добавление и Разрешение переменных"}

**1. Начальное состояние**

Контекст начинается с начального сообщения с данными.

```json
[
  {
    "type": "data",
    "data": { "user": { "name": "Alex", "status": "active" } }
  }
]
```

**2. Исполнение Вызова инструмента**

Инструмент вызывается для обновления статуса пользователя.

```json
// Выполняется вызов
{
  "_tool": "updateUserStatus",
  "newStatus": "inactive",
  "_outputPath": "†data.user.status"
}
```

**3. Контекст после Выполнения**

Движок добавляет новое сообщение с выводом, куда включены метаданные о вызове, создавшем этот вывод.

```json
[
  // Исходное сообщение с данными
  {
    "type": "data",
    "data": { "user": { "name": "Alex", "status": "active" } }
  },
  // Добавленное сообщение вывода от вызова
  {
    "type": "data",
    "data": { "user": { "status": "inactive" } },
    "_call": {
      "_tool": "updateUserStatus",
      "newStatus": "inactive",
      "_outputPath": "†data.user.status"
    },
    "_date": "2025-10-26T12:00:00Z"
  }
]
```

**4. Разрешение переменных**

- Чтобы найти `†data.user.status`, движок প্রথমে проверяет последнее сообщение. Он находит `user.status` и возвращает `"inactive"`.
- Чтобы найти `†data.user.name`, движок проверяет последнее сообщение, не находит `user.name`, затем проверяет предыдущее сообщение. Он находит значение там и возвращает `"Alex"`

:::::

Мощь сочетания :term[Ссылок на переменные]{canonical="Variable Reference"} с :term[Путями вывода]{canonical="Output Path"} кроется в их способности задавать операции с данными, которые еще недоступны. Например, :term[Вызов инструмента]{canonical="Call"} можно настроить для работы со значением из сообщения :term[Входа]{canonical="Input"}, даже если этот конкретный ввод еще не предоставлен. Это позволяет создавать переиспользуемые, параметризованные рабочие процессы.

Эта концепция также распространяется на объединение :term[Вызовов инструментов]{canonical="Call"} в цепочки. Можно создать :term[Вызов инструмента]{canonical="Call"} со :term[Ссылкой на переменную]{canonical="Variable Reference"}, указывающей на :term[Путь вывода]{canonical="Output Path"} _предыдущего_ вызова в той же последовательности. Это формирует многоэтапный поток данных, в котором вывод одного инструмента становится вводом для следующего.

## Вызовы без Пути вывода

Не каждому :term[Вызову инструмента]{canonical="Call"} необходимо сохранять свой результат. Отказ от свойства `_outputPath` — осознанный выбор, сигнализирующий о различном поведении для скрытых (latent) и явных вызовов.

### Временные рассуждения для скрытых вызовов

Для скрытого вызова пропуск `_outputPath` позволяет ему работать как временный шаг для рассуждения — "мысль", которая направляет последующие действия в рамках того же такта (turn), но не записывается в постоянное :term[Состояние]{canonical="State"}. Это специальная методика структурирования процесса рассуждения LLM.

Например, агента можно спроектировать так, чтобы он сначала использовал скрытый инструмент `think` для анализа проблемы и планирования стратегии. Эта "мысль" не сохраняется, но её генерация моментально обогащает внутренний контекст самой LLM. На следующем же этапе внутри того же `solution`, LLM уже может генерировать конкретные, явные :term[Вызовы инструментов]{canonical="Call"}, которые окажутся более эффективными и точными благодаря предшествующему, несохраненному этапу рассуждений.

### "Выстрелил и забыл" для явных вызовов

Для явного вызова :term[Активности]{canonical="Activity"} отсутствие `_outputPath` означает операцию по принципу "выстрелил и забыл". :term[Цикл исполнения]{canonical="Execution Loop"} запустит :term[Активность]{canonical="Activity"}, но не будет дожидаться результата или сохранять его в контексте.

Это полезно для побочных эффектов, когда возвращаемое значение не требуется для продолжения текущего рабочего процесса. Вот частые примеры:

- Запись события во внешний сервис аналитики.
- Отправка уведомления пользователю или другой системе.
- Запуск длительного фонового процесса без необходимости блокировать текущий план.

Его цена уже названа выше: вызов, который ничего не записывает, не сохраняет состояние, поэтому в контексте не остается следов того, был ли он запущен, или нет. Выбирайте подход "выстрелил и забыл", если повторение операции безвредно. Но если это не так, дайте вызову `_outputPath` — тогда факт его запуска станет обычным значением, и `erase` послужит инструментом для его намеренной отмены.

## Взаимодействие с другими системами

- **:term[Сообщение с данными]{canonical="Data Message"}:** `_outputPath` — это основной механизм для создания и обновления :term[Сообщений с данными]{canonical="Data Message"} внутри рабочих процессов. Он превращает :term[Вызов инструмента]{canonical="Tool Call"} без сохранения состояния в операцию с сохранением состояния, записывая результат в контекст и делая его доступным для последующих шагов.

  > Sidenote:
  > - :term[005: Агент/Данные]{href="./005_agent_data.md"}

- **:term[Сообщение состояния]{canonical="State Message"}:** Хотя целью может быть любое :term[Сообщение с данными]{canonical="Data Message"}, в большинстве случаев идет запись в :term[Сообщение состояния]{canonical="State Message"}. Это делает объект :term[Состояния]{canonical="State"} главным "черновиком" рабочего процесса, позволяя разным инструментам обмениваться информацией и использовать результаты друг друга на протяжении множества тактов :term[Цикла исполнения]{canonical="Execution Loop"}.

  > Sidenote:
  > - :term[009: Агент/Состояние]{href="./009_agent_state.md"}

- **:term[Ссылка на переменную]{canonical="Variable Reference"}:** :term[Путь вывода]{canonical="Output Path"} напрямую связан со :term[Ссылкой на переменную]{canonical="Variable Reference"}. :term[Путь вывода]{canonical="Output Path"} записывает данные в контекст, а :term[Ссылка на переменную]{canonical="Variable Reference"} их читает. Вместе они формируют законченную, декларативную схему передачи данных, связывая вывод одного инструмента со вводом другого.

  > Sidenote:
  > - :term[007: Агент/Переменные]{href="./007_agent_variables.md"}

- **:term[Выражения]{canonical="Expression"}:** Выражения внедряют логику непосредственно в контуры передачи данных. Используя `<|>` и `*>` в :term[Пути вывода]{canonical="Output Path"}, :term[Вызов инструмента]{canonical="Tool Call"} можно настроить на обработку условных исходов или распределение результатов по нескольким адресатам. Это переводит систему от жестких, запрограммированных потоков к гибкой структуре, которая адаптируется под условия во время ее исполнения.

  > Sidenote:
  > - :term[011: Агент/Выражения]{href="./011_agent_expressions.md"}

- **:term[План]{canonical="Plan"}:** В контексте :term[Плана]{canonical="Plan"}, :term[Пути вывода]{canonical="Output Path"} выполняют роль "проводов", которые соединяют разные :term[Вызовы инструментов]{canonical="Tool Call"} ("узелки") в полноценный граф передачи данных. Это позволяет агенту настраивать и выполнять целую многоэтапную стратегию в виде единого декларативного объекта.

  > Sidenote:
  > - :term[012: Агент/План]{href="./012_agent_plan.md"}

- **:term[Экземплирование]{canonical="Instancing"}:** Если :term[Вызов инструмента]{canonical="Tool Call"} включает свойство `_instance`, любой указанный в нем `_outputPath` автоматически ограничивается контекстом данных этого конкретного экземпляра. Это гарантирует изоляцию данных при параллельной обработке, так что вывод инструмента, работающего с одним экземпляром, не затронет состояние другого.

  > Sidenote:
  > - :term[013: Агент/Экземплирование]{href="./013_agent_instancing.md"}

## От Временных результатов к Постоянному состоянию

Механизм :term[Пути вывода]{canonical="Output Path"} предоставляет способ управления потоком данных между отдельными :term[Вызовами инструментов]{canonical="Tool Call"}, и его целью может быть любое :term[Сообщение с данными]{canonical="Data Message"}. Тем не менее, для создания сложных, многоэтапных агентов, способных рассуждать и адаптироваться с течением времени, требуется особая память — тип сообщения, специально разработанный для сохранения информации между множеством независимых запросов.

:term[009: Агент/Состояние]{href="./009_agent_state.md"} описывает протокол этой постоянной памяти.
