Документ Сверки

Это документ, который компьютер создаёт автоматически. Он как бы подслушивает обсуждение, подводит итоги, записывает, о чём все договорились, какие споры решили и что теперь нужно делать.

Неизменные правила

СТРОГО СОБЛЮДАЙ ЭТИ ПРАВИЛА:

  1. Временный файл: Ты МОЖЕШЬ создать файл {OUTPUT_DIR}/{FILENAME}.ndjson для записи комментариев. Не создавай никаких других временных файлов. Это как черновик — один можно, а устраивать беспорядок из кучи бумажек нельзя.
  2. Загрузка за один раз: Загружай все нужные данные (комментарии) за один раз. Не нужно бегать туда-сюда много раз, как в магазин за каждым продуктом по отдельности.
  3. Проверка по имеющимся данным: Всегда проверяй информацию по тем данным, что у тебя уже есть (в JSON). Не загружай их заново только для проверки.
  4. Язык: Итоговый документ ДОЛЖЕН быть на том языке, который указан в задании (например, на русском). Технические термины, код и цитаты комментариев переводить не нужно.
  5. Полнота: Абсолютно каждый комментарий должен быть учтён в Отчёте о Полноте. Ничто не должно потеряться.
  6. Без перезапусков: Если найдёшь ошибку (например, чего-то не хватает), не начинай всё сначала. Просто исправь эту конкретную ошибку и продолжай работу.
  7. Анализ «в уме» (без скриптов): Не используй для анализа и подсчётов сторонние программы (скрипты на Python/Shell). Всю обработку информации нужно делать «в уме», используя только свои возможности.

Цель

Документ Сверки — это как мостик между обсуждением (в Pull Request) и реальными действиями. Он берёт все идеи из разговора и превращает их в чёткий план.

2. Получение данных

НИКАКИХ ВРЕМЕННЫХ ФАЙЛОВ

НЕЛЬЗЯ сохранять скачанную информацию во временные файлы (вроде process.md или pr.json), если на это нет прямого разрешения. Причина: Временные файлы создают беспорядок, а это запрещено Правилом №1. Исключение: Единственный разрешённый временный файл — это {OUTPUT_DIR}/{FILENAME}.ndjson для записи комментариев.

Вся остальная информация должна сразу выводиться на экран, а не в файлы.

ОГРАНИЧЕНИЕ: Тебе разрешено делать ТОЛЬКО следующие запросы в интернет:

  1. HTTP GET через curl на https://idealic.academy/raw/en/company/02_process.md
  2. HTTP GET через curl на https://idealic.academy/raw/en/company/50_prompt_truth.md
  3. Запрос к GitHub (чтобы узнать автора Pull Request)
  4. Запрос к GitHub (чтобы получить все комментарии, одной командой ниже)

Не пытайся скачать изменения в коде (diff) или список коммитов. Это не твоя задача.

Шаг 1: Загрузи нужные документы (Обязательно) Скачай информацию по этим ссылкам. Обрабатывай каждый документ отдельно. Ограничение: ВАЖНО: Ты должен использовать отдельные команды для каждого документа. НЕ объединяй их через && или ;.

  1. Процесс:

    curl -s https://idealic.academy/raw/en/company/02_process.md

  2. Истина:

    curl -s https://idealic.academy/raw/en/company/50_prompt_truth.md

  3. Определение Сверки:

    curl -s https://idealic.academy/raw/en/company/22_document_alignment.md

Шаг 2: Получи детали PR (чтобы узнать роли) Узнай, кто автор этого Pull Request.

gh api "repos/{OWNER}/{REPO}/pulls/{PR_NUMBER}" --jq '{author: .user.login, title: .title}'

Шаг 3: Загрузи комментарии

  1. Скачай в файл: Выполни ровно эту команду, чтобы сохранить все комментарии в файл {OUTPUT_DIR}/{FILENAME}.ndjson.

    gh api graphql -F owner='{OWNER}' -F repo='{REPO}' -F pr={PR_NUMBER} -f query='
  query($owner:String!, $repo:String!, $pr:Int!) {
    repository(owner:$owner, name:$repo) {
      pullRequest(number:$pr) {
        reviewThreads(first: 100) {
          nodes {
            isResolved
            comments(first: 50) {
              nodes {
                databaseId
                body
                author { login }
                createdAt
                path
                diffHunk
                replyTo { databaseId }
                url
                reactions(first: 10) { nodes { content } }
              }
            }
          }
        }
      }
    }
  }
' --jq '
  .data.repository.pullRequest.reviewThreads.nodes[]
  | .isResolved as $resolved
  | .comments.nodes[]
  | {
      id: .databaseId,
      body,
      user: (.author.login // "ghost"),
      created_at: .createdAt,
      path,
      diff_hunk: .diffHunk,
      in_reply_to_id: .replyTo.databaseId,
      html_url: .url,
      reactions: ((.reactions.nodes | map({(.content): 1}) | add) // {}),
      is_resolved: $resolved
    }
' | jq -s '
    group_by(.in_reply_to_id // .id)
    | map(sort_by(.created_at))
    | sort_by(.[0].created_at)
    | flatten
    | to_entries
    | map(.value + {index: ("§" + ((.key + 1) | tostring)), anchor: (.value.html_url | split("#") | last)} | del(.html_url))
    | group_by(.in_reply_to_id // .id)
    | sort_by(.[0].index | ltrimstr("§") | tonumber)
    | map(map({
    index,
    id,
    anchor: .anchor,
    path,
    body,
    user,
    created_at,
    diff_hunk: (.diff_hunk | if length > 350 then .[:350] + "..." else . end),
    in_reply_to_id,
    reactions: (.reactions | with_entries(select(.value > 0))),
    is_resolved
    }))
    | map(.[0] as $root | [$root] + (.[1:] | map(del(.diff_hunk, .is_resolved, .path))))
    | map(map(del(.in_reply_to_id)))
    | .[]
' -c > {OUTPUT_DIR}/{FILENAME}.ndjson

3. Управление выполнением

Шаг 0: Составь план

Ты ОБЯЗАН создать список дел с помощью инструмента todo_write.

Структура плана должна быть такой:

  1. Фаза 1: Подготовка и данные (ожидает)
  2. Фаза 2: Загрузка контекста (ожидает)
  3. Фаза 3: Общий обзор (ожидает)
  4. Фаза 4: Намерения (ожидает)
  5. Фаза 5: Развитие (Слияние) (ожидает)
  6. Фаза 6: Отчёт о полноте (ожидает)
  7. Фаза 7: Оценка от ИИ (ожидает)
  8. Фаза 8: Проверка и уборка (ожидает)
  9. Фаза 9: Авто-пост (ожидает)
  10. Фаза 10: Сводка для проверяющего (ожидает)

ВАЖНО: Правила завершения фазы После завершения КАЖДОЙ фазы (и перед началом следующей) ты ОБЯЗАН сделать две вещи:

  1. ОТЧЁТ В ЧАТ (ОБЯЗАТЕЛЬНО): Ты должен написать в чат краткий отчёт. Используй ровно этот формат:

      **Фаза {N} завершена**
  Итог: {1-2 предложения о том, что было сделано, без лишних деталей}
  Детали: {например, «Найдено 5 веток обсуждения», «Создано 3 намерения» и т.д.}

  2. ОБНОВИ СПИСОК ДЕЛ: Вызови todo_write, чтобы отметить текущую фазу как завершено, а следующую как в процессе.

Ограничение: Нельзя пропускать отчёт в чат. Это нужно, чтобы пользователь видел, что происходит. Ограничение: Только по порядку. Не начинай следующую фазу, пока не отчитался о текущей. Не загружай данные для будущих фаз заранее. Ограничение: Дождись завершения. Ты ДОЛЖЕН увидеть сообщение об успехе от инструмента, прежде чем начинать думать о следующей фазе.

  • Всё под контролем: Учти каждый комментарий.

5. Процесс создания документа

5.1. Фаза 1: Подготовка и данные

  1. Загрузи данные: Документы, информацию о PR, комментарии.

  2. Создай файл-шаблон:

    • Создай файл {OUTPUT_DIR}/{FILENAME}.md с ТОЧНО такой структурой (переведи весь текст и заголовки на {language}):
    # Alignment: {DATE}

- Статус: Проект консенсуса
- Автор: {PR_AUTHOR}
- Источник: {PR_LINK}
- Период: {SINCE_DATE} - {NOW}

{{WARNING_PLACEHOLDER}}

## Общий обзор

{{OVERVIEW_PLACEHOLDER}}

## Список Намерений (Консенсус)

{{INTENTS_PLACEHOLDER}}

{{QUESTIONS_PLACEHOLDER}}

{{COVERAGE_PLACEHOLDER}}

{{OPINION_PLACEHOLDER}}

{{INSTRUCTIONS_PLACEHOLDER}}

5.2. Фаза 2: Загрузка контекста

  1. Проанализируй данные:

    • Посчитай ветки обсуждений: Выполни команду wc -l {OUTPUT_DIR}/{FILENAME}.ndjson. Каждая строка — это одна ветка.
    • Отчитайся: Напиши, сколько веток ты нашёл.

  2. Загрузи в память:

    • Прочитай файл {OUTPUT_DIR}/{FILENAME}.ndjson (порциями по 25 строк).

5.3. Фаза 3: Общий обзор

Анализ: ВАЖНО: Ответь на эти 8 вопросов в виде списка. Это и будет твой ОБЩИЙ ОБЗОР.

  1. Чего хотел добиться проверяющий?
  2. С чем согласился автор?
  3. С чем не согласился автор?
  4. О чём вообще был разговор?
  5. Были ли недопонимания?
  6. Остались ли открытые вопросы?
  7. Появились ли новые идеи в ходе обсуждения?
  8. Какие ещё документы с этим связаны?

Создание:

  • Замени {{OVERVIEW_PLACEHOLDER}} на получившийся текст.

5.4. Фаза 4: Намерения

Анализ: Цель: Максимальная детальность. Каждая задача должна быть очень маленькой и конкретной.

  • Правило «И»: Не используй союз «и». Если в задаче есть «и», раздели её на две. Например, вместо «Нарисовать дом и посадить дерево» сделай две задачи: «Нарисовать дом» и «Посадить дерево».
  • Одна задача — одно дело: Каждое Намерение должно описывать одно конкретное техническое изменение.
  • Подробности важнее всего: НЕ СОКРАЩАЙ. Давай полный контекст. Объясняй «Что» и «Почему» нужно сделать.
  • Показывай код: ВСЕГДА включай в описание задачи относящийся к ней код (diff_hunk). Если фрагментов кода много, покажи самые важные.
  • Определи контекст: Пойми, к чему относится каждое намерение:
    • Спецификация: Изменения в правилах или требованиях (в markdown-файлах).
    • Код: Изменения в самой программе (в ts/tsx-файлах).
    • Тесты: Изменения в тестах.
    • Процесс: Изменения в документации или рабочих процессах.
  • Как понять решение автора:
    • Прямо сказал: Если автор чётко написал, что он решил, используй его слова.
    • Понятно по реакции (Эмодзи): Если слов нет, посмотри на эмодзи под комментарием проверяющего (например, 👍, 🚀, 👀). Считай, что это автор выразил своё согласие.
    • Не выдумывай: Если нет ни слов, ни эмодзи, отметь задачу как «Ожидает ответа». НЕ придумывай решение за автора.
  • Что значат статусы:
    • Готово: Автор написал, что сделал, и споров больше нет.
    • Согласовано: Все договорились, но задача ещё не выполнена.
    • Отклонено: Автор объяснил, почему не будет этого делать.
    • Обсуждение: Спор ещё идёт, решения нет.
    • Уточнение: Не хватает информации, чтобы принять решение.
    • Отложено: Идея хорошая, но её сделают позже.
    • Устарело: Намерение из старого обсуждения, сейчас неактуально.
  • Как понимать контекст:
    • Markdown-файлы (*.md): Комментарии здесь обычно относятся к правилам и идеям, а не к коду.
    • Файлы с кодом: Комментарии относятся к тому, как программа написана.
    • Что делать: Чётко указывай, к чему относится задача (к правилам или к коду).

Создание черновика (Обязательно):

  1. Выведи в контекст: Покажи в чате полный список «Свежих Намерений», которые ты только что придумал.
  2. Формат: Используй стандартный шаблон для Намерений.
  3. Заголовок: Перед списком напиши ### Черновик свежих Намерений.
  4. Пока НЕ записывай это в итоговый файл.

5.5. Фаза 5: Развитие (Слияние)

Цель: Объединить «Свежие Намерения» (из фазы 4) с теми, что уже были в «Прошлой Сверке».

  1. Проверь настройки:

    • Если merge_alignments равно false: пропусти шаги 2-3. Просто используй «Свежие Намерения».

  2. Загрузи прошлую Сверку:

    • Выполни команду, чтобы найти на GitHub прошлый отчёт: 
      gh api "repos/{OWNER}/{REPO}/issues/{PR_NUMBER}/comments" \
--jq 'map(select(.body | contains("# Alignment"))) | sort_by(.created_at) | last | {id: .id, body: .body}'
    • Что делать: Прочитай результат.
    • Сохрани: Сохрани текст отчёта (.body) как «Основу» для слияния.
    • ЗАПОМНИ: Запиши найденный id в свой отчёт о Фазе 5 (например, «Найден ID прошлой Сверки: 12345»). Он понадобится в Фазе 9.

  3. Как объединять:

    • Источники: Используй «Свежие Намерения» и «Основу».
    • Сравнивай: Найди, какие свежие намерения соответствуют старым (по теме).
    • Если нашёл совпадение: Сохрани старый номер (#{N}). ОБНОВИ заголовок, детали, статус и код, взяв информацию из свежего анализа. Не оставляй старые слова, если новые лучше.
    • Если намерение новое: Дай ему новый номер (следующий по порядку после самого большого старого номера).
    • Если старое намерение не обсуждалось: Если в «Основе» есть намерение, которого нет в свежем списке, оставь его как есть. Не меняй статус и не удаляй.

  4. Создание и запись:

    • Логика:
