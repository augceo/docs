План

Это словно карта действий агента, которая представляет собой граф Вызовов Инструментов. Эта карта передается от шага к шагу, чтобы система не забывала, что она делает, и умела менять тактику на ходу.

Сообщение План — это главный способ заставить агента помнить всё задуманное. Агент умеет выполнять простые разовые просьбы, как торговый автомат. Но когда появляется План, это сигнал: мы начинаем долгий проект. Это заставляет Цикл Выполнения бережно хранить составленный план и результаты (то есть Состояние) от одного шага к другому, будто вкладывать закладку в книгу.

Эта память — фундамент для создания умных агентов. Когда мозг системы получает свой План вместе со свежим Состоянием, он мгновенно понимает, где находится, как турист с картой. Он может идти прямо по маршруту, добавлять туда новые Вызовы Инструментов или вообще порвать карту и придумать новую, если столкнется с закрытой дорогой. Без Плана каждый запрос — это чистый лист, и агент ничего не вспомнит о прошлых решениях.

Как строится План

Связи между этапами не прописываются жесткими линиями. Они похожи на передачу эстафетной палочки — информация течет от шага к шагу через Состояние.

  • Узлы (Вызовы Инструментов): Каждый шаг — это конкретное действие, которое нужно сделать.

    • 008: Агент/Вывод

    Связи (через Состояние): Шаги связываются друг с другом, записывая и считывая данные из Состояния. Один Инструмент записывает свой ответ в определенное место, используя свойство Путь Вывода. А следующий Инструмент может забрать этот ответ в качестве входных данных, используя Ссылку на Переменную на то же самое место.

Так появляется строгая очередь: второй Вызов Инструмента не сможет ожить, пока первый не сделает работу и не положит информацию в Состояние.

Например, План проверить профиль пользователя, а затем сделать по нему краткую выжимку, будет состоять из двух Вызовов Инструментов:

[
  {
    "_tool": "fetchUserProfile",
    "userName": "Alice",
    "_outputPath": "†state.userProfileData"
  },
  {
    "_tool": "summarizeProfile",
    "profile": "†state.userProfileData",
    "_outputPath": "†state.profileSummary"
  }
]

Здесь шаг summarizeProfile должен дождаться, пока fetchUserProfile принесет ответ, образуя двухшаговый маршрут. Это легко представить в виде простой схемы.

Содержимое Плана: Граф Потока Данных

План не обязан состоять только из прямой, как стрела, последовательности. В нем могут быть узлы с условиями: когда дорога разветвляется в зависимости от того, как прошел другой шаг:

То, что лежит внутри сообщения План, называется графом потока данных. Это схема, которая строит стратегию агента как цепочку взаимосвязанных Вызовов Инструментов. Представляя работу в виде такой схемы, система может четко понимать, что за чем должно идти, где результат одной функции дает старт другой. Это удобный технический формат, который Цикл Выполнения легко считывает и запускает в работу.

Кстати, такую структуру графа можно использовать не только для запуска рабочих процессов. Вы можете попросить агента набросать граф Вызовов Инструментов для чего-то совершенно иного — нарисовать карту социальных связей, показать структуру базы данных или визуализировать проект.

Важно отличать такие рисунки от реального Плана. Да, внутри всё устроено похоже, но настоящим путеводителем они становятся только тогда, когда мы отправляем их в Запрос как специальное сообщение Plan, подразумевая, что мы хотим, чтобы агент пошел работать. Это защищает систему от путаницы, где мы просто визуализируем идеи, а где раздаем приказы.

Хотя План отлично помогает накидывать идеи или "думать вслух", здесь он в первую очередь нужен для старта реальной работы. Поэтому мы используем формат Ориентированного ациклического графа (DAG), где каждая точка — это Вызов Инструмента.

У этого DAG есть несколько строгих правил, которые делают его идеальным для дела:

  • Граф (Схема): Это весь набор вашего сообщения План: сами Вызовы Инструментов (узлы) и потоки данных, которые их соединяют (ребра).
  • Ориентированный: Связи идут только в одну сторону, как вода по течению реки. Шаг, который создает данные, всегда стоит перед шагом, который их пьёт.
  • Ациклический (Работа без зацикливаний): В маршруте нет круговых ловушек, благодаря чему у него есть ясное начало и логичный конец. Это важнейшая функция безопасности — она не дает LLM построить бесконечную карусель. Перед тем как начать, система проверяет, всё ли в порядке и нет ли циклов.

Чтобы заставить план бегать по кругу (как цикл for), мы используем прием делегирования и вложенности. Главный, "верхний" План занимается подсчетом (например, отмеряет шаги-итерации), а для каждого нового оборота привлекает Делегата, вызывая его как отдельный запрос. Внутри этого под-запроса существует свой маленький, отдельный План, и он занимается логикой одной конкретной итерации. Именно так мы безопасно строим кольцевые циклы и никогда не запутываемся.

Любой шаг запускается в ту секунду, когда по его Пути Вывода появляется значение, и ни секундой раньше. Шагу не нужны метки "готово" или "подожди-ка" — он просто смотрит, появились ли нужные данные в Состоянии. Именно из этого правила вытекает вся магия системы — ветвления маршрута, ожидание еще не родившихся результатов и разница между ними.

Планирование и Выполнение — это одно и то же действие

Планировать — значит уже действовать. У агента нет никакого ползунка переключения режима. Когда LLM выдает своё solution (решение), она одновременно и размышляет над проблемами, и сразу закрывает все шаги, которые может закрыть сейчас.

  • Скрытый инструмент (например, нарезающий текст на абзацы) в одной мысли получает и свой приказ (call), и выплёвывает готовый результат (_output).
  • Явная Активность отправляется в путь с помощью Цикла Выполнения ровно в тот момент, когда для нее найдены значения по её Ссылкам на Переменные.

Второе условие — это и есть всё правило планирования. Инструмент запускается ровно тогда, когда у него есть на руках всё, что он запрашивал. Шаг, который еще не готов бежать, — это просто шаг, которому не хватает информации.

Таким образом, агенту вообще не обязательно заканчивать весь план за один заход. Он рисует всю схему разом и выполняет те кусочки, которые может. Если для скрытого шага еще нет входных данных (они просто не подъехали), он оставляет ячейку _output пустой, а не фантазирует результаты из воздуха. Это не считается ошибкой — он просто не запускается. Шаг покорно лежит в плане, а на следующем ходу, когда долгожданная информация появляется, агент быстро его доделывает.

Развилка путей (вида †state.sunny <|> †state.rainy) работает точно так же и переживет текущий ход. Когда ход проектируется, никаких данных для явного вызова еще в природе нет, так что выбирать не из чего. Активность сделает свой ход во время работы. А вот скрытый вызов всегда работает наоборот: его _output (исход) — это собственные размышления модели, поэтому, придумывая план, она уже делает этот выбор. Альтернативы, которые модель решила не брать, просто считываются со состояния чуть позже. Те ветки, где значений так и не появилось — это просто те रास्ते, по которым мы никогда не пойдем. Инструменты, которые на них стояли, просто отпадают, а не отмечаются как провалы.

Предлагать, а не Выполнять

Осознанный подход к работе — сначала строим план, затем ждем проверки человеком — тоже не требует никаких "особых кнопок". Это всё то же правило расписания, только использованное хитро: черновик (предложение плана) — это просто инструмент, который ждет данных оттуда, куда их еще никто не написал.

Что это за пути? Вы решаете сами на уровне договоренности. Любая запись в области †state.approvals (согласования) — это барьер-блокпост, и нет других способов его возвести: никаких галочек напротив задач, никаких тайных каналов. Если барьер нужно где-то регистрировать галочкой, кто-то обязательно об этом забудет. Вы не можете "забыть" сам путь к данным.

Дайте каждому запасному плану свой личный барьер и пускай каждый его первый шаг читает именно его. План А будет ждать переменную †state.approvals.planA, а План B будет ждать †state.approvals.planB. Пока данных нет ни там, ни там, оба плана спят, и сидят в Плане просто как предложения командиру — как чистая схема ваших возможных тактик. И это ровно то, чего требует осознанная работа. Черновик маршрута можно:

  • Проверить: посмотреть, нет ли на маршруте глупых зацикливаний или других оплошностей.
  • Отрепетировать: прогнать вхолостую и сымитировать действия.
  • Представить на одобрение: показать живому человеку, чтобы он подправил, поменял или дал этому зеленый свет (HITL).

Дать зеленый свет означает просто записать значение в этот блокпост. И всё, никаких секретных механизмов больше нет — шаги выбранного плана немедленно просыпаются (ведь теперь им есть что читать!), а шаги выброшенной в мусорку альтернативы остаются стоять столбом и тихо отпадают со следующего хода. Какому варианту какой шаг принадлежит — определяется исключительно путем к барьеру. Нет никакого специального ярлычка "ожидает ревью" и никакой параллельной системы.

На деле только ПЕРВЫЙ шаг ветки спрашивает барьер; остальные шаги читают то, что напишет он. Вся эта куча следующих за ним шагов висит на блокпосте, и ждет по той же самой причине, хотя барьер упомянут только на самом верху.

Одобрение — это процесс, происходящий МЕЖДУ заходами, а никогда не внутри одного захода. Ничто внешнее не может влезть и поменять Состояние, пока цикл вертится. Поэтому предложение никогда в жизни не будет выполнено ровно на том же шагу, который его породил. Модель делает предложение, цикл тормозит. Человек (или другой управляющий) смотрит, решает, записывает одобрение в блокпост, и вот уже следующий цикл начинается с этого значения, которое лежит в Состоянии готовеньким. Ничего не надо ставить на паузу, ничего не надо замораживать в криокамере. От Цикла Выполнения не требуется никакой сложной памяти. Красота и дешевизна механизма кроется как раз в том, что все решается просто именем переменной.

Ждущее предложение — это не поломка, и как ошибка оно не светится. Запрос ждёт. А вот запрос, стоящий на пути, куда уже никто никогда ничего не напишет — он уже сломан. И тот, и другой всего-навсего столкнулись с тем, что их Ссылки на Переменные не материализовались. Система аккуратно выводит ожидание один раз в конце цикла: "Мы ждем у блокпоста". Она не пишет это каждый ход красными буквами, иначе контекст лопнет от спама, а модель испугается и решит, что использовать контрольные барьеры — это преступление.

Одобрение для отдельных задачек-экземпляров не усложняет систему. Барьер — это просто обычный путь в Состоянии, он работает так же, как остальные: если повесить добро глобально, он разбудит потоки у всех экземпляров сразу; если записать добро на один конкретный экземпляр, разбудится только он один, а остальные продолжат дремать на блокпосте. Никакого особого синтаксиса не требуется, потому что строгие правила из 013: Агент/Экземплирование и без этого все прекрасно рулят.

Учитывайте единственную важную вещь: план-предложение с инструментами, у которых уже есть всё для старта, сорвется с цепи моментально. Инструмент, который читает переменные, уже лежащие сейчас в Состоянии — это не предложение, это прямой приказ. Поэтому барьер должен быть Ссылкой на Переменную. †state.approvals.planA — будет ждать. А слово "approved", гордо написанное прямо в значение, ждать никого не собирается. Если хотите, чтобы план предлагался — заставьте его ждать несуществующих данных.

План как Живая Стратегия

План не высечен в камне; это живая стратегия. Его можно менять и перемалывать на каждом кругу вашей работы. Но помните, что План — это не любая строчка, прилетевшая от нейросети (LLM). Когда модель в первый раз высыпает стопку Вызовов Инструментов — она лишь предлагает сценарий действий. Настоящим Планом он становится только когда мы пришиваем его как сообщение контекста к следующему запросу в цикле.

Это колесо трансформирует одноразовый позыв в бесконечный, гибкий подход:

  • контекст нового запроса держит в кармане Состояние и сообщение с Планом с нашего прошлого круга.
  • Новое решение, которое рожает LLM, хранит новую комбинацию Вызовов Инструментов, и вот уже эта комбинация станет нашим новеньким Планом для следующего шага.

Такой круговорот помогает агентам быть и целеустремленными, и гибкими. Он может спокойно двигаться по изначальному Плану, но если что-то свернуло не туда (например, Вызов Инструмента выдал ошибку), он может на лету нарисовать себе свежий План, обходящий проблему. Система становится упругой, как мячик, и выкручивается из любых ситуаций.

Пример: Планирование на шаг вперед

Этот пример показывает, как План работает словно колея, направляя агента и не давая ему свернуть со стандартного пути, даже когда вокруг много других привлекательных вариантов.

Сценарий: Агенту службы поддержки нужно сделать возврат средств. Обычное дело — сначала проверить историю платежей клиента (понять всю картину), а затем вернуть деньги.

1. Начальный Запрос

В самом начале поступает просьба клиента. Опираясь на этот input, языковая модель пишет себе стандартный План в два шага. Это идеальный маршрут, когда всё идет хорошо.

Контекст и Схема Запроса

// Agent.Request(config, schema, context)
{
  "schema": {
    "type": "object",
    "properties": {
      "calls": { "type": "array" },
      "output": {
        "type": "object",
        "nullable": true,
        "properties": {
          "confirmationId": { "type": "string" },
          "message": { "type": "string" }
        }
      }
    }
  },
  "context": [
    {
      "type": "input",
      "request": "I'd like a refund for my last order.",
      "customerId": "cust_123",
      "amount": 50.0
    }
  ]
}

Решение от LLM (`solution`)

{
  "calls": [
    {
      "_tool": "checkBillingHistory",
      "customerId": "†input.customerId"
    },
    {
      "_tool": "issueRefund",
      "customerId": "†input.customerId",
      "amount": "†input.amount"
    }
  ],
  "output": null
}

2. Следующий Запрос в Цикле

Цикл Выполнения запускает команду checkBillingHistory и загружает результаты в Состояние. История полна сюрпризов (например, клиент уже делал отмену платежа). Агент без четкого руководства, скорее всего, испугался бы и передал это дело начальнику (вызвал бы инструмент escalateToSupervisor).

Но у нас под рукой План. Скрестив то, что агент знает (сложное Состояние) с тем, что он должен делать (План), мозг агента точно понимает, где находится, и продолжает уверенно идти по колее "идеального пути".

Контекст

[
  {
    "type": "state",
    "billingHistory": {
      "orders": 5,
      "lastChargeback": "2025-09-10"
    }
  },
  {
    "type": "plan",
    "plan": [
      {
        "_tool": "checkBillingHistory",
        "customerId": "†input.customerId"
      },
      {
        "_tool": "issueRefund",
        "customerId": "†input.customerId",
        "amount": "†input.amount"
      }
    ]
  }
]

Новое Решение от LLM

{
  "calls": [
    {
      "_tool": "issueRefund",
      "customerId": "†input.customerId",
      "amount": "†input.amount"
    }
  ],
  "output": {
    "confirmationId": "refund_xyz789",
    "message": "The refund has been processed successfully."
  }
}

План следит за порядком, останавливая случайную панику и удерживая действия в задуманном русле.

Пример: Корректировка Плана

Этот пример демонстрирует, как агент может подкорректировать свой текущий План на ходу, если поступят новые обстоятельства, просто выбрав другой инструмент.

Контекст

Агенту дается изначально правильный План, но приходит новый Input (Ввод) от пользователя с другим важным ограничением.

[
  { type: 'tool', tool: Tool.bookFlight },
  { type: 'tool', tool: Tool.bookHotel },
  { type: 'tool', tool: Tool.findPetFriendlyHotel },
  {
    type: 'plan',
    plan: [
      {
        _tool: 'bookFlight',
        destination: '†input.destination',
      },
      {
        _tool: 'bookHotel',
        destination: '†input.destination',
      },
    ],
  },
  {
    type: 'input',
    destination: 'Berlin',
    instruction: "Actually, I'll be traveling with my dog.",
  },
];

Решение от LLM (`solution`)

LLM видит, что старый план никуда не годится. Модель берет старый план, выбрасывает его и пишет себе новый, заменяя обычный выбор отеля на более подходящий инструмент.

{
  "calls": [
    {
      "_tool": "bookFlight",
      "destination": "†input.destination"
    },
    {
      "_tool": "findPetFriendlyHotel",
      "destination": "†input.destination"
    }
  ],
  "output": null
}

Модель не просто меняет настройку или пару цифр; она в корне меняет подходы, подбирая другой Инструмент (findPetFriendlyHotel), потому что условия игры изменились. Эти новые инструменты — новый План агента для следующего шага в Цикле Выполнения.

Пример: Работа с Ограничениями и Ошибками

Этот пример показывает, как агент реагирует, если идеальный сценарий Плана терпит крах. Вы увидите два этапа: изначальный радужный план и срочный "пересмотр", который происходит, если ломается инструмент.

1. Изначальный План

Агенту дают в руки инструменты и сумму задачи. Он рисует красивый двухэтапный План, который даже не предполагает, что что-то может сломаться.

Первоначальный Контекст

Agent.Request(config, {
  schema: {
    type: 'object',
    properties: {
      calls: { type: 'array' },
      output: {
        type: 'object',
        nullable: true,
        properties: {
          status: {
            type: 'string',
            enum: ['Success', 'Failed'],
          },
        },
      },
    },
  },
  context: [
    { type: 'tool', tool: 'Tool.processPayment' },
    { type: 'tool', tool: 'Tool.confirmOrder' },
    { type: 'tool', tool: 'Tool.reportFailure' },
    { type: 'input', amount: 50.0 },
  ],
});

Первоначальное Решение

{
  "calls": [
    {
      "_tool": "processPayment",
      "amount": "†input.amount",
      "_outputPath": "†state.receipt <|> †state.error"
    },
    {
      "_tool": "confirmOrder",
      "receipt": "†state.receipt"
    }
  ],
  "output": null
}

2. Ошибка и Перестроение Плана

Цикл Выполнения пытается провести оплату processPayment, но банк дает отказ. Движок записывает значение в переменную †state.error. При новом заходе модель видит ошибку в контексте, смотрит на уже неактуальный красивый план, и собирает спасательную стратегию.

Контекст для Следующего Запроса

[
  {
    "type": "state",
    "error": { "code": "card_declined", "message": "Your card was declined." }
  },
  // Старый и уже неактуальный план всё еще находится в контексте
  {
    "type": "plan",
    "plan": [
      { "_tool": "processPayment", "_outputPath": "†state.receipt <|> †state.error" },
      { "_tool": "confirmOrder", "receipt": "†state.receipt" }
    ]
  }
]

Новое Решение (Обновленный План)

{
  "calls": [
    {
      "_tool": "reportFailure",
      "error": "†state.error"
    }
  ],
  "output": { "status": "Failed" }
}

Агент заметил, что в Состоянии теперь лежит error (ошибка). Он забросил старый "идеальный" План и состряпал себе новый, состоящий всего из одного шага reportFailure (Сообщить о провале). Так система реактивно маневрирует при внезапных неудачах.

Пример: Планирование по Схеме

Этот пример показывает, как передача жесткой schema (схемы) для Состояния работает как трафарет, позволяющий модели (LLM) построить идеально правильный, крепкий План.

Контекст со Схемой Состояния

Мы даем входные данные Input и кидаем сообщение State, в котором есть лишь пустышка — schema (схема). Она и диктует логику того, как переменные в плане будут перетекать друг в друга.

[
  { "type": "tool", "tool": "Tool.detectLanguage" },
  { "type": "tool", "tool": "Tool.isEnglish" },
  { "type": "tool", "tool": "Tool.translateText" },
  {
    "type": "input",
    "text": "Bonjour le monde"
  },
  {
    "type": "state",
    "schema": {
      "type": "object",
      "properties": {
        "language": { "type": "string" },
        "isEnglish": { "type": "boolean" },
        "translatedText": { "type": "string" }
      }
    }
  }
]

Решение от LLM (`solution`)

Модель использует эту схему Состояния как готовый чертеж. Ей не нужно ничего изобретать, она просто бережливо скрепляет Путь Вывода одной команды с проводами входа другой.

{
  "calls": [
    {
      "_tool": "detectLanguage",
      "text": "†input.text",
      // LLM в курсе, что путь можно подглядеть из схемы
      "_outputPath": "†state.language"
    },
    {
      "_tool": "isEnglish",
      // Модель корректно перенаправляет результаты прошлого шага.
      "language": "†state.language",
      "_outputPath": "†state.isEnglish"
    },
    {
      "_tool": "translateText",
      "text": "†input.text",
      "isEnglish": "†state.isEnglish",
      "_outputPath": "†state.translatedText"
    }
  ],
  "output": null
}

Давая schema (схему), мы предоставляем агенту четкий чертеж. Модели не нужно ломать голову над именами переменных или их порядком в танце; она просто расставляет детали по готовым окошкам. Результат — надежный, железобетонный План.

Эта повторяющаяся карусель из планов и их выполнения — бьющееся сердце любого Процесса. Окружение как бы делает моментальный снимок происходящего: набор открытых Инструментов, живое и дышащее Состояние с данными, плюс сам План.

От Единого Плана к Повторным Рабочим Процессам

Сам по себе План просто обозначает цепочку действий для одной-единственной задачи. Но если мы хотим превратить это в настоящие многоразовые механизмы, которые можно "вызывать на помощь" из других Планов, нам нужно красиво упаковать их в компоненты.
