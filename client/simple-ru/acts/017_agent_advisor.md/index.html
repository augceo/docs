017: Агент/Советник

  • Требуется:
    • 001: Агент/Запрос
  • Улучшает:
    • 002: Агент/Инструмент
    • 010: Агент/Цикл
Advisor

Специальное контекстное сообщение (с kind: "advisor"), которое определяет роль или модель анализа. Оно поручает агенту составить свое "мнение" или оценку уверенности в формате четкой структуры до выбора Инструмента или генерации Вывода.

Протокол Советников заставляет систему работать по принципу "сначала подумай, потом делай". Регистрируя Советников, агент смотрит на задачу через призму определенных ролей — например, как "Архитектор безопасности" или "Менеджер продукта" — прежде чем начать действовать.

Ненаправленное мышление

Рассуждения без структуры (в духе "Цепочки мыслей") часто бывают хаотичны. Агенты блуждают без карты, смешивая сбор информации, логику и принятие решений в один шумный поток текста.

Из-за такого отсутствия структуры контекст забивается лишними рассуждениями. Без четкого направления агент путается, бесконечно меняет мнение, что приводит к снижению общей точности. Это похоже на попытки извлечь точные цифры из хаотичного эссе. Решения, которые строятся на базе такого сплошного текста, трудно отследить.

Протокол Советников решает эту проблему, наводя порядок в рассуждениях. Он помогает проводить оценку четко и предсказуемо. Это также улучшает понимание того, как работает система. Вместо "простыней текста", скрытых внутри логов, мы получаем структурированные, взвешенные ответы. В них сразу видно, где мнения расходятся, к чему склоняется система и какие дает рекомендации. Так гораздо проще принимать решения и составлять понятные отчеты.

Протокол Советников не заменяет скрытое рассуждение языковой модели, он лишь упорядочивает одну конкретную часть этого процесса. Он превращает оценку в понятный артефакт — взвешенное мнение, которое становится прямой инструкцией для принятия решений.

Разные взгляды и выбор инструментов

Регистрируя нескольких Советников, система заставляет агента смотреть на проблему с разных, часто противоположных сторон (например, с точки зрения "Рисков" и "Возможностей"). Это расхождение мнений ложится в основу механизма Взвешенного выбора инструментов, когда Советники выдают конкретные "голоса" или оценки уверенности за определенные Инструменты.

Агент собирает эти голоса со своего совета. Он не просто берет инструмент "наугад", а сводит воедино разные мнения, чтобы прийти к общему знаменателю. Использование инструмента — это расчетливый результат противоборствующих советов.

Сообщение Советника

Сообщение Советника задаёт оптику, через которую агент будет смотреть на проблему.

  • id: Уникальный идентификатор советника (например, "securityArchitect").
  • persona: Для чего нужен этот советник — его область знаний и точка зрения, которую он отстаивает.
  • answer: JSON-схема, описывающая форму ответа советника. Это позволяет получать точные количественные данные (оценки риска, бюджеты и т.д.) вместо простого голосования.
  • on: Задаёт стратегию участия советника.
  • scopes: Список ключей контекста (например, ["input", "state"]), на которых должен сфокусироваться советник.
  • isInstanced: Флажок (по умолчанию false). Если true, советник анализирует каждый элемент индивидуально при массовой обработке контекстов в партии.

Поля persona и answer не обязательны, но если вы задаете схему answer, она напрямую влияет на форму результата модели: требуете от неё выбрать один из двух вариантов — получите этот вариант, а не сплошной текст.

Один советник, много сообщений

Советник — это не просто одно отдельное сообщение; это собирательный портрет всех сообщений с одним и тем же id. Позднее сообщение просто обновляет существующего Советника поле за полем, так что запрос может уточнить роль, которую система уже зарегистрировала раньше:

{
  "type": "advisor",
  "id": "riskAnalyst",
  "answer": {
    "type": "object",
    "properties": { "score": { "type": "number" } }
  }
}

В этом сообщении не указано поле persona, и это нормально. Более свежие сообщения побеждают при перезаписи полей. В свою очередь, неизвестный id просто создаст нового Советника с нуля. О цене этого правила стоит сказать прямо: опечатка в id незаметно создаст нового пустого Советника без роли, вместо того чтобы обновить уже работающего.

Параметр on является исключением и устанавливается только один раз. Он решает, как именно Советник будет работать — в качестве свойства в ответе, или через инструмент ConsultAdvisor. Если попытаться сменить роль в процессе, система сломается на границах кеша. Сообщение без параметра on просто наследует то, что было задано ранее.

Стратегии выполнения

Настройка on управляет тем, когда Советник включается в процесс:

  • start (В начале): Высказывает своё мнение только в самом начале диалога, чтобы задать направление.
  • finish (При завершении): К нему обращаются, когда нужно решить, стоит ли останавливать цикл.
  • request (Постоянно): Подает голос при старте, при завершении и на каждом шаге цикла. Отлично подходит для мониторинга безопасности или ключевых стратегических ролей.
  • null / undefined (По запросу): Молчит, пока его не позовут. В системе есть специальный мета-инструмент ConsultAdvisor, с помощью которого языковая модель может сама позвать таких советников, если столкнётся со сложным выбором.

Порядок советов

Когда Советники включены, языковая модель в первую очередь генерирует их структурированные ответы. Она буквально "надевает шляпу" этих персонажей, чтобы проанализировать состояние дела или проголосовать за дальнейшие действия. Затем Агент сразу использует эти ответы для финального решения о том, какой Инструмент применить.

Количественные данные, такие как "голоса", записываются в виде текстового JSON (Inline JSON) прямо внутри строки. Это не перегружает общую структуру ответа, но сохраняет математическую точность.

Регистрация Советников

[
  {
    "type": "advisor",
    "id": "riskAnalyst",
    "on": "request",
    "scopes": ["†state.deploymentHistory"],
    "persona": "Analyze risks and Vote for deployment actions.",
    "answer": {
      "type": "object",
      "properties": {
        "thought": { "type": "string", "description": "Risk assessment of the deployment." }
      },
      "required": ["thought"]
    }
  }
]

Ответ языковой модели

{
  "advisors": [
    {
      "id": "riskAnalyst",
      "thought": "The new feature has passed unit tests but lacks integration tests. High risk of regression.",
      "calls": "{\"deploy\": 10, \"rollback\": 5, \"delay\": 95}"
    }
  ],
  "calls": [
    {
      "_tool": "delay",
      "_why": "RiskAnalyst strongly advises delaying due to insufficient testing."
    }
  ]
}

Взаимодействие с другими системами

    • 002: Агент/Инструмент

    Инструмент: Советники не выполняют никаких действий сами, они лишь голосуют за них. Применение советника выглядит как вызов обычного инструмента в структуре ответа, но на самом деле это мета-действие, "мыслительный процесс", который строго предшествует применению реального Инструмента. Это гарантирует, что мы собираем советы до того, как начать действовать.

    • 010: Агент/Цикл

    Цикл: Параметр on встраивает советников в рабочий процесс агента. Советники со значением on: request работают как постоянные мониторы на каждом витке цикла. А если on: null (по запросу), они выступают в роли клапана безопасности, доступного для модели в ситуациях, когда она сталкивается с любой неопределенностью.

    • 012: Агент/План

    План: Советы крайне важны на этапе планирования. Опрашивая советников при старте (start) или постоянно (request), агент проверяет, сходится ли его изначальная стратегия с общим мнением профильных специалистов, и таким образом делает План надежным и осмысленным изначально.

    • 013: Агент/Экземплирование

    Экземплирование: Советники умеют работать с пакетными вычислениями. Если установить isInstanced: true, советник начнет различать отдельные задачи. Система создаст совет для каждого элемента контекста в партии по отдельности (используя _instance).

    • 015: Агент/Области видимости

    Области видимости: Параметр scopes помогает направить внимание советника. В отличие от строгой изоляции данных, как в Делегатах, здесь это работает скорее как мягкая подсказка — направление внимания. Она просит конкретного эксперта в первую очередь изучать указанные ключи контекста (например, ["†state.deploymentHistory"]), поддерживая разделение сфер ответственности без жесткой блокировки остальных данных.
