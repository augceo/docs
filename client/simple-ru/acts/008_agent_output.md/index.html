008: Агент/Результат

  • Требует для понимания:

  • Открывает путь к:

Путь Сохранения

Мета-свойство _outputPath в Вызове. Оно указывает, куда нужно сохранить результат работы инструмента. Представьте, что это адресная строка, которая говорит системе, куда положить данные, чтобы их легко можно было найти на следующих этапах.

У агента есть два вида результатов: промежуточные (когда Вызовы Инструментов записывают свои данные в общий контекст) и Итоговый Результат — то, что получается в самом конце работы.

Запись в контекст с помощью Путей Сохранения

Хотя писать можно в любое Сообщение с Данными, обычно результаты складывают в Сообщение Состояния, чтобы сохранить их между разными этапами длительного задания.

Хотя любое Сообщение с Данными может работать как черновик для записей, главное средство для сохранения данных — это мета-свойство Путь Сохранения. Когда система выполняет Вызов Инструмента с этим свойством, она добавляет его результат в общую историю как новую запись.

Это новое сообщение выглядит как обычное Сообщение с Данными, но в нем есть две дополнительные служебные пометки (которые скрыты от ИИ):

  • _call: оригинальный Вызов Инструмента, который произвел эти данные на свет.
  • _date: точное время (штамп времени), когда данные были записаны.
  • _outputMethod: способ сохранения данных, который говорит системе, как смешивать эту новую информацию с уже существующей.

Все это создает прозрачный журнал изменений, словно чек из магазина. Это помогает программистам понять логику агента и быстро находить ошибки.

Как задать Путь Сохранения

Указать Путь Сохранения можно двумя способами. Это дает вам разный уровень контроля над поведением инструмента.

Динамический путь (Решает ИИ)

Здесь языковая модель (ИИ) сама решает, куда сохранить результат прямо во время работы. Это делает инструмент очень гибким.

// Tool schema allows any string for _outputPath
{
  "_outputPath": {
    "type": "string",
    "description": "Path to store the user summary.",
    "pattern": "^†"
  }
}

Жесткий путь (Прописан заранее)

Этот подход заставляет инструмент работать строго по правилам — он всегда будет писать свой результат в одно и то же, заранее заданное место.

// Tool schema locks _outputPath to a specific value
{
  "_outputPath": {
    "type": "string",
    "const": "†data.user.summary"
  }
}

Динамическая сборка данных (Чтение прошлого)

Очень важный момент: когда появляются новые сообщения, они добавляются в конец списка, а не склеиваются в момент записи. Представьте себе стопку бумаг. Финальный результат собирается воедино только тогда, когда вы пытаетесь прочитать данные.

Когда системе нужно прочитать Ссылку на Переменную (например, адрес †data.user.name), движок начинает перебирать сообщения в обратном порядке — от самых свежих к самым старым.

  • Если движок находит сообщение с методом set (установить) или вообще без метода, он тут же останавливается. Это значение и становится финальным, а все старые документы игнорируются. Работает правило: "Кто последним написал, тот и прав".
  • Если он находит методы вроде merge (глубокое слияние), assign (замещение), push или concat (добавление в список), он продолжает листать стопку назад. Он собирает все такие сообщения, пока не наткнется на set или на самое дно стопки. Затем он воспроизводит все эти действия по порядку (от старых к новым), чтобы собрать итоговый результат.
  • Если он находит метод erase (стереть), он останавливается так же, как при set, но возвращает пустоту. Возникает ощущение, как будто по этому адресу никогда никто ничего не писал.

Такая система сборки данных помогает сохранять полную историю изменений и позволяет надежно управлять памятью.

Стирание данных как единственный способ отмены

Вызов считается завершенным, когда по его Пути Сохранения появляются данные. Нет никакого отдельного списка выполненных задач. Само наличие данных является доказательством того, что работа выполнена. Агент ждет своей очереди, потому что нужные ему данные еще пустые. И он начинает действовать, как только там что-то появляется.

Поэтому, если вы хотите запустить шаг заново, нужно удалить старый результат — "стереть" путь. Именно для этого существует метод erase. Перезапуск здесь выглядит не как приказ "начни заново", а как очистка старого черновика.

Из этого вытекает простое правило: если вызов ничего не записывает, у него нет состояния. Вызов без _outputPath не оставляет никаких улик. Система не знает, запускался он или нет, поэтому нет никакой разницы, выполнить его один раз или дважды. Если какое-то действие обязательно должно сработать только один раз, оно обязано оставить после себя запись.

Пример: Добавление и чтение данных

1. Начальное состояние

В самом начале у нас лежит только исходное сообщение data.

[
  {
    "type": "data",
    "data": { "user": { "name": "Alex", "status": "active" } }
  }
]

2. Запуск вызова инструмента

Мы вызываем инструмент, чтобы поменять статус пользователя.

// Call being executed
{
  "_tool": "updateUserStatus",
  "newStatus": "inactive",
  "_outputPath": "†data.user.status"
}

3. Память после запуска

Движок кладет в стопку новое сообщение. В нем записан результат и служебная информация о том, какой инструмент его произвел.

[
  // Original data message
  {
    "type": "data",
    "data": { "user": { "name": "Alex", "status": "active" } }
  },
  // Appended output message from the call
  {
    "type": "data",
    "data": { "user": { "status": "inactive" } },
    "_call": {
      "_tool": "updateUserStatus",
      "newStatus": "inactive",
      "_outputPath": "†data.user.status"
    },
    "_date": "2025-10-26T12:00:00Z"
  }
]

4. Чтение переменных

  • Чтобы узнать †data.user.status (статус пользователя), движок берет самое последнее сообщение. Находит там новый статус и возвращает "inactive".
  • Чтобы узнать †data.user.name (имя пользователя), движок тоже сначала смотрит на последнее сообщение. Там имени нет. Тогда он заглядывает в предыдущее сообщение, находит его там и возвращает "Alex"

Главная сила объединения Ссылок на Переменные и Путей Сохранения в том, что вы можете программировать опираясь на данные, которых еще даже не существует! Например, вы можете настроить Вызов на чтение Ввода пользователя до того, как пользователь что-то вообще написал. Это позволяет создавать универсальные шаблоны, которые подстраиваются под ситуацию.

Это работает и для соединения Вызовов в цепочку. Один инструмент может использовать результат предыдущего инструмента в качестве своих входных данных. Получается настоящий конвейер, где информация бесшовно перетекает от этапа к этапу.

Вызовы без пути сохранения (без результата)

Не каждому Вызову Инструмента нужно сохранять то, что он сделал. Если вы намеренно не укажете свойство _outputPath, вы тем самым поменяете поведение системы. Это нужно в двух случаях:

Мимолетные размышления (Для скрытых вызовов)

Если не указать путь сохранения для так называемого скрытого вызова, он превращается в "мимолётную мысль" агента. Это внутреннее рассуждение, которое помогает ИИ принять решение именно сейчас, но не засоряет долгосрочную память (оно не сохраняется в Состояние). Это отличный способ направить логику ИИ в нужное русло.

Например, агент может использовать скрытый инструмент think (подумать), чтобы проанализировать проблему и составить план. Эти размышления не сохранятся на будущее, но прямо в этот момент они обогатят внутренний контекст ИИ. Благодаря этому уже на следующем шаге ИИ создаст настоящие Вызовы, которые будут точнее и логичнее.

"Выстрелил и забыл" (Для обычных вызовов)

Для явного (открытого) вызова Действия отсутствие _outputPath означает работу по принципу "выстрелил и забыл". Цикл Исполнения запустит Действие, но не будет дожидаться его окончания или записывать результаты в память.

Это удобно для задач, чей результат никак не влияет на дальнейшую работу. Например:

  • Отправка отчета об ошибке в систему аналитики.
  • Отправка email-уведомления пользователю.
  • Запуск долгой фоновой задачи без остановки текущего процесса.

Вы платите за это отсутствием состояния: система не запоминает, что вызов состоялся. Выбирайте подход "выстрелил и забыл", только если случайный повтор этого действия не вызовет проблем. Во всех остальных случаях обязательно указывайте _outputPath.

Как это работает с другими системами

    • 005: Агент/Данные

    Сообщение с Данными: Путь Сохранения — это основной механизм создания бумажных записей в журнале агента. Он превращает обычный инструмент без памяти во вдумчивую операцию, сохраняя её плоды для будущих задач.

    • 009: Агент/Состояние

    Сообщение Состояния: Чаще всего эти данные пишутся именно в Сообщение Состояния. Благодаря этому объект Состояния становится надежным блокнотом, где разные инструменты обмениваются своими находками в течение долгого времени.

    • 007: Агент/Переменные

    Ссылка на Переменную: Это напарник Пути Сохранения. Один данные записывает, другой — их читает. Вместе они создают поток, похожий на электрическую цепь между инструментами.

    • 011: Агент/Выражения

    Выражения: Они добавляют математику и логику прямо в "провода" (пути) вашего агента. Используя в путях специальные значки вроде <|> и *>, инструмент может ставить условия или раздавать свои результаты сразу по нескольким адресам. Это учит систему быть гибкой.

    • 012: Агент/План

    План: Внутри Плана пути сохранения играют роль кабелей, соединяющих отдельные Вызовы Инструментов (узлы) в единый механизм, так что агент может воплощать в жизнь целые многоходовые стратегии.

    • 013: Агент/Экземплирование

    Экземплирование: Если вы запускаете несколько копий одного инструмента (с помощью свойства _instance), система сама позаботится о том, чтобы каждый из них писал отчеты только в свою личную "папку". Так данные разных агентов никогда не перемешаются.

От мимолетных мыслей к надежной памяти

Хотя система путей отлично передает информацию между отдельными Вызовами Инструментов, для создания умных и самостоятельных агентов нужна особая, специализированная память, которая не забывает важное между запросами.
